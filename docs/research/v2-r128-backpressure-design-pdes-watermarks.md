## §0 要旨

1. 今の艦隊の道は背圧になっていない。返事は「出した刻み+δ_think」と「届いた刻み」の遅い方に入る(`llm_io.py:140-142`)。GPU の遅さが世界の中の思考時間に漏れている。δ_think はランで 1 つ(既定 L1=1 刻み)。
2. PDES の言葉に直すと、エンジンは 1 分刻みの同期型の論理過程で、δ_think が lookahead に当たる。保守的同期の「安全になるまで待つ」が 10-25 §2-7 の背圧と同じ形になる。Fujimoto は「保守的同期の成否は lookahead で決まる」と書く [S1◎]。
3. ストリーム処理の透かしと違い、エンジンは未着の呼びをすべて知っている。だから完全な透かしが作れ、待てば遅れは 0 にできる。弱点は Akidau の言う「遅い 1 件が全体を止める」[S5◎]。直し方は先読みを延ばすこと・パイプラインにすること・区域ごとの時計(TM1)にすること。
4. 背圧の上限(体ごと 1 本・艦隊ごと N 本)は**世界の規則として決定論的に**置く。GPU の空き(demand・credit)で誰が考えられるかを決めると、漏れが入口に移るだけになる。輸送の層の credit は世界から見えない所(送りの待ち)に閉じ込める。
5. 集中の度合いで割り込む規則には注意点がある。Lavie らは、知覚の負荷は妨害を減らすが、作業記憶の負荷は妨害を**増やす**と報告した [S20◎]。「考えている最中ほど割り込まれにくい」は一般則にはならない。値は判断モデルに出させ、錨で確かめる形がよい(見立て)。
6. 「考えは捨てない」は、透かしの 3 つの扱い(捨てる・積み増す・取り消して出し直す)[S5◎] のうち「積み増す」に当たる。割り込まれた考えは、行動には使わずテープと本人の記憶に残す(Flink の脇の出力 [S6◎] に近い)。
7. 差分の見積り(推測)は src が +250〜450 行・試験が +300〜500 行。§6-1 メモの +130〜220 行は 2-7 の 1〜2 だけの値で、集中の規則・体ごとの上限・計器を足すと増える。
8. 段の分け方(見立て)は 2 段。背圧と体ごとの上限は「欠陥の直し」(mock の 19 構成は不変の見込み)。集中の規則は「改良の腕」にし、E 系列で確かめてから既定にする。

## §1 前提(リポの決定と今の実装)

### 1-1 決まっていること

- 10-25 §2-7: δ_think(世界の中の思考時間)と GPU の待ち時間(壁時計)を混ぜない。刻みは、その刻みに適用する返事がそろうまで進まない。返事に依らない処理は先に進めてよい。熟考中は System 1 が変化の強さと集中の度合いを比べ、強ければ打ち切り(まとまらない判断で行動)、弱ければ溜めて後で気づく。集中の度合いは熟考に入るときに判断モデルが決める。会話の相手の発話は常に割り込める([回答 10-25](../design/v2-answers-2026-10-25.md) §2-7)。

## §2 先例 A PDES の保守的同期と楽観的同期

| 事実 | 出典 | 等級 |
|---|---|---|
| 各 LP は届いた事象を時刻の順に処理する(局所因果制約)。同時刻を除けば、これを守れば逐次の実行と同じ結果になる | [S2] Fujimoto Synchronization | ◎ |
| 保守的=「安全になるまで待つ」(null message の CMB・デッドロックの検出と回復・ラウンドで回す同期型)。楽観的=違反を許し、ロールバックで直す(Time Warp) | [S2] | ◎ |
| null message は「この先に送る事象の時刻の下限」を知らせ、デッドロックを避ける。lookahead が小さいと null message が増える(time creep)。lookahead 0 の輪は livelock になる | [S1] Fujimoto Lookahead | ◎ |
| 「時刻 T の LP は T+L 以上の事象しか送らない」が lookahead。「保守的同期の成否は lookahead で決まる」。lookahead は物理の制約・割り込めない振る舞い・時刻の誤差の許容・次の相互作用の前もっての抽選から得られる | [S1] | ◎ |
| 時刻刻みのシミュレーションは暗に lookahead を使う(同じ刻みの事象は独立・新しい事象は次の刻み以降) | [S1] | ◎ |
| lookahead は増やすのはすぐできるが、減らすのは進んだ分だけしかできない(HLA の Modify Lookahead) | [S1] | ◎ |
| 再現性の条件=事象の計算が壁時計に依らないこと・同時刻の事象を毎回同じ順で処理すること・外からの入力に論理時刻を振ること | [S1] | ◎ |
| Chandy & Misra 1979(IEEE TSE SE-5(5):440-452)。全体の制御なしにデッドロックを避ける | [S3] | ○ |
| Time Warp(Jefferson 1985・TOPLAS 7(3):404-425)。遅れた事象で巻き戻し、反メッセージで送った分を打ち消す。GVT は下限の透かしで、取り消せない出力は GVT を越えてから出す | [S4] Colyer の解説 | ○ |

- 写し方(見立て)。エンジン=同期型の LP(刻み=ラウンド)・艦隊=もう 1 つの LP・δ_think=艦隊の側の lookahead。エンジンは未着の呼びの集合と適用の刻みをすべて知っているので、null message は要らない。刻み T を進めてよいのは「未着の呼びの最小の t_apply > T」のとき。これは LBTS(時刻の下限)そのもの。
- 輪は 1 つ(エンジン↔艦隊)で、δ_think ≥ 1 刻みなので lookahead 0 の輪は無い。止まるのは艦隊が固まったときだけ。だから要るのはデッドロック回避ではなく「固まりの上限」(§6-1 メモ §1-2 の (c))。
- TM2 で δ_think が本人の出力(トークン数など)で決まるようになると、適用の刻みは返事が来るまで分からない。その場合は lookahead=δ_think の下限(例: L1 の床 1 刻み)にして、「出した刻み+下限」までに届くのを待ち、届いた後で本当の適用の刻みへ置く。HLA の「下限の約束」と同じ形になる(推測)。
- Time Warp の形(待たずに進み、遅れた返事が来たら世界を巻き戻す)は、決定論は保てる。ただし 35 万体の状態を刻みごとに控える費用が大きい。体どうしの相互作用で巻き戻しが広がる(見立て・採らない候補)。

## §3 先例 B ストリーム処理の透かし(watermark)

| 事実 | 出典 | 等級 |
|---|---|---|
| 透かし=処理済みの事象時刻の下限(多くは推定)。多くの分散データでは 100% 正しい透かしは作れない | [S5] Akidau 2015 §2 | ◎ |
| 透かしの 2 つの欠点。速すぎる(透かしの後ろに遅れたデータが来る)と、遅すぎる(遅い 1 件で全体が止まる) | [S5] §2.3 | ◎ |
| triggers は「処理時刻のいつ出すか」を決める。出し方は 3 つ。Discarding(前の結果と無関係)・Accumulating(前の結果を磨く)・Accumulating & Retracting(前の値を取り消してから新しい値) | [S5] §2.3 | ◎ |
| Flink の allowed lateness の既定は 0=透かしの後ろに来た要素は捨てる。許容の内なら窓に足し、late firing で更新した結果を出す。`sideOutputLateData` で捨てた分を別の流れに取り出せる | [S6] Flink windows | ◎ |

- 写し方(見立て)。この答申の場面では透かしは**完全**にできる(未着の集合を知っている)。だから「速すぎる」は起きず、「遅すぎる」だけが残る。背圧は「透かしが T を越えるまで刻み T を確定しない」と言い換えられる。
- 遅れた返事の扱いの選択肢を透かしの言葉で並べると、次の 4 つになる。捨てる(Flink の既定)=憲法 1 の「破棄禁止」に反する。届いた刻みに適用(今の形)=許容遅延が無限で late firing。行動に使わず記録だけ(脇の出力)。取り消して出し直す(Time Warp・retracting)。
- 「δ_think を延ばして記録する」案は、許容遅延つきの late firing に当たる。思考時間が GPU の速さで決まるので、2-7 の前提(混ぜない)とぶつかる。速さのための腕として宣言して使う以外は採らない(見立て)。

## §4 先例 C 背圧(backpressure)

| 事実 | 出典 | 等級 |
|---|---|---|
| Reactive Streams は「受け手に任意の量を溜めさせない」ための非ブロッキングの背圧。受け手は `request(n)` で需要を出し、送り手は需要を超えて `onNext` しない(規則 1.1・2.1・3.8 は加算) | [S7] | ◎ |
| Flink 1.5 の credit-based flow control。受け手が空きの緩衝を credit(1 緩衝=1 credit)として送り手に知らせ、backlog も返す。背圧は論理の路 1 本にだけかかり、多重化した TCP を止めない | [S8] | ◎ |
| TCP の窓は、受け手が今受け入れる用意のある番号の幅(RFC 9293 §3.8.6)。窓 0 の探りは必須(§3.8.6.1・MUST-36) | [S9] | ◎ |
| vLLM の `max_num_seqs`=1 回の繰り返しで処理する列の上限(既定 128 は試験用の便宜)。KV が足りないと先取りして後で再計算する(V1 の既定は RECOMPUTE)。chunked prefill では decode を先に回す | [S10][S11] | ◎ |
| vLLM の `policy`=fcfs(到着順)か priority(値の小さい方が先・同じなら到着順) | [S11] | ◎ |
| Orca の反復単位のスケジューリング(continuous batching の元)。早く終わった要求が残りを待たず、新しい要求が途中から入れる | [S12] | ○ |
| vLLM の batch invariance=`VLLM_BATCH_INVARIANT=1` で出力がバッチの大きさと順に依らない。compute capability 8.0 以上。性能に響き得る。RTX 50 系(CC 12.0)の名は無い | [S13] | ◎ |
| 当方の B14: A5000(CC 8.6)で ON なら 32/32 一致・OFF なら 3/32。速さの差は無し | `docs/bench/b14_batch_invariance/README.md` | ◎ |

- 写し方(見立て)。背圧は 2 つの層に分けて考える。世界の層は「誰がいつ考え始めるか」を決める。ここは決定論的な規則(アービタの L4 の上限・体ごと 1 本)だけで決め、GPU の状態を読まない。輸送の層は「出した呼びを GPU に流す速さ」で、credit や `max_num_seqs` で絞る。絞った分は送りの待ち行列で待たせ、世界へ Deferred として返さない。
- 今のキュー満杯(`fleet.py:971-1000`)は、輸送の層の満杯を世界の層の繰り延べに変えている。これが漏れの 2 本目。待ち行列の上限を「1 刻みの上限×先読みの刻み数」以上の決まった値にすれば、メモリも有界のままになる(推測)。
- vLLM の priority に t_apply(早く要る順)を渡すと、世界の待ちを短くできる。EDF を輸送の層だけで使う形で、世界の結果は変わらない。ただしバッチの組み方が変わるので、batch invariance が ON の前提(推測・5070 では未確認)。

## §5 先例 D エージェント社会シミュレーション・anytime・注意

| 系 | LLM の遅れの扱い | 等級 |
|---|---|---|
| Generative Agents(Park ら 2023) | 刻みごとにサーバーが JSON を読み、全員を動かしてから次へ(逐次・同期)。実時間 1 秒=ゲーム 1 分。並列化は今後の課題 | [S14] ◎ |
| AgentSociety(Piao ら 2025) | 体は独立に非同期で動き、asyncio で待ちを隠す。環境の刻み(ms)と LLM のラウンド(全員が終わるまで)を別に測る。1 万体で 1 ラウンド 459〜5,681 秒。遅い組に律速される | [S15] ◎ |
| OASIS(Yang ら 2024) | 1 刻み=3 分。時間の確率で一部だけ起こす。非同期で要求を出し、UUID で返事を引く。刻みを閉じる規則は書かれていない | [S16] ◎ |
| GATSim(Liu ら 2025) | 刻み Δt のループで、計画の見直し → 状態の更新 → 移動 → 振り返り → 保存の順。見直しの機会は 3 つに絞る(多すぎると高く、人らしくもない) | [S17] ◎ |
| Project Sid(Altera 2024) | 10 個の部品を並行に回す。遅い考え(振り返り・計画)が反射を止めない。決定は認知の制御器 1 か所に絞る | [S18] ◎ |
| Concordia(DeepMind) | 逐次・同時・非同期の 3 つの engine。非同期は体ごとのスレッドが各自の速さで GM とやり取りする(Apache-2.0) | [S19] ◎ |
| anytime algorithm(Zilberstein 1996) | 考える時間と結果の質を交換する。割り込める型と契約の型 | [S21] ○ |
| 注意の負荷(Lavie ら 2004) | 知覚の負荷が高いと妨害が減る。作業記憶の負荷・二重課題では妨害が増える | [S20] ◎(要旨) |
| 目標の記憶(Altmann & Trafton 2002) | 割り込まれた目標は活性で戻る(目標の棚ではなく記憶の一般の仕組み) | [S22] ○ |

- 「世界が考えを待つ」のは Generative Agents と GATSim(同期)。「世界が進む」のは Project Sid と Concordia の非同期(壁時計=世界時間)。AgentSociety と OASIS はその中間。どれも「世界の中の思考時間」と「GPU の待ち」を分けて扱っていない(◎ 読んだ範囲で)。当方の 2-7 の形(世界の時計は待つ・体は考えている間も動く・待つのは本人の新しい判断だけ)にそろう先例は見当たらない。
- LLM の呼びは「契約の型」に近い(B_world の上限で着地する・認知設計 §2 の ②)。割り込みで「まとまらない判断」を出す形は、契約の型を打ち切って控えの答え(判断モデルの分布)を使う形になる(見立て)。

## §7 設計案(2-7 と 11-01 §10-1 に沿う・見立て)

### ① 飛行中の上限
- 体ごと 1 本。返事を待っている体には新しい呼びを出さない(`decide.py:176-178` の再送を検査に変える)。新しい起床は ③ の規則で「割り込む」か「溜める」かに分ける。TM2 の「待つのは新しい判断だけ、その人だけ」と同じ。
- 艦隊ごと N 本は 2 段に分ける。世界の層=アービタの 1 刻みの上限(今の L4・決定論)。輸送の層=`max_num_seqs` とクライアントの実行中の上限(今の 64/GPU)。後者で入らない分は送りの待ち行列で待たせ、世界へ返さない。
- 待ち行列の上限は決まった値にする(例: 1 刻みの上限×5 刻み)。超えたらランを止めて記録する(黙って繰り延べない)。

### ② 先読み δ_think(背圧の本体)
- 適用の刻み=出した刻み+δ_think(レーン)。刻み T の llm_receive で「t_apply ≤ T の未着」がそろうまで待つ。L2・L3 の呼びは待たない(`wait_idle` の待ちすぎを直す)。
- 返事に依らない処理(body・world・presence・知覚の前計算)は待ちの前に回す(今の順で既にそうなっている)。
- 固まりの上限は「止まったと見なす秒」(例 30 分)。超えたら状態を書いてランを止める(§6-1 メモ §1-2 の (c))。300 秒は「遅い」の印として数えるだけにする。
- TM2 以降(δ が出力で決まる)は、下限の lookahead で待ち、届いた後に本当の刻みへ置く(§2)。

### ③ 集中の度合いで割り込む(不応期の置き換え)
- 熟考に入るとき、判断モデルが集中の値 f を出す(2-7 の 3)。新しい刺激は System 1 の顕著性 s を持つ。s > f なら割り込み、s ≤ f なら溜めて、返事の適用の直後に 1 回だけ起こす(2-7 の 2 と同じ「まとめて 1 回」)。
- 尺度は驚きの 0〜5 の言葉(DM)にそろえ、同じ尺度で比べる(推測)。会話の相手の発話は常に割り込む(2-7 の 4)。
- 判断モデルが来るまでは、f はレーンの固定の表(expedient)か、性格の欄からの抽選で置く。どちらも腕で振る。
- 注意点。Lavie らの結果では、作業記憶の負荷は妨害を増やす [S20]。「熟考中は割り込まれにくい」を固定の規則にすると、人と逆向きになる恐れがある。f を判断モデルに出させ、向きを錨で確かめる(§8)。
- 考えていない体の不応期は、11-01 §10-1 のとおり「予算の装置」と宣言して残す。

### ④ 考えは待たせても捨てない
- 割り込まれた考えの返事は、届いたら行動には使わず、テープと本人の記憶に「考えかけたこと」として残す(脇の出力)。認知設計 §2 の「信念だけ後から更新」と同じ向き。
- 今の `one_per_agent` は、同じ刻みに LLM の返事が 2 つ来ると行動コードの小さい方を残し、もう 1 つを黙って落とす。① で体ごと 1 本にすると、艦隊の道ではこの衝突は起きない。古いテープの再生と mock の δ ≥ 2 のために畳みは残し、落ちた件を源の組ごとに数える(新しい形では 0 が不変条件)。
- 時間切れと満杯の繰り延べ(今は答えを捨てて起こし直す)は、② の待ちで起きなくなる。残すのは止まったときの記録だけ。

### ⑤ 決定論と再開
- 背圧の後、適用の刻みは GPU の速さに依らない。LLM の出力が決定論的なら(seed=hash(call_id, run_seed)・batch invariance ON)、同じ入力でバイト一致を主張できる。5070 で batch invariance が効くかは未確認(B14 は A5000 で合格)。
- キュー満杯の判定を GPU の状態から外す(①)。これで繰り延べになる体が毎回同じになる。
- 再開は、刻みの境で未着の呼び(`fleet_inflight`)を状態に書き、再開で出し直す(`build.py:1638-1649` の口が既にある)。出し直した返事が元と同じかは batch invariance しだい。
- テープは列を足さない(適用の刻みは導ける・§6-1 メモ §1-4)。meta に `backpressure: true` を足す案。

### ⑥ 計測の分離(10-25 §6-7)に足す欄
- 刻みごとの待ちの秒(最大・p50・p99)と待った刻みの数・艦隊が遊んだ割合(パイプラインの効き)。
- 透かしの遅れ=T − 未着の最小の t_apply(刻み)。遅れて届いた件数と遅れの分布(新しい形では 0)。
- 体ごとの上限で止めた起床の数・割り込みの数(条件ごと)・溜めた刺激の数と溜めた刻みの分布・割り込まれた考えの件数(適用/記録だけ)。
- `one_per_agent` で落ちた件(源の組ごと)・止まったと見なした件・送りの待ち行列の最大の長さ。
- 世界の中の思考時間の分布(出した刻みから適用まで)。背圧の後は δ の表と一致するはず。
