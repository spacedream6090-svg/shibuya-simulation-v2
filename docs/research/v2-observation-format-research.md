## ① 結論(推奨形式・10行)

1. **「唯一最良の入力形式」は先行研究に存在しない**——形式間の優劣はモデル・タスクで反転する(表理解ではHTML最良、推論ではplain textが競争的)。よって形式は**品質でなく運用要件**(バイト一致・トークン効率・過剰追従抑止)で決めてよい。
2. 推奨 = **決定論的テンプレでレンダリングした「素性タグ付き・短い平叙文の固定ブロック」**。生JSONは渡さない(記号トークンの膨張+バイト一致が壊れやすい+利得の証拠なし)。
3. ただし **JSON的な「キー:値」の平坦性は保つ**(1行1事実・固定順序)。人間向け散文にしない。
4. **出力側**をJSONスキーマで強く縛ると推論が落ちる(gpt-3.5 GSM8K 75.99→49.25、claude-3-haiku 86.51→23.44)。v2原則4「量はスカラー、質は自由文」を実証が支持。出力は最小スキーマ+短い自由文。
5. ブロック順序 `[静的system]→[種別]→[場所セル共有]→[個体]→[問い]` は**prefix経済(前方一致)と位置効果(recency)の両方に整合**し、変更不要。
6. 追加規約: **[個体]の直後に[問い]** を置き、問い文で個体の要点を1行再掲する(lost-in-the-middle対策)。`[推測]`
7. トークン予算: 自リポのベンチ実測形 `shared 1000 + suffix 500 / out 64-128` をそのまま正典化。**観測ブロック合計 ≈950tok(共有650+個体300)= 入力1,500の63%**。
8. **差分観測はLLM入力に持ち込まない**。差分は配送層(dormant・再送抑止)だけ。理由: 各判断は履歴なしの単発呼びであり、かつ差分化は個体ごとに履歴が分岐して**セル共有のバイト一致を原理的に壊す**。
9. 過剰追従の抑止は **素性タグ(spotlighting)**が一次実証あり(攻撃成功率 >50% → <2%)。看板・発話・UGCは必ずタグ+引用符+字数キャップ+間接話法。
10. 予算の支配変数は「同時に生きている場所セル数」。自リポ実測で cells=1→8→32→128→512 と増やすと 598.97→539.11→516.16→479.74→472.64 tok/s と単調劣化(c32/o64)。**Zipf型の人気偏りは+8.8%回復**(128セル: 479.74→521.75)。

## ② ユーザーがまず読む大枠(8行)

- **知覚を「JSONで渡すか自然文で渡すか」は、実は品質の問題ではありませんでした。** 先行の実証は割れていて、どちらが勝つかはモデルとタスクで入れ替わります。だから v2 は「品質で選ぶ」のをやめて、**バイト一致(キャッシュ)・トークン数・過剰反応の抑止**という3つの運用条件で形式を決めるのが正解、という結論です。
- 決めた形は「**機械が決定論的に生成する、素性タグ付きの短い平叙文を、固定順・固定行数で並べたブロック**」。JSONの良さ(1行1事実・順序が固定)は残し、JSONの悪さ(記号でトークンが膨らむ・書式ゆれでキャッシュが壊れる)は捨てます。
- **既決のブロック順序は正しい**と先行から裏が取れました。変更は不要で、追加するのは「問いを最後に置き、個体の要点を1行だけ問いの中に再掲する」だけです。
- トークンの割り振りは、**すでに自分たちのベンチで測った形(共有1000+個体500)がそのまま最適配分の骨格**でした。観測に使えるのは合計950トークンです。
- 一番の発見は「**差分だけ送る**という省エネ案は使えない」ことです。差分にすると個体ごとに文面が枝分かれして、せっかくのキャッシュ共有(1.6-2.0倍の高速化)が壊れます。差分は「送るか送らないか」の判断にだけ使い、送るときは常に完全な現在形を送ります。
- 広告・看板の過剰反応対策は、「**世界が書いた文**」と「**誰かが書いた文**」を字面で区別するタグが有効だという一次実証がありました(攻撃成功率が50%超→2%未満)。
- 一方で **「観測に何トークン割くべきか」を書いた先行研究はゼロ**でした(§5)。ここは v2 が最初に数字を置く領域になります。

## ③ 問い1-6の証拠

### 問い1: 観測の表現形式の実証比較

#### 1-a. 出力形式の制約は推論を壊す(実読・PDF本文抽出済)

Tam et al., *Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models*, arXiv:2408.02442(Appier AI Research + NTU)。**PDF本文をpymupdfで抽出して表を直読**。

3設定の定義(本文§2 逐語):
- **Constrained Decoding (JSON-mode)**: 生成時にトークン空間を強制。OpenAI/Gemini の JSON mode。
- **Format-Restricting Instructions (FRI)**: 「JSON/XML/YAMLで、このスキーマで答えよ」と指示するだけ(トークン空間は強制しない)。
- **NL-to-Format**: まず自然言語で答え、次に目的形式へ変換する2段。

**Table 1(GSM8K、9種のプロンプト摂動の平均・括弧内は標準偏差)** — 実表の値:

| Model | Text | JSON | XML | YAML |
|---|---|---|---|---|
| gemini-1.5-flash | 89.33 (0.8) | 89.66 (0.3) | 89.26 (0.3) | 89.21 (0.4) |
| + schema constraint | — | 89.21 (1.5) | 88.20 (2.2) | 87.42 (3.7) |
| claude-3-haiku | 86.51 (0.8) | 86.99 (0.2) | 86.96 (0.6) | 82.89 (5.7) |
| + schema constraint | — | **23.44 (22.9)** | 79.76 (7.0) | 80.63 (2.8) |
| gpt-3.5-turbo | 75.99 (3.1) | 74.70 (1.1) | 60.45 (7.2) | 71.58 (3.0) |
| + schema constraint | — | **49.25 (12.0)** | 45.06 (19.9) | 73.85 (5.6) |
| LLaMA-3-8B | 75.13 (0.9) | 64.67 (2.23) | 65.07 (0.56) | 69.41 (0.95) |
| + schema constraint | — | 48.90 (6.7) | 56.74 (8.3) | 46.08 (16.8) |

読み: 「JSONで答えよ」だけなら害は小さい。**明示スキーマを課した瞬間に崩れる**(claude-3-haiku 86.99→23.44、gpt-3.5 74.70→49.25)。標準偏差も跳ね上がる(0.2→22.9)=**プロンプト摂動への感度そのものが上がる**。

**Table 2(gpt-4o-mini-2024-07-18)**:

| Task | NL | FRI | JSON-Mode | JSON-Schema |
|---|---|---|---|---|
| GSM8K | 94.57 (3.95) | 87.17 (4.43) | 86.95 (1.36) | 91.71 (0.68) |
| Shuffle Obj | 82.85 (5.67) | 81.46 (3.71) | 76.43 (9.74) | 81.77 (6.86) |
| Last Letter | 83.11 (3.54) | 84.73 (2.99) | 76.00 (6.69) | 86.07 (3.33) |

新しめのモデル(gpt-4o-mini + CFG強制の Structured Output API)では差が縮む。本文の総括(逐語): *"format restrictions' impact on LLM performance is task-dependent: stringent formats may hinder reasoning-intensive tasks but enhance accuracy in classification tasks requiring structured outputs."*

パースエラー説の否定(本文§5.3 逐語): *"In the LLaMA 3 8B setting, the parsing error rate for the Last Letter task in JSON format is only 0.148%, yet there exists a substantial 38.15% performance gap"* → **劣化はパース失敗ではなく生成過程そのもの**。

> **v2への直結**: これは**出力**の話であって入力の話ではない。しかし原則4「量はスカラー、質は自由文」を強く支持する。**T1出力に厳密JSONスキーマを課すと、40万体の判断品質が構造的に劣化する**。出力は「短い自由文 + 少数の列挙型スカラー」に留めるべき。

#### 1-b. 入力形式は「モデル×タスクで反転する」

- **Salinas & Morstatter?** ではなく: *Does Prompt Formatting Have Any Impact on LLM Performance?*, arXiv:2411.10541(abstract実読)。plain text / Markdown / JSON / YAML の4テンプレを比較。**GPT-3.5-turbo はコード翻訳タスクで最大40%の性能差**、GPT-4 はこの変動に対してより頑健。→ 形式感度は**モデル規模で減衰する**。
- *Table Meets LLM: Can Large Language Models Understand Structured Table Data?*, arXiv:2305.13062(HTML実読)。CSV/JSON/XML/Markdown/HTML/NL+Sep を7つの構造理解タスクで比較。**HTML + 形式説明 + role prompt で総合65.43%**が最高、**HTMLはNL+Sepを6.76ポイント上回る**。Table 2抜粋(GPT-3.5):

| Format | Table Partition | Cell Lookup | Reverse Lookup | Column Retr. | Row Retr. | Size Detect | Merged Cell |
|---|---|---|---|---|---|---|---|
| NL+Sep | 93.00 | 39.67 | 52.00 | 60.67 | 31.00 | 42.00 | 71.33 |
| HTML | 96.67 | 44.00 | 47.33 | 63.33 | 42.00 | 67.00 | 76.67 |

  → 「マークアップの方が良い」が言えるのは**表の構造そのものを問う課題**に限る。逆引き(Reverse Lookup)ではNL+Sepが勝つ。
- 上記2件と 1-a を合わせると: **入力形式の選択で一貫して勝つ形式は同定されていない**。これは「形式は運用要件で決めてよい」という積極的な許可になる。

#### 1-c. シーングラフ(3D scene graph)

**SayPlan** (Rana et al., CoRL 2023, arXiv:2307.06135)。公式プロジェクトページ逐語: *"We leverage a JSON representation of this graph as input to a pre-trained LLM"*。環境規模: *"two large-scale environments spanning up to 3 floors, 36 rooms and 140 objects"* / *"an office floor spanning 36 rooms and containing 150 different assets and objects"*。
機構: 階層3DSGを**折り畳んだ(collapsed)状態**——部屋ノードだけ露出——から始め、LLMが `expand` / `contract` のAPI呼び出しでタスク関連部分グラフだけ展開する。展開しては畳むので**探索中の入力トークンがほぼ一定に保たれる**。
トークン削減 **オフィス82.1% / 家庭60.4%** `[未確認: 原文PDFは10MB超でfetch不可。独立2経路の検索要約が一致した値]`。

> **v2への直結**: SayPlanの「折り畳み→必要部分だけ展開」は**LLMに探索させる**設計。v2は逆に**エンジンが可視性を決定論的に計算して切り出す**(R3-1)ので、SayPlanのAPI往復は不要——**同じトークン節約を、LLM呼び出しゼロで得ている**。これは v2 設計の優位点として台帳に書ける。ConceptGraphs等の「実行時に3Dから構築」系は R3-1 の VLA不採用と同じ理由で不要。

**Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, TACL 2024, arXiv:2307.03172**(HTML経由・要約取得)。20文書マルチ文書QA:

| Model | pos 1 | pos 5 | pos 10 | pos 15 | pos 20 | closed-book | oracle |

| Claude-1.3 | 59.9 | 55.9 | 56.8 | 57.2 | 60.1 | 48.3 | 76.1 |
| MPT-30B-Instruct | 53.7 | 51.8 | 52.2 | 52.7 | 56.3 | 31.5 | 81.9 |
| LongChat-13B | 68.6 | 57.4 | 55.3 | 52.5 | 55.0 | 35.0 | 83.4 |

`[部分未確認: closed-book 56.1 / oracle 88.3 は本論文の周知値と一致するので信頼できるが、位置別の各セルは原表と1対1照合していない]`
重要: **GPT-3.5 の中央(pos10)53.8% は closed-book 56.1% を下回る**——中央に置かれた情報は「無いより悪い」。U字。

**Levy, Jacoby & Goldberg, *Same Task, More Tokens: the Impact of Input Length on the Reasoning Performance of LLMs*, ACL 2024, arXiv:2402.14848**(HTML実読・逐語引用取得)。
- 入力長: *"roughly 250, 500, 1000, 2000, and 3000 tokens"*
- モデル: *"GPT4, GPT3.5, Gemini-Pro, Mistral Medium and Mixtral 8x7B"*
- 劣化: **精度 0.92 → 0.68**(3000トークンまで伸ばしたとき)
- 位置: *"when the key paragraphs appear last, accuracy is often highest (suggesting recency bias)"*、中央配置は多くのモデルで低下
- 追加の失敗様式: 長くなるほどモデルは *"ignore instructions and generate answers which do not contain"* 指定形式 → **長い入力は形式追従も壊す**

> **v2への直結**:
> - T1入力1,500トークンは FLenQA の 1000-2000 帯に相当。**0.92→0.68 の劣化曲線の途中にすでに乗っている**。1,500 は上限であって目標ではなく、**削れるなら削る**のが素直。
> - 既決の順序 `…→[場所セル共有]→[個体]→[問い]` は、**最も個体判断に効く情報(個体固有+問い)を末尾**に置いており、recency bias と一致。**変更不要**。
> - リスク: [場所セル共有]が650トークン級になると、[種別]ブロックが「中央」に落ちる。種別ブロックは行動の型を決める重い情報なので、**種別は短く(≤150tok)し、その要点を[問い]に1行だけ再掲**するのが安全。`[推測: 直接の実証は未発見]`

### 問い3: prefix cache整合の配置規約の先行

#### 3-a. 3つの主要実装は全て「厳密な前方トークン一致」

| 実装 | 一致の粒度 | 実測・仕様 |
|---|---|---|
| **SGLang / RadixAttention** (arXiv:2312.07104) | **トークン列の厳密な前方一致**。radix木でKVを管理、LRU葉から追い出し、**longest-shared-prefix-first** のキャッシュ意識スケジューリング、参照カウントで実行中バッチを保護 | **最大6.4×**スループット向上(vs vLLM 0.2.5 / Guidance 0.1.8 / LMQL 0.7.3)。本番(Chatbot Arena)キャッシュヒット率 **LLaVA-Next-34B 52.4% / Vicuna-33B 74.1%**、ベンチでは **50-99%**、最適ヒット率の **96%** を達成。first-token latency **1.7×**改善(Vicuna-33B) |
| **vLLM Automatic Prefix Caching**(公式設計doc) | **完全ブロック単位の厳密一致**。*"We only cache full blocks."* 部分一致は不可(4トークンブロックで2トークンしか合わなければ再利用不能)。ブロックハッシュ = `hash((親ブロックのハッシュ, このブロックのトークン列, extra_hash))`。既定 SHA256+pickle | キャッシュを壊すもの: マルチモーダル入力の差異、LoRA ID の差異、`cache_salt` の差異、Python/vLLM のバージョン差(CBOR不使用時) |
| **Anthropic Prompt Caching**(公式ガイダンス) | **バイト前方一致**。レンダリング順は `tools` → `system` → `messages`。「前方のどこか1バイトでも変われば、それ以降の全ブレークポイントが無効」 | ブレークポイント最大4。**最小キャッシュ長はモデル依存 512-4096トークン**(下回ると無言で非キャッシュ、`cache_creation_input_tokens: 0`)。キャッシュ読み ≈0.1×、書き 1.25×(5分TTL)/2×(1時間TTL) |

#### 3-b. 公式が明記する「静的を先頭・可変を末尾」の規約

Anthropic の設計ガイダンス(公式ドキュメント由来)の要点:
- 安定度で入力を分類する: **一度も変わらない→最前 / セッション毎→グローバル接頭辞の後 / ターン毎→最後 / リクエスト毎(タイムスタンプ・UUID)→排除するか最末尾へ**。
- **「共有接頭辞・可変接尾辞」パターン**: ブレークポイントは**共有部分の末尾**に置く。全体の末尾に置くと毎回別エントリを書くだけで一度も読まれない。
- **システムプロンプトを凍結せよ**: 「現在日時」「モード」「ユーザー名」をシステムに埋め込むと、その後ろ全部が無効化される。
- **ツール/モデルを会話中に変えるな**: ツールは位置0にレンダリングされるので、追加・削除・並べ替えが全キャッシュを壊す。**ツールは名前でソートして決定論的に直列化せよ**。
- **フォーク(要約・圧縮・サブエージェント)は親の接頭辞をバイト単位でそのまま再利用せよ**。作り直すと親のキャッシュを丸ごと外す。
- **無言の無効化要因**(grepすべきパターン): `datetime.now()` / `uuid4()` / `sort_keys=True` なしの `json.dumps` / `set` の反復 / システムに f-string でセッションIDを埋める / 条件分岐でシステム節を出し分ける / ユーザーごとに変わる `tools=build_tools(user)`。
- **検証法**: `usage.cache_read_input_tokens` が繰り返しリクエストで0のままなら、どこかに無言の無効化要因がある。

#### 3-c. マルチエージェント向けの共有プレフィクス設計

**KVFlow: Efficient Prefix Caching for Accelerating LLM-Based Multi-Agent Workflows**, arXiv:2507.07400(abstract実読)。エージェント実行スケジュールを **Agent Step Graph** として抽象化し、各エージェントに **steps-to-execution**(次に起動されるまでの時間的近さ)を割り当て、**KVノード単位の細粒度追い出し**に使う。LRUは「次に誰が来るか」を予測しないので取りこぼす、という問題設定。**単一ワークフローで最大1.83×、多数同時ワークフローで最大2.19×**(SGLangの階層radixキャッシュ比)。

> **v2への直結**: v2 の場所セルは「次にどのセルが呼ばれるか」がスケジューラ側で既知(時計と人流)。**KVFlow の steps-to-execution を「次のtickでそのセルに誰かいるか」で実装できる**。追い出し方針を LRU から「次tickで生存するセルを保護」に替えるのが、R3-8以降のU6(認知LOD)と自然に噛み合う。ベンチ計画への追加候補。

#### 3-d. バイト一致を保つ正規化の実務(公式docと実装から導出、規約は §④に記載)

一次資料が明言しているのは以下だけ:
- vLLM: ハッシュは **(親ハッシュ, ブロック内トークン列)** のタプル。**トークン列が同一でなければ一致しない**=文字列レベルの正規化が必須。
- Anthropic: **`sort_keys=True` なしの `json.dumps`、`set` の反復、条件分岐セクション**が無言の破壊要因。**ツールは名前でソート**。
- SGLang: 一致は**厳密なトークン前方一致**、あいまい一致・意味的一致は存在しない。

**「数値丸め・列挙順・空白の正規化規約」を明文化した論文・公式docは発見できなかった**(§5)。§④の規約は上記から**導出したもの**であり、先行の引き写しではない。

### 問い4: 言語化テンプレの設計(過剰追従の抑止)

#### 4-a. 素性タグ(spotlighting)— 一次確認あり

Hines, Lopez, Hall, Zarfati, Zunger, Kiciman, *Defending Against Indirect Prompt Injection Attacks With Spotlighting*, arXiv:2403.14720(abstract実読)。spotlighting は *"a family of prompt engineering techniques"* で、*"transformations of an input to provide a reliable and continuous signal of its provenance"*(**入力の出所を連続的・信頼可能に示す変換**)を使う。効果(逐語): ***"spotlighting reduces the attack success rate from greater than 50% to below 2% in our experiments with minimal impact on task efficacy."***
`[未確認: delimiting / datamarking / encoding という3技法名は abstract に列挙されておらず、本文未読。技法の内訳は引用しないこと。]`

> **v2への直結**: 「観測に含まれる看板文・広告文・他者の発話・UGC本文」は**まさに間接プロンプトインジェクションの構造**である。>50%→<2% は、素性タグを**任意の改善ではなく必須の防壁**として台帳に置く根拠になる。広告答申の「注意ゲート4段」+「既定非注入」と同じ層に、**素性タグを第0段として入れる**べき。

#### 4-b. プロンプト文面の中立化は結果を大きく動かす — 一次確認あり

*Towards Operational Validation of LLM-Agent Social Simulations: A Replicated Study of a Reddit-like Technology Forum*, arXiv:2508.21740(EPJ Data Science 掲載・HTML実読)。
- モデル: Dolphin Mistral 24B Venice Edition、Y Social プラットフォーム上で **30日シミュレーションを30回独立実行**、Voat の v/technology(30日窓あたり約576ユーザー・日次アクティブ平均31人)に較正。
- 中核の所見: **ペルソナ記述を中立化した変種は、平均毒性を46.7%低下させ、0.5超のスコアを持つ項目の割合を51.5%低下させた**。
- 対照: *"no-politics variant produces only modest shifts with overlapping intervals"* = 話題を消すより**記述の枠づけを変える方が効く**。
- 著者の結論(逐語): *"agent behavior remains sensitive to prompt wording, context selection, and model idiosyncrasies, so 'validity' is always conditional on a documented prompting protocol."*

> **v2への直結**: これは R3-8 を「契約書」として書く**理由そのもの**である。文面の枠づけが結果を50%動かすなら、**観測テンプレの文面は較正パラメータと同格の管理対象**であり、版管理・ablation対象・台帳記載対象になる。「知覚契約書」の本質は API 仕様書ではなく**文面凍結宣言**である。

#### 4-c. 長い入力は形式追従自体を壊す

FLenQA(問い1-d)の副次所見: 入力が長くなるほどモデルは *"ignore instructions and generate answers which do not contain"* 指定形式。→ **観測ブロックを膨らませると、出力スキーマ遵守率が下がる**。トークン予算は品質だけでなく**パース成功率**の問題でもある。

### 問い6: 観測の冗長性と忘却(毎回全観測 vs 差分)

#### 6-a. 先行の状況

- **Concordia**: GMは「観測しなかったと判断したイベントについては観測を発行しない」= **イベント駆動の差分配送**。ただしこれは**配送の有無**であって、送るときは完全な観測文。
- **OASIS**: 毎ステップ RecSys が上位k件を推薦し直す = **毎回フル再送**。
- **Generative Agents**: 毎ステップ視野内の全オブジェクト/エージェントを memory に流し、検索して**文脈窓いっぱい詰め直す** = フル再構成。
- **世界モデル系(LLMに次状態を予測させる研究)**では full-state prediction と delta prediction の対比が議論されている `[未確認: arXiv:2606.09032 等は原文未読。かつこれは「LLMが出力する側」の話で、v2の「LLMに入力する側」とは別問題]`。
- **LLM社会シムで「観測を差分だけ渡した」実装例は発見できなかった**(§5)。

#### 6-b. v2に固有の決定的な論拠(設計から導出)

**差分観測は v2 のアーキテクチャと原理的に両立しない。** 理由2つ:

1. **状態の置き場所**: v2 の T1 判断は**会話履歴を持たない単発呼び**である(prefix共有はKVキャッシュの話であって、モデルに前回の文脈が「見えている」わけではない)。差分だけ渡すと、LLM側に累積状態を保持する場所がない。累積はエンジンが持つ——が、エンジンが持っているなら**エンジンが完全な現在形をレンダリングして渡すのが最短**であり、差分にする意味が消える。ドクトリン「状態と集約はエンジン、意思決定と発話だけLLM」がそのまま答えになっている。
2. **バイト一致の破壊**: 差分は「その個体が前回いつ何を見たか」に依存する。同じセルにいる100体は、入場時刻が違えば差分が全部違う。**その瞬間に、セル共有ブロックのバイト一致(=1.63-1.83×の高速化)が失われる。** 差分でトークンを2割削っても、キャッシュを失えば実効スループットは 720→443 tok/s(−38%)。**差分は正味の損である。**

#### 6-c. したがって推奨

- **LLMが見る観測は、常に「有界な完全現在形」**。上位k打ち切り・段階尺度量子化で有界性を担保する(削減は「差分」でなく「有界化」で行う)。
- **差分は配送層に閉じ込める**: R3-3 で決めた dormant(変化まで再送しない)は、**エンジン内部の再計算・再レンダリング回避**として維持し、**プロンプト文面には出さない**(dormant対象は「変わっていないので前回と同じ行がそのまま出る」= バイト一致が保たれる、が正しい姿)。
- **例外は個体ブロック D6 のみ**: attachment/dormant の変化行は、セル共有の**後ろ**(D6)に置く限りバイト一致を壊さない。ここだけは「変化があった行だけ出す」でよい。
- **状態追跡能力の実証**: 「LLMが差分だけで状態追跡できるか」を直接測った研究は見つからなかった。ただし FLenQA(長入力で0.92→0.68)と lost-in-the-middle(中央はclosed-bookより悪い)は、**累積を文脈に積むほど劣化する**方向を一貫して示しており、差分累積方式に不利な間接証拠になる。

## ④ R3-8 への設計含意

### 4-1. 観測スキーマ案(レコード型)

観測は**5ブロック・固定順序**。共有ブロックは**固定行数・固定順序・可変長禁止**、個体ブロックのみ可変長。

```
[A] SYSTEM        version=obs-tmpl/1.0.0   ← 版数を先頭に埋める(改版=全キャッシュ入替を明示)
[B] KIND          種別ID + 種別規約
[C] PLACE         cell=<id> slot=<time-bucket>      ← ここまでがバイト一致の共有接頭辞(≈1000tok)
    C2 場所
    C3 見えるもの(固定10行・不足はパディング行)
    C4 掲示(固定4行・不足はパディング行)
    C5 人(固定3行)
    C6 音(固定2行)
    C7 空(固定2行)
    C8 予備(固定行)
[D] SELF          ← ここから個体固有(可変長・キャッシュ非共有)
    D1..D7
[E] ASK           問い + 個体要点1行再掲 + 出力形式
```

**ブロック順序を変えてはならない理由**(3つ揃って初めて成立):
1. prefix は**前方一致**なので、共有度の高い順に前から並べる(SGLang/vLLM/Anthropic 全実装で同じ)。
2. recency bias により、判断に最も効く情報([D]個体・[E]問い)は末尾が最良(FLenQA・lost-in-the-middle)。
3. 1と2が**同じ並びを指す**——共有度が高い情報ほど個体判断への寄与が小さいから。これは偶然ではなく、v2の観測設計が構造的に幸運な形をしていることの現れ。

### 4-2. 決定論的レンダリング規約(バイト一致の保証)

R3-8 に条文として置くべき8項:

1. **版数の先頭埋め込み**: `[A]` 先頭に `obs-tmpl/<semver>`。テンプレを1文字でも変えたら semver を上げる。上げないと**古いキャッシュと新しい文面が混在**する。
2. **列挙順は (量子化距離, 安定ID) の辞書順**に固定。距離は生値でなく量子化値でソートする(生値でソートすると微小変動で順序が入れ替わりバイトが変わる)。
3. **数値は必ず量子化して段階語に落とす**。連続値をそのまま書かない。やむを得ず数値を書く場合は**固定桁で丸めて固定幅ゼロ埋め**(`07`, `1.5`)。
4. **辞書・集合の直列化は必ずキーソート**(Anthropic公式が名指しする無言の破壊要因)。Python の `set` を反復しない。
5. **文字正規化は NFKC 固定**。全角/半角・異体字・波ダッシュを正規化してからレンダリング(渋谷の店名は表記ゆれが激しい)。
6. **共有ブロックは固定行数**。空でも「パディング行」を出す。行の欠落もバイト差である。`[C]` の長さがtickごとに揺れると、その後ろの `[D]` の位置がずれてキャッシュ境界が動く。
7. **時刻・乱数・個体IDを共有ブロックに入れない**。時刻は「時間帯バケット」に量子化して `[C1]` にのみ書く(バケット境界でセル全体が入れ替わるのは正しい挙動)。
8. **フォーク(T2昇格・要約・検証)は親の `[A][B][C]` をバイト単位で複製**してから独自部分を末尾に足す(Anthropic公式の "fork must reuse the parent's exact prefix")。

### 4-3. 文面規約(過剰追従の抑止)

1. **観測は平叙文・現在形のみ**。命令文・依頼文・二人称呼びかけを `[C][D]` に書かない。命令は `[A]` と `[E]` にしか存在しない。
2. **評価語・重要度語を禁止**。「重要な」「注目すべき」「危険な」「魅力的な」を観測に書かない。段階尺度は**閉じた既定語彙**からのみ選ぶ(例: 人通り = {ほとんどない, まばら, ふつう, 多い, 非常に多い} = Fruin LOS の量子化)。
3. **素性タグを全行に前置**(spotlighting の一次実証: 攻撃成功率 >50%→<2%)。最低限4種:
   - `[世界]` エンジンが計算した事実(密度・騒音・日照・可視物)
   - `[掲示]` 看板・広告・貼り紙のテキスト(店主/広告主が書いた)
   - `[発話]` 他エージェントの発話(傍受・会話)
   - `[自分]` 内受容・記憶・所持
   `[掲示]` と `[発話]` は**世界が保証しない文字列**であり、そう読むことを `[A]` の凡例で明示する。
4. **引用は間接話法+字数キャップ**。看板は `[掲示] 「<10-20字>」と書かれた看板が見える。` の形に固定する。命令文が書かれていても、観測文としては「そう書かれている」という事実の報告になる。**これが広告答申の注意ゲート第0段。**
5. **「なし」を書かない**。空欄は固定パディング行(`—`)。「〜はない」という否定文はLLMの注意を引きすぎる。
6. **数値の過剰精度を出さない**。「65.3dB」でなく「騒がしい(65dB級)」。過剰精度は過剰追従を招き、かつバイト一致を壊す。
7. **文面は較正パラメータと同格に管理**(arXiv:2508.21740 の 46.7% を根拠に)。文面変更は台帳の版・ablation対象・declared-distortion の記載対象。**「知覚契約書」の本質は API 仕様書ではなく文面凍結宣言である。**

### 4-4. 出力側の含意(原則4の実証的裏付け)

- **厳密JSONスキーマ強制はT1に課さない**。Tam et al. の schema constraint で claude-3-haiku 86.51→23.44、gpt-3.5 74.70→49.25。標準偏差も 0.2→22.9 に拡大=プロンプト感度そのものが増す。
- 推奨: **「短い自由文1-2文 + 少数の列挙型スカラー」を FRI(スキーマなしの緩い指示)で**取る。パースは LLM 以外の決定論的パーサ+失敗時の1回リトライ(Tam et al. Figure 5 が「2回目の呼び出しで構文修復できる」ことを示している)。
- FLenQA の副次所見(長入力で形式追従が壊れる)より、**観測を膨らませることは出力パース失敗率の上昇に直結する**。予算超過は品質だけでなく運用の問題。

### 4-5. isovist × セル共有の衝突(R3-5 の2解像度分離の再確認)

R3-5 が既に「場所セル(prefix共有単位)=100m級 ≈139セル / 可視性格子=2.5m」と分離済み。R3-8 での追加規約:

- **`[C3]` 可視スマートオブジェクトは「セル代表点からの可視集合」を使う**(個体位置ではない)。個体位置の isovist を使うと同一セル内の100体で全部違う文面になり、共有が消える。
- **個体位置の isovist は `[D]` 側でのみ使う**——具体的には D2(注意到達した行為)・D4(被注視性)の絞り込みに使い、可視物リストの生成には使わない。
- **セル代表点可視集合と個体可視集合の差**は「declared distortion」として台帳に記帳する(そのセルにいるのに実際は柱の陰で見えない物が観測に出る)。カバー率を測る。
