## 結論(5 行)

1. **セル由来の入力は概算 tok で 15〜16%**(c7-day-4 で 147.3 / 923.5 = 16.0%、今の HEAD の mock で 14.9%(記憶 ON は 14.5%))。指示書の「約 16%」は c7 の概算 tok の比で、実トークンに直すと 13〜16%。時刻と天気の B3 はセル部分の後ろに並んでいるので、セルの単位でしか共有されない部分は **B3 を足して約 19%** になる。
2. **出どころの写し違いが 2 つある**。「100 トークンごとに約 8%」は BN-5 ではなく **BN-2(ベンチ第 4 段・09-03)の個体長の掃引**(300→800 で −40.6%)。「2.39 倍」は c7-day-4 の実測ではなく、**ベンチ第 2 段の合成データ**(共有 1,000+個体 500・共有元 1 本・c128)の値。c7-day-4 の prefix の命中は記録に無い。
3. **c7-day-4 の呼の列で数えると、セル部分の prefix の再利用は 48〜73% だった**(GPU 7 枚への振り分けを再現し、GPU ごとの直前 64〜∞ 呼の窓で数えた)。指示書の 12% は「セル部分が 100% 共有」と「概算 tok のまま」を前提にしており、2 つの前提の誤差は逆の向きに出る。
4. **処理量の見込み(推測)**: (a) 同じ長さで個人化すると **−9〜−29%(中央 −17%)**。B3 を個人の部分より前へ移すと −6〜−25%(中央 −13%)、さらに場所の定型文を共有すると −4〜−22%(中央 −11%)になる。(b) 視野 214° で列挙の行を絞ると、同じ 3 つの設計で中央 −13% / −8% / −5% になる。記憶 ON でもほぼ同じで、0〜2 ポイント小さい。幅の大部分は KV キャッシュがどこまで prefix を保持するか(窓 K)で決まり、GPU で測るまで絞れない。
5. **CPU の費用は LLM の時間より 2 桁ほど小さい(推測)**。セルの描画を呼ごとに組み直す分は 1 描画あたり +21〜49 µs で、39 万体 1 日で約 1〜2 分(推測)。変化検出を本人の位置の場で行う近似は、40 万体で素の numpy 6〜11 ms/tick で、今の P6(同じ手元機で 0.9〜1.7 ms)の 4〜12 倍だった。numba にした場合の値は測っていない。

## §1 指示書の 3 つの数の出どころ

### 1-1 「入力の約 16%」

- c7-day-3 のログ `平均tok 共有静的 642.8/750 セル 147.5/250 個体 133.3/300 (合計 923.7)` で 147.5 / 923.7 = **16.0%**、c7-day-4 で 147.3 / 923.5 = **16.0%**(#5・#7)。数え方は renderer の概算(ブロックごとに文字数 ÷ 2)。**実トークンの比ではない**。
- 今の HEAD では B0(システム)が 603 → 706 概算 tok に伸びたので、同じセル部分でも比は 14.9% に下がる(§2)。

### 1-2 「人ごとの部分が 100 トークン増えるごとに約 8% 落ちる」= BN-2(BN-5 ではない)

- 出どころは台帳の **BN2-s1000i300 / i500 / i800**(#1)。共有 1,000 tok(全体+種別+セル 200・139 セル Zipf 1.0)に個体 300 / 500 / 800 tok を足した合成プロンプトで、単 GPU・c64・o128 の呼/秒が **8.642 / 6.775 / 5.127**。300→800 で 1 − 5.127 / 8.642 = **40.7%** 減、5 で割って **8.1%/100tok**(本書で再計算。台帳 README は 40.6%)。
- これは「300 tok を基準にした平均の割合」。区間で見ると 300→500 は −10.8%/100tok、500→800 は −8.1%/100tok(500 を基準)になる。1 呼の時間(1 / 呼/秒)は個体長の一次式でよく表せて、**1 / 呼/秒 = 0.0682 秒 + 1.586×10⁻⁴ 秒 × 個体 tok**(3 点で直線)。
- BN-5(第 5 段)はブロックの順序と契約サイズの比較で、この値は出ていない。知覚契約 l.37 は同じ値を「BN-2C 実測」の段落に書き、指示書 10-03 §5-3 と知覚契約の冒頭の注記(l.4)は「BN-5」と書いている。**写しの訂正が 2 か所に要る**(本書は直していない)。

### 1-3 「c7-day-4 の prefix 共有の効き 2.39 倍」= ベンチ第 2 段の合成データ

- 出どころは台帳の m2-8b-int8-pcON-c128-o128-pfx の **1,031.86 tok/秒** と、同条件で prefix キャッシュを切った **432.42 tok/秒** の比 **2.386**(#3・#4)。合成プロンプト(共有 1,000+個体 500)で、共有元は 1 本しかない(README も「num_prefixes=1 の上界」と書いている)。
- c7-day-4 では prefix キャッシュの ON/OFF を比べておらず、命中率も記録に無い(ログ・構築報告を grep した)。R-73 §0 #39 も同じ 2.39 倍を「本 repo の実測」として引いている(循環参照の検査の対象)。
- 本書では 2.39 倍の代わりに、§5 の当てはめで「キャッシュ無しの時間 ÷ キャッシュありの時間」を今と廃止後で比べた(§5-3)。

## §3 共有の実態(c7-day-4 の呼の列)

- 共有ブロックの本文は全部で 1,482 種類(B2 520・B3 288・B4 152・B4b 516・B1 5・B0 1)。各 tick で呼の多い上位 10 セルが呼の **平均 54%(中央 50%)** を占め、1 tick に現れる B2 は平均 228 種類だった。
- 再利用の数え方: 呼を `xxh64(call_id) % 7`(`fleet.route_primary` と同じ。least-in-flight の振り替えは無視)で GPU に分け、tick 順に並べ、**同じ GPU の直前 K 呼の中に同じ prefix があれば当たり**とした。K=64 は GPU あたりの in-flight 上限(予算行 L6)、K=∞ は「一度出た prefix は消えない」理想。テープの tick 内の並びがセル順に寄っている可能性を除くため、tick 内をでたらめに並べ替えた対照(seed 1)も数えた。

| 窓 K(GPU ごとの直前の呼) | 16 | 64 | 256 | ∞ |
|---|---|---|---|---|
| B1 まで当たる率(テープの順) | 96.5% | 99.4% | 99.95% | 100% |
| **B4b まで(セル部分すべて)当たる率**(テープの順) | 49.9% | **58.4%** | 59.2% | 72.5% |
| 同上(tick 内をでたらめに並べた対照) | 31.1% | **47.7%** | 63.0% | 72.5% |
| 当たる概算 tok / 呼(c7 の構成・対照) | 668 | 699 | 728 | 767 |
| 入力のうちキャッシュから出る割合(c7 の構成・対照) | 72.3% | 75.7% | 78.8% | 83.1% |

- **セル部分の再利用は 48〜73%**(K=64〜∞)。BN-2C(合成・139 セル Zipf 1.0)の「セル節は個体トークンと同じ値段」(命中 59.4% → 48.8%)より高めに出るのは、実際の呼が少数のセル(駅前など)に集中しているため。
- 検算: §5-1 の当てはめに c7-day-4 の構成を入れると、K=64 で 66〜69 呼/秒、K=∞ で 78 呼/秒になる。実測は 2,706,593 呼 ÷ 33,000.8 秒 = **82.0 呼/秒**(エンジンの時間も含む壁時計)。当てはめの b・c を固定すると、実測と両立するのは K が 256(対照の並び)〜∞ の側だけになる(推測)。ただしベンチは o128、本番の出力は平均 37.4 tok なので、当てはめの絶対値は本番より遅く出る。どちらの理由が大きいかは GPU で測るまで分からない。

## §5 処理量への換算(計測 3・推測)

### 5-1 2 つの物差し

1. **当てはめ**: BN-2・BN-2C の 12 行で `1 呼の時間 = a + b × 当たらない入力 tok + c × 当たった入力 tok` を最小二乗で合わせた。a = 0.01379 秒、**b = 1.80×10⁻⁴ 秒/tok、c = 2.69×10⁻⁵ 秒/tok**(当たった tok は当たらない tok の約 1/7 の値段)。12 行の相対誤差は ±5% 以内(r66/bn_fit.json)。
2. **8% 則**: 当たらない tok の増分 × 8.13%/100tok(指示書の物差し)。

- 2 つの差: 8% 則は BN-2 の 300 tok 基準(1 呼 0.116 秒)の割合なので、今の構成(当てはめで 1 呼 0.089 秒)に当てると小さく出る。当てはめの方が今の構成に合わせた値になる。幅として両方を残した。

### 5-2 処理量の変化(既定・K=64・対照の順)

| 案 | 並びそのまま | B3 を前へ | B3 を前へ+場所を共有 |
|---|---|---|---|
| (a) 同じ長さ | −8.8〜−16.2% | −5.8〜−11.2% | −4.4〜−8.7% |
| (b) 214° | −5.6〜−10.0% | −2.5〜−4.2% | −1.2〜−1.5% |
| (b′) 46°(参考) | −1.5〜−2.4% | +1.1〜+5.4% | +2.5〜+8.9% |

- K を広げるほど今のセル共有の価値が大きくなり、廃止の損も大きくなる(K=∞ では (a) 並びそのままで −16〜−29%)。K=16 では (a) 並びそのままで −6〜−11%。全部の組み合わせは r66/model_c7d4_shuffled.json と r66/model_c7d4.json(テープの順)。

### 5-3 prefix の効き(2.39 倍に当たる量)がどれだけ失われるか

当てはめで「全部を当たらない tok とした時間 ÷ 今の時間」を prefix の効きと呼ぶと(推測):

## §7 結論の表(計測 5・推測)

**セル廃止で処理量は x% 落ちる見込み**(K=64〜∞・k=1.24〜1.55・当てはめと 8% 則の幅。括弧は K=256・対照の 4 値の平均)。

| 腕 | 案 | 並びそのまま | B3 を前へ | B3 を前へ+場所を共有 |
|---|---|---|---|---|
| 既定 | (a) 同じ長さ | −9〜−29%(−17) | −6〜−25%(−13) | −4〜−22%(−11) |
| 既定 | (b) 視野 214° | −6〜−24%(−13) | −3〜−19%(−8) | −1〜−15%(−5) |
| 記憶 ON | (a) 同じ長さ | −9〜−28%(−17) | −6〜−23%(−13) | −4〜−20%(−10) |
| 記憶 ON | (b) 視野 214° | −6〜−23%(−12) | −3〜−18%(−8) | −1〜−14%(−5) |

- 前提: 呼数・出力長・GPU は c7-day-4 と同じ。ブロックの長さは HEAD の mock、当たる率は c7-day-4 の呼の列。BN の当てはめは単 GPU・c64・o128・合成コーパス。
- **指示書の 12% との比較**: 12% は「セル部分 147.5 概算 tok が全部共有から全部個人へ」× 8.1%/100tok = 11.9% で再現できる。これには逆向きの誤差が 3 つある。(i) セル部分は 100% 共有ではなく 48〜74%(過大の向き)。(ii) BN の tok は実トークンで、概算 tok の 1.24〜1.55 倍(過小の向き)。(iii) B3 も共有から外れる(過小の向き)。足し合わせると、指示書が想定した設計(共有は場所の定型文などに限る=右の列)の (a) の中央 −11% に近いが、幅は −4〜−22% と広い。
- 損を減らす手(推測・設計の判断は親とユーザー): B3 を個人の部分より前へ置く(3〜5 ポイント戻る)、場所の定型文を共有に残す(さらに 2 ポイント前後)、視野で列挙を絞る(4〜6 ポイント)。B3 を前へ移すのは、知覚契約 §1 の 5「文面凍結」と §2.2 の順序の改版になる。

## §8 実 LLM での確認の手順(GPU 後)

1. **命中率の実測**: vLLM の prefix キャッシュの計数(/metrics の命中と問い合わせの数。名前は版で違うので起動時に確かめる)を、GPU ごと・10 分ごとに取る。今のプロンプトで c7 型の負荷(39 万体・c64/GPU)を流し、§3 の窓 K の値と比べて、どの K が本番に近いかを決める。
2. **合成の置き換えで先に測る**: 個人化の描画ができる前に、c7-day-4 のテープ(call_id・tick・block_ids)と blocks の本文、mock の B5・B6 の分布から、3 つの腕のプロンプトを作る。今 / セル部分を呼ごとに違う同じ長さの本文に置き換え(a)/ 列挙の行を 214/360 に縮める(b)。それぞれ並びそのままと B3 を前への 2 通り。同じ呼の順・同じ艦隊の設定(DP7・64 in-flight/GPU・max_tokens 96・温度 0.7)で各 10〜20 分流し、呼/秒・TTFT・命中率を比べる。
3. **物差しの検証**: 2 の結果で §5-1 の当てはめ(b・c)を本番の出力長で合わせ直し、§7 の表を更新する。8% 則との差もここで決着させる。
4. **CPU**: 個人化の描画を実装したら、5,000 体と 39 万体の 1 tick で `render` の時間を測る(P4 の逐次ループの中身)。変化検出は numba の版を P6 のテストと同じ形(40 万体×100 tick)で測り、P6 の行を delta で改める。

## §9 限界と空欄

- tokenizer が無いので、実トークンは換算 k の幅(1.24〜1.55)で扱った。k の回帰は B5・B6 の長さ(テープに無い)との相関で歪む。
- 当たる率は「同じ GPU の直前 K 呼」という単純化で、vLLM のブロック単位(16 tok)の保持・追い出しや、least-in-flight の振り替えは入れていない。c7-day-4 は HEAD より B0 が短く、セルの B2 の資産も当時の版。
- BN の当てはめは合成コーパス・o128・単 GPU。本番の出力は平均 37.4 tok で、入力の重みが本番の方が大きい可能性がある(その場合、§7 の損は過小)。
- 視野で短くなる (b) は「列挙の物が向きに一様に散る」仮定で、店頭の向き・建物の遮蔽・距離による絞り込みは入れていない。
- 個人化したときの起床の数(CELL_BLOCK に替わる本人の周りの変化で起きる数)と、それによる L4 の呼の総量の変化は**空欄**。
- 5,000 体の描画時間は手元機(他のプロセスと同居)の参考値。
