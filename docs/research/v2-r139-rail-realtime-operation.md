## §0 要旨(10 行)

1. 路線の数え方は W12 の 8 線(山手・埼京〈湘南新宿ラインを埼京線に畳む〉・東横・田園都市・銀座・半蔵門・副都心・井の頭)。根拠は `rail.py` の線別の定員の表と `w12_real_timetables.py` の `FOLD_LINES`(§1)。
2. **列車の在線(`odpt:Train`)が出ているのは JR 東日本と京王だけで、どちらもチャレンジ枠**。データカタログの「列車ロケーション情報」は 6 件で、東急と東京メトロの分は無い(§2)。東京メトロの公開枠のリアルタイムは GTFS-RT の Alert(運行情報)だけで、在線は 10-13 の洗い出しでも 0 件だった。
3. 東急は運行情報と駅の時刻表(渋谷は横浜方面・中央林間方面だけ)しか無く、列車の時刻表も在線も無い。京王は在線・GTFS・GTFS-RT・列車と駅の時刻表・運行情報がそろうが、すべてチャレンジ枠。JR の運行情報はカタログの JR の組織の 8 件に載っていない(チャレンジの案内の頁は「運行情報をはじめ」と書く=食い違い)。
4. `odpt:delay` の単位は**秒**(整数)。ただし公式の仕様書は登録してログインしないと読めず、本書の根拠は二次資料(個人の記事・公開のコード)にとどまる。秒で書かれていても、値が分の倍数に丸められているかは確かめられなかった(2014 年の個人ブログに旧東京メトロ API の「5 分未満は切り捨て」という注がある・未確認)。更新の周期は `odpt:frequency`(秒)という欄で示されるが、値は読めていない(「数十秒」「1 分間隔」は二次資料)。
5. **公開の時刻表は全部が分の精度**。ODPT の駅と列車の時刻表は全件が `HH:MM`(公開枠 6,606 件・チャレンジ枠も全部)。東京メトロの GTFS は発車の秒の欄が 168,017 行すべて `00` で、着と発の差は 0 秒が 167,843 行・60 秒が 150 行・120 秒が 24 行(§3)。
6. 事業者の内部のダイヤは秒を持つ。細井 1987(JR・ORSJ)は、運転時刻表はダイヤ図の時刻表示記号で「15 秒(10 秒の場合もある)単位」になり、「駅頭や市販の時刻表は、秒の部分を切り捨てたもの」と書く(実読)。東急は停車時分を「5 秒単位で切り上げ」(※C7)。JR 東日本の ATOS の秒の扱いの一次資料は読めなかった。
7. 停車時分の模型は、どれも「定数+乗車×係数+降車×係数+混雑の項」の形。Lin & Wilson 1993(ボストンの LRV)は 1 両で 12.50+0.55 乗+0.23 降+0.0078 混雑の積(R² 0.62)。Puong 2000(同 Red Line)は 1 扉あたり 12.22+2.27 乗+1.82 降+6.2×10⁻⁴×(通過の立ち客/扉)³×乗(二次資料からの写し)。日本の値は ※R-77 の 0.771/0.472/0.040(モデル出力の回帰)と ※C7 の小林・岩倉 2019(確認時分 8.7〜20.5 秒・終着の最低 45 秒・200% 前後の模型は無い)。
8. 遅れの伝播について読めた範囲では、細井 1987 の「余裕時間が無いと遅れが終着駅まで回復できず、他の列車に波及する」(余裕は基準運転時分の 2〜3% 前後)と、MIT の講義資料の「停車時分は団子運転(bunching)の決定的な要素」が言えるだけ。「発車=max(表の時刻, 乗降の完了)」をそのまま書いた一次資料は、読めた範囲には無い。扉の間・車両の間で max を取る形(DT=max(DOT₁…DOTₘ))はある。
9. 今の形との差: 60 秒刻み・発車=時刻表の分を刻みの番号に直に置く(`rail.py:351`)・停車 1 刻み(終端 2)・発車は刻みの次で運び出す(`:807`)・遅延なし(`:839`「遅延は第2陣」)・混雑で停車が延びる §2.6 (ii) は未実装。1 秒刻みでは分の表が最初の 1,440 秒に詰まる(独立の読み §4 第 1)。
10. 決めるべき題は 8(§6): 表の時刻の秒の置き方・発車の規則・停車時分の模型・扉と車両の分け方・遅れの伝播の範囲・到着の表・ODPT のリアルタイムの役割(設計書は検証専用と置く)・チャレンジ枠の期限(2027-03-12 に削除)。推薦は書かない。

### 4-3 「発車=max(表の時刻, 乗降の完了)」の形の先例

- 読めた範囲で、この式をそのまま書いた一次資料は無い。
- 近い形は 2 つ。(i) 扉・車両・列車で停車時分の max を取る D1(列車の停車=最も遅い扉の完了)[W14]。(ii) 計画の時刻を、始発の時刻+基準運転時分+余裕+停車の和で作る細井 1987 の式(P1・計画の段の式で、運行中の発車の規則ではない)[W13]。
- 【見立て】日本の通勤線では、表の時刻より前に乗降が終わっても早発しない運用(表の時刻まで待つ)と、乗降が長引けば発車が遅れる運用の組み合わせが「max」に当たる。このうち「早発しない」を事業者の規程で確かめた資料は読めていない。乗り残し(混雑率 200% の上限で扉を閉める)を入れると、「乗降の完了」の中身は「乗れる人が乗り終える時刻」になる(今の 200% の上限の物理と同じ形)。

## §6 決めるべき題(選択肢と根拠・推薦なし)

1. **表の時刻の秒の置き方**: (a) 分の頭(:00)に置く/(b) 分の中の決まった位置に置く/(c) 分の中で seed つきの乱数で置く/(d) 停車時分の表や模型から逆算する(表の分を発車とし、到着=発車−停車)/(e) 事業者の単位(JR 15 秒・東急 5 秒など)の格子に合わせて推定する。根拠: 公開の時刻表は分の精度で、JR は秒を切り捨てている(§3)。(a) は切り捨ての向きに合う。(b)〜(e) はどれも【見立て】で、確かめる物差しが公開に無い。照合に使えるのは在線の遅延(秒)だけで、それは holdout(§2-4)。
2. **発車の規則**: (a) 表の時刻で固定(今)/(b) max(表の時刻, 乗降の完了+確認時分)/(c) (b) に上限を付ける(一定の時間で扉を閉め、残りは乗り残し)/(d) 乗降の完了だけで決める(表を待たない)。根拠: §4-3 のとおり、(b) をそのまま書いた一次資料は読めていない。「早発しない」は運用の規程で確かめる必要がある(未確認)。(c) の上限は今の 200% の物理とつながる。
3. **停車時分の模型**: (a) 線別の固定の表を秒に直す(メトロ 20〜60 秒ほか)/(b) 線形(D4: 0.771・0.472・0.040)/(c) 混雑の非線形(D3 の立ち客の 3 乗・D2 の積の項)/(d) 乗降時間+確認時分の 2 段(D5)/(e) 1 人ずつの乗降を事象にする(R-131 の 0.1 秒の目盛り)。根拠: 日本の係数はモデル出力の回帰(D4)か、200% 前後を外した実測(D5)しか無い。渋谷の朝は 200% に近い線がある(埼京線ほか・※R-77 §3)。海外の係数(D2・D3)は車両と乗り方が違う。
4. **扉と車両の分け方**: (a) 列車を 1 つの器(今)/(b) 車両ごと/(c) 扉ごと。根拠: D1 の max の形は扉ごとの偏りで停車が延びることを表す。号車ごとの偏り(渋谷着で 5・8 号車に偏る=※R-77 §4-3)を出すなら (b) 以上が要る。ホームの階段の位置(※R-90・R-91)と結びつく。
5. **遅れの伝播の範囲**: (a) 便ごとに独立(渋谷で生じた遅れは次の便に及ばない)/(b) 同じ線・同じ方向の後続の便に、最小の時隔を守らせて伝える/(c) 域外から着く便の遅れを外から入れる/(d) 着く便の遅れを分布で揺らす(アンサンブルの偶然として)。根拠: 本リポの世界は渋谷 1 駅で、域外は方面ノード。細井 1987 の波及(P1・P2)は線区の全体の話で、1 駅の中では時隔の制約だけが効く(【見立て】)。(c) は ODPT の在線を運行の入力にすることになり、設計書の「検証専用」と食い違う(§2-4)。(d) は CLAUDE.md §3 の「偶然を揺らす」に当たるが、分布の出どころが要る。
6. **到着の表**: (a) 発車の便から降りる(今)/(b) `w12_rail_events` の到着の行を読む(2-3c で作った器・既定は読まない)/(c) 到着=発車−停車の模型で作る。根拠: 銀座線・半蔵門線・副都心線は公開枠に渋谷の到着がある。東急の南からの到着と JR の途中駅の到着は分の精度でしか無い(着と発が同じ分)。
7. **ODPT のリアルタイムの役割**: (a) 検証専用のまま(遅延の分布・在線の駅の並びを照合の相手にする)/(b) 反実仮想の条件として実際の運休の日を再現するときだけ入れる(設計書の例外)/(c) 使わない。根拠: 照合できる線は在線のある JR 3 線(+京王=データが返るかは未確認)だけ。東急と東京メトロには在線が無い。遅延の欄の丸め(秒か分か)が分からないので、照合の目盛りは公式の仕様書で確かめてから決める必要がある。
8. **チャレンジ枠の期限との関係**: 在線(JR・京王)と京王の時刻表はチャレンジ枠で、2027-03-12 に削除が条件(§2-4)。(a) 期限の後も使える形(公開枠と利用者が手で入手した時刻表)だけで鉄道の秒の段を組む/(b) 期限までに照合だけを済ませる/(c) 期限の後の扱いを ODPT センターに問う。根拠: 記録 odpt-check.md §2-2 の含意(研究開発の利用に合わない可能性・法律の助言ではない)。

## §8 読めなかったもの・先に聞くもの

### 8-1 読めなかったもの(空欄のまま。記憶で埋めていない)

1. **ODPT の公式の API 仕様書**(v4)。`odpt:delay` の丸め・`odpt:frequency` の値・`odpt:Train` の欄の正式な定義。開発者サイトは JavaScript の画面で、仕様の文書はログインの後の頁と見られる(【推測】)。
2. JR 東日本の運行情報(`odpt:TrainInformation`)がチャレンジ枠にあるか(カタログの 8 件に無く、案内の頁はあると書く)。
3. JR 東日本の GTFS-RT のもう 1 つの資源(TripUpdate か Alert か)。2024 年のチャレンジでは `jreast_odpt_train_trip_update` という口があったと検索結果の要約に出たが、頁は開いていない。
4. 京王の在線(`odpt:Train`)と GTFS-RT が実際に中身を返すか、その種類(取得器は京王の在線を取っていない。記録の「実測 §2-4」の根拠は本書では読んでいない)。
5. 細井 1987 以外の、秒の単位の一次資料: 富井『列車ダイヤのはなし』・Wikipedia「乗務行路表」・トラベル Watch(時間切れ)・JR 東日本の ATOS の資料。
6. **海外の運行シミュレーターと遅延伝播の理論**: OpenTrack・RailSys の停車と発車の規則、Carey(時刻表の信頼性・knock-on delay)、Goverde(遅延伝播)、Weston(ロンドン地下鉄の停車の式)、TCQSM 第 3 版の停車の章。**Web の道具が利用上限で使えなくなり、検索も取得もできなかった**。
7. Puong 2000 の原典(MIT の内部メモ)・Lin & Wilson 1993 の原典(TRR 1361)・Adebisi 1986 の式。
8. 角田・川村・岩倉 2013(遅延連鎖シミュレーション)・仮屋﨑 2009 の図の数値(既存答申でも空欄)。
9. 小林・岩倉 2019 の発車の規則(表の時刻を待つか)。C7 の抜き書きに無く、本書で原典を読み直していない。
10. 運行情報の欄(`odpt:trainInformationStatus` ほか)の意味の出典(Ruby のライブラリの文書)は、開こうとして時間切れ。

### 8-2 先に聞くもの

1. 公式の API 仕様書を読むには、開発者サイトにユーザーのアカウントでログインする必要がある可能性が高い(【推測】)。読むかどうか、誰が読むかはユーザーと親の判断。
2. 京王と JR の在線の欄(`odpt:delay` の値の丸め・`odpt:frequency` の値)を API で確かめるのは、本答申の規則(API を呼ばない)の外。確かめるなら、取得器の既存の範囲(JR 3 線の在線)の保存物は holdout なので、holdout の規則と合わせて親が判断する。
3. ODPT のダンプの口が転送する `dataodpt.blob.core.windows.net` は許可の一覧の外(記録 odpt-collection §3 と同じ)。本答申では要らない。
