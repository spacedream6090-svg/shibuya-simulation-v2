## 要約(10行)

1. 都市シミュ/DTの標準的な過程集合は**4本柱**(人の移動・モノとエネルギーの代謝・金の循環・情報の循環)+**制度と自然**。v2は現在「人の移動+金+情報」の3本しか持たず、**モノとエネルギーの代謝が丸ごと空**である。ここが「Generative Agents と大差がない」の正体。
2. 先行LLM社会シムの世界側は薄い: Generative Agents=25体・Smallvilleの物体状態のみ/OASIS=推薦アルゴリズムのみ/CitySim=行動と滞在のみ/AgentSociety=**唯一 economic space(企業・銀行・政府・統計局)を持つが物流・廃棄物・インフラは無し**/Project Sid=Minecraft(物質保存はゲームエンジン由来)。**「都市の代謝を公的統計に対して閉じる」システムは先行に存在しない**(節3)。
3. 渋谷の代謝は公的実数で拘束できる: 区のごみ**43,663 t/年(令和6年度)**、宅配便**全国50億3,147万個/年(令和6年度)**、東京消防庁救急**935,373件(令和6年)**、区の民営事業所**27,624・従業者516,541人**、昼間人口**551,344**。
4. 決定的な予算論点: これらの担い手(配達員・清掃員・救急隊・警備員・保守員)は**合計で数百〜数千体オーダー**。T1標準10呼/体/日でも**呼数予算400万/日の0.1%未満**。エンジン側は配列演算で分オーダー(ベンチ README の余裕)。**「LLM呼を増やさずに世界を厚くする」最良の投資先はここ**。
5. 実装形の原則は既存ドクトリンで決着する: 「bbox内に運転主体がいる過程」=**層2エージェント行動**(配送・収集・補充・警備・救急)。「bbox外の上流」=**B類域外**(物流センター・発電・浄水)。「多数の行動の集計」=**C類集約**(騒音・混雑・電力負荷)。自然のみA類。
6. 金の保存則(U11 transfer API・faucet/sink 列挙)と**同型の「物の保存則」**を新設するのが本答申の中核提案: 在庫・廃棄物の質量収支を `move_goods(from,to,qty,sku)` 単一APIで強制し、faucet=域外仕入、sink=廃棄搬出・消費。月次「物質センサス」で区のごみ実数と突き合う。
7. パターン台帳への効き: 既存 D1′/D4′/D10/E1/E5/E6/C1 を**別ルートから拘束**し、新規行候補7本(廃棄物量・宅配個数・救急件数・断面交通量・インフラ日負荷形状・客室稼働・定期券/駅間OD)。世界側比率は42-46%→**約50%**へ。
8. 陣分け(推奨): **第1陣追加=モノの保存則骨格+店舗補充/納品+廃棄物収集+断面自動車交通+屋内占有**。**第2陣=宅配ラストマイル+公共サービス(救急/警察/清掃)+インフラ日負荷+ホテル在庫+工事規制**。**第3陣=不動産/家賃・災害・報道**。**保留=通信網の詳細・上下水道の管網・電力潮流**(知覚に届かず憲法5(a)(b)を満たさない)。
9. リスク: ActualLog の O(t) 成長(D-R2-6)。物流・収集ログは**日次集約+保持窓**を型レベルで強制しないと runB 構造の再発地点になる。
10. v2が本質的に違う点(一文): **「都市の代謝(モノ・廃棄物・エネルギー)を現実の公的統計に対して収支が閉じる形で持ち、その各フローの担い手を役割知識を持つエージェントの行動として実装する」LLM社会シミュレーションは先行研究に存在しない**(節6末に根拠)。

## 4. 設計原則との整合(行動 / 集約 / 規則 のどれで実装するか)

判定規則(既存ドクトリンの適用):
- **bbox内に運転主体がいる → 層2エージェント行動**(CLAUDE.md §3 第一原則)
- **bboxの外で進行 → B類(域外システム過程)**
- **多数の行動の集計が生む場 → C類(集約)**
- **誰の行動でもない → A類(自然)**
- **規範・予定の記述 → PlanSpec**(D-R2-1)
- どれでもないがエージェント化可能なのにエンジンで代替 → **executor=engine_rule のフォールバック台帳行**(D-R2-2)

## 6. 推奨: 世界過程の拡張ロードマップ

### 6.0 中核提案 — 「物の保存則」(U11 と同型・新設 U-Goods)

金の U11 と厳密に同型に置く:

```
move_goods(from, to, qty, sku, account_code)   # 単一API・在庫の直接代入は静的に禁止
faucet: 域外仕入(RoW→店舗)・訪問者の持込物
sink  : 消費(世帯が食べる/使う)・廃棄搬出(区の収集→bbox外)・返品/域外出荷
残差科目: 棚卸差異(未分類・閾値超でゲート失敗)
退蔵項  : 売れ残り在庫・退蔵された耐久財
検算   : ① 全SKUの 期首在庫+流入−流出=期末在庫 (O(N)総和・毎tick or 日次)
         ② 廃棄sinkの月次総量 ≈ 渋谷区ごみ実数(43,663 t/年 → 119.6 t/日)の band
```

**なぜこれが最大の一手か**: (i)「棚が減る=店員が補充する」というCLAUDE.md §3の看板例が、初めて**閉じた収支として検証可能**になる。(ii)経済(E1/E5/E6)と都市(D1′/D4′)の両方に別ルートで効く。(iii)公的実数(区のごみ量)という**外部アンカーが存在する数少ない世界側過程**。(iv)LLM呼ゼロ。(v)先行LLMシムに前例がない(節3)。

### 6.2 予算・状態成長への申し送り(D-R2-6 適用)

- **ActualLog の再発危険**: 納品・配達・収集・出動はすべて O(t) の追記ログを生む。**型レベルで日次集約+保持窓を強制**(D-R2-6 の `per_day_growth` / `retention` 欄)。読み出しは増分索引で O(1)。runB(未有界コーパス×全再走査)の最有力再発地点。
- **バイト予算**: SKU別在庫は**店舗POI側**(per_cell_bytes)に置き、**個体(M1 30KB/体)には載せない**。配達員の持ち物は「積載量スカラー+SKUベクトル(短)」で十分。
- **呼数**: 新規担い手 約1,000-1,500体 × T1 10呼/日 ≈ **5,000-8,000呼/日 = L4の0.2%未満**。ただし**イベント日の同時昇格**(ハロウィン・大規模障害)は D-R2-1 の警告どおり体数でなく**昇格イベント頻度**で見積ること。
- **性能予算 P4**: 質量収支検算②は O(N_SKU × N_店舗) の総和 → 日次実行で宣言。tick 毎は残差のみ。

### 6.3 「v2が従来のLLMシムと本質的に違う点」— 一文と根拠

> **v2は、都市の代謝(モノ・廃棄物・エネルギー)と貨幣循環の双方を、現実の公的統計に対して収支が閉じる形で持ち、かつその各フローの担い手を役割知識を持つエージェントの行動として実装する、最初のLLM社会シミュレーションである。**

根拠(節3の原文確認):
1. Generative Agents は abstract に economy/traffic/logistics/infrastructure の語がなく、環境は Smallville の物体状態のみ(25体)。
2. OASIS の環境は「dynamically updated environments」=**推薦システムと社会ネットワークのみ**。
3. CitySim の abstract は行動モデリングに限定され、インフラ・経済・物流の記述なし。
4. AgentSociety は唯一 economic space(firms/agents/government/banks・累進課税・Taylor Rule・NBS)を持つが、**モノの流れ・廃棄物・インフラは環境3空間(urban/social/economic)のどこにも無い**。
5. Project Sid の物質保存は Minecraft ゲームエンジン由来であり、**現実統計への照合が設計目標ではない**【確度中・本文未読】。
6. 一方 v2 は既に金の側で `transfer` 単一API・四重記入・「純資産合計=実物資産」検算を持ち(U11)、本答申はこれと同型の物の保存則を提案する。**「公的統計に対して閉じる」という点(区のごみ43,663 t/年に月次で突き合わせる)は先行のどれにもない**。
