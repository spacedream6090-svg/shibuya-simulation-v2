## §0 要旨

1. 差分の器は「行為=世界の状態の差分」を基本操作(CP1 の A〜D の口)の列で持ち、適用の前に検査し、全部通ったときだけ 1 つのまとまりとして当てる。形の先例は JSON Patch の test と全か無か・Datomic の取引関数(純関数・事前に入れたものだけ動く)・ゲームの command(行為を物にする)。
2. 器の部品はリポにほぼ揃っている。書き手は resolve 1 本(`resolve.py:1286`)、金は transfer(`ops.py:229`)、物は move_goods(`goods.py:529`)、権利は grant/revoke(`rights/ledger.py:245`・`:273`)、結果コード「権限なし」(`agents/state.py:242`)。足りないのは判例の器・叶わなかった望みの記録・旗 3 欄の 3 つ。
3. 検査の順の案: 形 → 参照 → 型の許可(CP1)→ 宣言した「無い」→ 物理 → 権利の旗 → 規則の表(machine)→ 保存則の試し当て。落ちた段を理由の型として本人へ短い文で返し、同じものを「叶わなかった望み」の行に書く。
4. 判例は「意図の型の鍵+穴(体・物・場所・量・時刻)+前提+基本操作の列+知覚の文+テストの事例 1 つ以上」で持つ。ランの開始時に凍結し、版とハッシュを manifest に書く(CP10)。
5. **食い違い 1**: §1 #3 は「ランの中では GM を呼ばない」と決め、§3 の 7 (イ) は「GM はランの中で穴を埋めるだけ」と書く。ランの中で穴を埋めるのが誰か(本人の判断の出力・コードの束ね・判断モデル)を決める必要がある(§7 題 1)。
6. **食い違い 2**: A2 の「旗が本社なら『できない』を返す」は、10-12 §1-4・CP3 の「権利に反する行動は止めず記録する」と向きが逆。止める根拠を「物理的に止める仕組み」とみるか、欄を入力の持ち物とみるか、記録に回すかを決める必要がある(題 4)。
7. 「brand があれば本社」の初期化は、フランチャイズでは法の事実と合わない場合がある。公取委の平成 21 年(措)第 8 号は、加盟店基本契約では加盟者が販売価格を自ら決めると認定し、同時にほとんどの加盟者が推奨価格で売っているとも書く。OSM も brand と operator を別の鍵にしている。
8. 経済センサスの「個人/法人」は「チェーンか否か」と同じ量ではない(1 店だけの会社も法人)。突き合わせは手順と注記だけにし、ずれは業種ごとの表で報告する案にした(数は出さない)。
9. smart object の形は、場所と物が口と判例を J0 の源「周りが示すできること」(`decision/layer.py:212`)へ出す形にする。いま空の道具 → 語の表(`tools/registry.py:343`)がその入口になる。文脈の量は 1 場所あたり約 100〜800 字と見積もった(推測・未計測)。
10. 核(v3)に依らずに決められるのは、差分の型・検査・判例と試験・昇格の手順・旗と入力の欄。適用の時刻・同じ時刻の差分の順・時間のかかる行為・顕著性で起こす口・テープの形は、核が決まってから決める(§6)。

## §1 差分の型

### 1-1 表現の候補の比較

列: ① 保存則の検査のしやすさ ② 権利の旗の検査 ③ テープへの記録 ④ 決定論 ⑤ 再開(checkpoint) ⑥ 雛形の穴の作りやすさ ⑦ 今の口との整合 ⑧ 先例。

| 候補 | ① 保存則 | ② 権利の旗 | ③ テープ | ④ 決定論 | ⑤ 再開 | ⑥ 穴 | ⑦ 今の口 | ⑧ 先例 |
|---|---|---|---|---|---|---|---|---|
| (a) 基本操作の列(`money.transfer`・`goods.move`・`right.grant` ほか) | 作りで守れる(金と物は transfer/move_goods の口を通るだけ。直接代入が形として書けない) | 操作の種類ごとに「どの旗を見るか」を表で引ける | 1 操作 1 行。既存の生ログ(transfer の輪・物の記録)と出来事の記録にそのまま乗る | 操作の列の順を固定すれば一意 | 状態は既存の台帳が持つので器は何も足さない | 操作の引数を穴にできる | 高い(書き手 1 本・AST の検査 `money_writers`・`rights_writers` がそのまま効く) | command(Nystrom)・Concordia v2 の「Python+LLM の混合」(R-124)・R-105 型 D |
| (b) 欄ごとの set/add/transfer の列 | transfer の欄は (a) と同じ。set/add を金と物の欄に使うと直接代入になり、検査で弾く必要がある | 欄ごとに旗を結ぶ(値札の欄 → 値付けの旗) | 1 欄 1 行 | 順の固定で一意 | 同上 | 欄の値を穴にできる | 中(保存されない欄=値札・営業時間・看板の文だけに set を許すなら (a) と併用できる) | ECS の component 書き換え・Inform 7 の Carry out |
| (c) JSON Patch(RFC 6902) | 金と物も `replace` で書けてしまう。保存は後の検算でしか見られない | 経路(JSON Pointer)ごとに旗を結ぶ | 文書としては小さい | `test` で事前条件を書け、全か無か(§5 の SHOULD terminate・HTTP PATCH は atomic) | 世界を 1 つの JSON 文書として持つ必要があり、SoA の今の作りと合わない | `value` を穴にできる | 低い(世界は配列の束で JSON 文書ではない) | RFC 6902 ◎ |
| (d) ECS の component の差(Bevy の Commands など) | (b) と同じ。構造の変化(体や物を足す・消す)を遅らせて同期点でまとめて当てる形は借りられる | component の型ごとに旗 | 1 命令 1 行 | `ApplyDeferred` で「順に当てる」 | 今の SoA の書き窓(`writable()`)と同じ考え | 命令の引数 | 中(遅らせて当てる形は resolve の Phase C と同じ向き) | Bevy Commands ◎(MIT OR Apache-2.0) |
| (e) 事実の差分(Datomic の assert/retract・イベントソーシング) | 事実を足すだけなので履歴は完全。保存は取引関数(`:db/cas` 型)の中で見る | 取引関数の中で旗を見て `cancel` で取り消せる | 事実の列そのものがテープになる | 取引は直列の pipeline で走る | 事実の再生で状態を作り直せる(Fowler の complete rebuild・temporal query) | 取引関数の引数 | 中〜高(テープと出来事の記録は既に「事実の列」に近い。ただ状態の本体は SoA) | Datomic ◎・Fowler ◎ |

読み取れること(推測を含む):
- 保存則を作りで守れるのは (a) だけ。(b)〜(d) は金と物の欄を「書けない欄」にする検査を足せば同じになる。CP1「A〜D は基本操作からしか書き換えない」とそろうのは (a)。
- (e) の取引関数は「雛形」の先例としてそのまま読める。純関数 `[db-before, args] -> tx-data`、事前に入れたもの(database function か classpath function)だけが動き、ランの中で新しく書かない。§1 #3 の「ランの中は凍結した判例だけ」と同じ形。
- 値札・品揃え・営業時間は保存されない欄なので、(a) に「店の欄の書き換え」の操作を 1 種足すか、(b) を併用するかの選択になる(題 3)。

### 1-2 操作の種類の表(案)

| 操作 | CP1 | いまの書き口 | 保存 | 主な検査 |
|---|---|---|---|---|
| `money.transfer` | A | `economy/ops.py:229` の `transfer`(帳簿の口を通す) | 保存(2 脚) | 残高・許された組(`accounts.is_allowed`) |
| `goods.move` | A | `economy/goods.py:529` の `move_goods` | 保存 | 在庫・許された組(`goods_is_allowed`) |
| `thing.make` / `thing.use` | B | grep で見つからなかった(B の口はまだ無い) | 材料の消費と生成で閉じる(Dwarf Fortress の REAGENT→PRODUCT・R-124) | 材料が揃うか |
| `right.grant` / `right.revoke` | C | `engine/rights/ledger.py:245`・`:273` | — | 種類と物の閉じた表 `OBJECTS_OF_KIND`(`:87`) |

| `body.intent` | E(法則への入力) | 物理のコード(`resolve.py` の `_apply_move` など) | — | 物理。位置を直接書かない |

`store.set` は**新しい欄の書き口**なので、§1 #3 の言う「器の拡張=コードでラン外」に当たる(推測ではなく今の書き口の有無から言える)。

### 1-3 差分の行の形(案・R-124 §5 ② の改め)

R-124 §5 ② の JSON をもとに、11-02r §2-2(世界の時刻はナノ秒・刻みに依存しない)に合わせて時刻の欄を `t_ns` に替え、出どころの欄を足した。
```json
{
  "schema": "shibuya.diff/1",
  "t_ns": 0,
  "actor": "agent:123",
  "origin": {"kind": "port | precedent", "id": "語の番号 か 判例の id@版"},
  "cause": {"type": "LlmCall", "call_id": "…"},
  "bind": {"actor": "agent:123", "target": "agent:456", "place": "poi:78", "sku": 3, "qty": 1, "at_ns": 0},
  "pre": [{"pred": "open|stock_ge|cash_ge|holds|reach|flag_is", "args": ["place"]}],
  "ops": [{"op": "money.transfer", "src": "actor", "dst": "place", "amount": "qty*price", "what": "金:消費支出"}],
  "duration_ns": 0,
  "percept": {"actor": "…", "observers": "…"}
}
```
- 役の名(`actor`・`target`・`place`)で書き、適用の直前に `bind` で束ねる(APC の固有名を抜いた雛形・R-124)。
- `amount` の式は四則と表の読み(値札・数量)だけに限る案(推測)。任意の式を許すと「コードを書く」ことになり、§3 の 7 (イ) の成り立つ条件に反する。

## §2 適用の前の検査

### 2-1 検査の順(案)と「できなかった」の理由の型

| 段 | 検査 | 見るもの(今の読み口) | 落ちたときの理由の型 | 本人への文(例・知覚どおり=D3) | D4 の分け方の初期値 |
|---|---|---|---|---|---|
| 0 | 口か判例があるか | 適用表 `_APPLY_BY_VOCAB`(`resolve.py:3448`)・凍結した判例の器 | `no_port` | 「どうすればいいか分からなかった」 | 欠陥の候補 |
| 1 | 形 | スキーマ(差分の行の形) | `malformed` | 返さない(器の誤り=計器だけ) | 欠陥 |
| 2 | 参照 | 体・POI・SKU・権利の行が実在するか | `bad_target`(`ResultCode.BAD_TARGET`) | 「相手(もの)が見当たらなかった」 | 正しい失敗の候補 |
| 3 | 型の許可(CP1) | D を他人に書かない・A を作らない | `forbidden_kind` | 返さない(判例の誤り) | 欠陥 |
| 4 | 宣言した「無い」 | `world/processes/absent.py` の宣言(店の出入り・雇う/辞めさせる・新しい品目=§5-4) | `declared_absent` | 「今はできなかった」 | 宣言による不在(第 3 の区分) |
| 5 | 物理 | 届く・営業中・容量・鍵・時間が残るか(`talk_within_reach`・`open_mask`・`crowd.can_admit` など) | `physics`(既存の `CLOSED`・`TOO_FAR` ほか) | 「閉まっていた」「遠すぎた」 | 正しい失敗 |
| 6 | 権利の旗 | A2 の旗 3 欄(§5)・`Rights.holds`(`rights/ledger.py:357`) | `flag_hq`(`ResultCode.NO_PERMISSION`=`agents/state.py:242`)か「許可のない行動」の記録 | 「値段は本部が決めるので変えられなかった」(題 4 しだい) | 正しい失敗 |
| 7 | 規則の表(machine) | `docs/design/rules-table.json` の `kind: machine` の 16 行(消費税・源泉徴収など=止めるより自動でかける行) | `machine_rule` | 「…の決まりでできなかった」 | 正しい失敗 |
| 8 | 保存則の試し当て | 写しに当てて残高・在庫・流れの表が閉じるか(`economy/checks.py`) | `conservation` | 「お金が足りなかった」(`MONEY_SHORT`) | 正しい失敗 |

- R-124 §5 ③ の 8 段との違い: 「宣言した『無い』」を物理の前に置いた(無いと宣言した過程が裏口から入る危険=R-124 §6 のまとめ)。物理を権利より前に置いた(現実でも先に体が止まる)。順の根拠は推測で、題 5 の一部として扱う。
- 全か無か: 1 つでも落ちたら何も当てない(RFC 6902 §5 の例「no changes being made to the document at all」・Datomic の `cancel`)。今の `transfer` も「検査 → 出来事を書く → 金を書く」の順で、金だけ動いた状態を残さない(`ops.py` の見出しの 6)。
- 検査の時点: PostgreSQL は CHECK を行ごとに即時、外部キーなどだけを取引の終わりまで遅らせられる。差分の器でも「段 1〜7 は即時・段 8 は差分のまとまりの終わり」と分けられる(推測)。
- `kind: human` の 14 行は止めない。起きたことにして記録する(回答 11-01 §5・10-12 §1-4)。

### 2-2 「叶わなかった望み」の計器(案)

行の欄(1 行=1 回の試み): `t_ns`・`agent`・`role`(店主・店長・客など)・`place`(セルと POI)・`intent_raw`(本人の自由な言葉=D2)・`intent_key`(正規化した鍵・当たらなければ空)・`stage`(上の表の段の番号)・`reason`(理由の型)・`target_kind`・`origin`(口・判例・無し)・`cause`(判断の呼びの id)。
- 既存の `UndefinedActionRecord`(`llm/undefined.py:542`)は `tick` の欄で持つ。11-02r §2-2 により新しい行は `t_ns` で持つ。
- 計器の出し方: 回数を「理由の型 × 役割 × 場所の種類 × 時間帯」で数え、版上げごとに上位の `intent_key` と `intent_raw` の見本を出す(D3 の 1「原因で束ねる」の材料)。
- 返し方: 本人へは段 0〜8 の文の型だけを返し、器の中の言葉(判例・段の番号)は見せない(推測・題 8)。
- D4 の計器(正しい失敗/欠陥)に「宣言による不在」を 3 つ目の区分として足すかは題 8 に含めた。

## §3 判例(意図の型 → 差分の雛形)

### 3-1 雛形の形

| 欄 | 中身 | 先例 |
|---|---|---|
| `key` | 意図の型の鍵(R-124 §5 ⑤ の 9 欄の完全一致・語彙の版と規則の表のハッシュを含む) | APC のキーワード・D-71 答申の完全一致 |
| `holes` | 穴の型と範囲: 体(役の名)・物(SKU・物の種類)・場所(POI・セル・場所の種類)・量(整数の上下限)・時刻(`at_ns` か `duration_ns`・上下限) | Convai の型つき引数(R-124)・Datomic の取引関数の `args` |
| `pre` | 前提の述語(エンジンの読み口だけ) | Sims の Check Tree・Inform 7 の Check・PDDL の precondition(R-124) |
| `ops` | §1-2 の操作の列(穴を参照) | Datomic の取引関数の戻り値=tx-data |
| `percept` | 本人と周りへの文の型 | Inform 7 の Report・Concordia の event statement |
| `tests` | 事例 1 つ以上: (スナップショットの id, 穴の値, 期待する差分か期待する理由の型) | CP11(答えの分かっている場面)・ASI の 3 検査(R-124) |
| `meta` | `precedent_id@version`・`source_model`(下書きのモデル)・`reviewed_by`(Fable)・`accepted`(ユーザーの承認日)・`conf`・`status` | 10-12 §1-4 D3 の 8・CP8 の代わりの台帳 |

### 3-2 穴の埋め方(ランの中)

§1 #3 によりランの中で GM は呼ばない。穴を埋める候補は 3 つ(題 1):

| 候補 | 中身 | 利点 | 欠点 | 現実との整合 |
|---|---|---|---|---|
| (i) 本人の判断の出力 | 判断の呼び(L2 か判断モデル)の構造化出力に「判例の名+穴の値」を入れる | 本人の考えがそのまま入る | 判断の出力の欄が増え、D2(メニューにしない)と擦れる | 量の穴(値段・数)を本人が決める=A2 の 1「何をするかは本人が考える」と合う |
| (ii) コードの束ね | 行為者=自分・場所=今の場所・相手=注意の焦点(`focus_target`)などを決まりで束ねる | 決定論・LLM の呼びが増えない | 量の穴を埋められない(既定値を置くと設計者の指紋) | 量の穴が残る判例には使えない |
| (iii) 判断モデル | 穴の値の分類・回帰 | 速い | 第 1 世代の判断モデルは穴の型を学んでいない(推測) | dm_eval の後でしか分からない |

§3 の 7 (イ) の「GM はランの中で穴を埋めるだけ」を、(ii) のコードの束ね手を「GM」と呼ぶ意味に読めば、§1 #3 と矛盾しない(推測による読み)。

### 3-3 判例の保存と昇格(ラン外)

1. **集める**: 叶わなかった望みの行を `intent_key`(空なら `intent_raw` の正規化)で束ねる(D3 の 1)。
2. **下書き**: フロンティアモデル(構築側)が雛形の JSON とテストの事例を書く。Claude の構造化出力は数の範囲を書けないので、範囲はコードで検査する(R-124 §2)。
3. **機械の検査**: スキーマ・CP1 の型・宣言した「無い」に触れないか・各テストの事例をスナップショットに当てて期待どおりか・元の試みをスナップショットから再生して通るか(D3 の 5)。
4. **形を決める**: 物の affordance(既存の語+物の状態)で表せるならそちらを先にする(R-124 §5 ⑥ の 4・親案に賛成済み)。
5. **親の検収**: Fable が生の記録で確かめる(D3 の 6・D6)。
6. **ユーザーの検収**(D3 の 7)。
7. **凍結**: 判例の器の版を上げ、器のハッシュを manifest に入れる(CP10)。次のランから効く。ランの中では器は育たない。
8. **器の拡張**: 新しい欄・新しい操作の種類(§1-2 の `store.set` など)が要る判例は、雛形では足せない。コードの版上げ(試験と切替口つき・ラン外)にまわす。

失効: 規則の表のハッシュか語彙の版が変われば鍵が変わり、自然に当たらなくなる(R-124 §5 ⑥ の 6)。消さずに `status=revoked` にする。

## §4 smart object の形

### 4-1 形

- 場所と物は「自分の口」(語彙の行為の実体=適用の関数か判例)と、自分を対象にした判例の名を持つ。本人の文脈に出すのは、J0 の源「周りが示すできること」(`engine/decision/layer.py:212` の `affordance_words`)の拡張として行う。今は場所の種類と営業時間から語を作り(`:222`〜`:231`)、道具の台帳から語を足す口(`:232`〜`:237`)があるが、道具 → 語の表 `TOOL_ACTION_WORDS`(`engine/tools/registry.py:343`)は空。
- 先例との対応:

| 先例 | 物が持つもの | 選び方 | v2 での対応 |
|---|---|---|---|
| The Sims(Forbus & Wright・R-124 で親確認済み) | 行為の手続き+Check Tree+広告(欲求ごとの値) | 効用の最大化のコード。Check Tree が偽なら選択肢にも出ない | 口と判例の `pre` が偽なら文脈に出さない。広告の値は持たない(選ぶのは本人の判断=D2 と 10-12 §1-4) |
| UE Smart Objects | 活動の集まり・slot・活動の tag・予約(Claim → Occupied → Free) | 体が範囲と tag で探す。物は実行の論理を持たない | 口の容量(席・列)は slot の予約と同じ形。物が論理を持たない点は「口=適用の関数はエンジンの側」と同じ |
| Kallmann & Thalmann 1998(smart object の名の出どころ) | 物が自分の相互作用の特徴(部品・動き・つかむ所・機能)を持つ | 体の側の系を物ごとに書き換えなくてよい | 物を足せば口が増える(語彙を閉じたまま世界を増やす=R-124 §1 の読み取り) |
| Generative Agents | 場所と物を包含の木で持ち、文に直して渡す | LLM が木を上から選ぶ | 本人が知っている場所だけ出す(道具の台帳の `known_by` と同じ考え) |

### 4-2 文脈の大きさの見積り(推測・未計測)

式: 1 回の判断の追加字数 ≈ Σ(見える場所 m)[口の数 p × 口の字数 a + 判例の数 q × 判例の字数 b]。

| 場面 | m | p × a | q × b | 1 場所 | 合計 |
|---|---|---|---|---|---|
| 今(口だけ・語彙 v3 は 13 語以下=`decision/sources.py` の逐次ループ宣言) | 1 | 4〜8 語 × 10〜15 字 | 0 | 約 40〜120 字 | 約 40〜120 字 |
| 判例を足した店 | 1 | 同上 | 5〜20 件 × 15〜30 字 | 約 115〜720 字 | 約 115〜720 字 |
| 見える店が多い通り | 3〜5 | 同上 | 同上 | 同上 | 約 350〜3,600 字 |

- 字とトークンの比は Qwen3 の分かち方で測っていない(未計測)。上限は「顕著性の上位 k 場所だけ」「本人が知っている判例だけ」で抑える案がある(題 7)。
- D2(分類をメニューにしない)との関係: 口と判例を一覧で見せると促しになる。J0 は「頭に浮かんだこととして見せる言い方」を R108-7 の空欄にしている(`decision/sources.py` の見出しの expedient)。判例の名の見せ方も同じ空欄に入る。

### 4-3 語彙(112 件)との関係

- 口は語彙の行為の実体である。routing §5 の「語彙に足す行為」23 行(見送る・何をいくつ・接客と価格改定に適用を付ける ほか)は、口を足す候補の一覧になる。判例は「語彙に無いが、既存の操作の組で表せる行為」を受け持つ。
- routing §1-8 の #101(値段を変えるか)は行き先が L2、つなぎは「価格は構築時の値で固定と宣言」。A2 の後は「店主の L2 → 口 `store.set` → 旗の検査」の道になり、`store.set` は器の拡張(§1-2)を要する。
- 112 件のうち L1.5 の 55 件・L2 の 7 件が口を通る。判例で受けるのは、どの行にも当たらない行為(語彙の外)だけ。
