## 2. JR・東急・京王の時刻表を実データにする

今は、メトロ 3 線だけが ODPT の実ダイヤで、JR 3 線・東急 2 線・京王は等間隔の推定です。ダイヤは「外からの決定」として実データから入れる方針なので、次のように進めます。

### 2-1. ユーザーの判断(2026-10-12)

- **今は商用利用ではない研究開発の段階なので、各社の公式の時刻表(PDF)を、ユーザーが自分で入手して Claude Code に渡す。** 法人化して商用で使う段になったら、鉄道会社に利用の許諾を申請する。
- これは CLAUDE.md §7 の注「いまはどのサイトからも取得しない。再開はユーザーの判断」に対するユーザーの判断です。**Claude Code が公式サイトから自動で取得するのは、引き続き行いません。** 渡すのはユーザーが手で入手したファイルだけです。
- **NAVITIME の画面を保存したもの(京王 井の頭線の `3544.pdf` など)は使いません。** NAVITIME の規約は生成 AI での処理を名指しで禁じています。京王は、京王の公式の時刻表をユーザーが入手して渡します。
- 根拠の整理(法律の助言ではない): 発車時刻は事実で、著作物ではない。取り出すのは事実だけで、図の表現は使わない(著作権法 30 条の 4 の情報解析に近い使い方)。各社の規約の「私的使用の範囲を超える場合は許諾」との関係は、商用の前に許諾を取ることで解く。

### 2-2. Claude Code がすること

1. ユーザーが渡した公式の時刻表から、**事実だけ**(発車時刻・種別・行き先・平日/土休・方面・時刻表の版=ダイヤ改正の日付)を表(CSV)に取り出す。東急の PDF は文字のデータが無い図なので、画像から読み取ることになる。**読み取りは 2 回独立に行い、食い違いを突き合わせ、時ごとの本数を手で数えた値とも照らす**(読み違いを防ぐ)。
2. 渡されたファイルと取り出した表は `data/` の下に置き、**git に入れない・公開しない**。ライセンス台帳に「ユーザーが入手した公式の時刻表・研究開発の段階でユーザーの判断で使用・商用の前に各社の許諾が要る」と記録する。
3. 入ったら W12 の該当の線を実ダイヤに置き換える(等間隔の推定は、実データの無い線だけに残す)。置き換えの版上げは鉄道の段に合わせる。
4. 並行して、ODPT のチャレンジ枠(キーは環境変数)で JR 東日本・東急・京王の時刻表が取れるか、取れるなら使用条件を調べて報告する(使えれば、商用の段での許諾の手間が減る可能性がある)。
5. 足りない線と方面(例: 湘南新宿ライン・JR の各方面)の一覧を出し、ユーザーに頼む。

- 実データが入るまでは、等間隔の推定(丸めを直したもの)をつなぎとして台帳に載せる。

## 6. 作り方の改善(ボトルネックへの対策)

第 329 で挙がったボトルネックの根は、**`run_day`(`engine/run.py` の約 3,000 行・入れ子の関数 17 個が同じ変数を共有)にほぼ全部の処理が入っていること**だと考えます。作業木を分けても、全員がこの関数を触る限り取り込みでぶつかり、差が出ても原因の場所が分かりにくくなります。次のように改めてください。

### 6-1. 第 1 期の最初に「1-0 分解」を足す(結果不変)

- `run_day` を、①世界の状態の箱(状態の表)、②処理の単位(系: 移動・知覚・判断・会話・お金・鉄道ほか)、③決まった順に系を呼ぶ短い進行役、に分ける。
- **各系は「読む欄」と「書く欄」を宣言し、宣言の外を書いたら試験で落ちる**ようにする(状態台帳の検査と一体に)。
- 中身は変えず、byte-check 19 構成・2 日のラン・指紋で同じ値を確かめる。
- 既存の `engine/processes/` はこの型に近いので、それを土台に広げる。先例はゲームエンジンの「状態の表+処理の系」(UE5 の MassEntity・Unity の DOTS など)。E1 の比較表に入れる。
- **分解の切り方(系の境目と口)は、先に紙で作り、別の検収役と親が確かめてから切る**(切り方を誤ると後で口を作り直すため)。
- そのあと T0(時計)を 1 本で小さく通し、残りの土台を並べる。

### 6-2. 口の約束を先に

- 土台 8 つは、それぞれ決まった口(インターフェース)の向こうに作る。**親が先に口の約束と受入の試験を書き**、実装役はそれを満たすように作る。仮の実装(fake)を用意し、他の土台ができていなくても単体で試せるようにする。

### 6-3. 作業木と取り込み

- 実装役は各自の作業木と枝で作る。親が依存の順に取り込み、取り込むたびに 6-4 の段 2 の確かめをする。
- リサーチは文書だけの別の枝で進める(コードとぶつからない)。

### 6-4. 確かめ方の段を分ける

| 段 | いつ | 中身 |
|---|---|---|
| 0 | 保存のたび | その系の単体の試験 |
| 1 | 段の途中 | 関係する試験+小さな人数の byte-check(過去に差が出た構成を含む 3〜4 構成)+**系ごとの出力の指紋**(差が出たら、どの系かがすぐ分かる) |
| 2 | 取り込みの前 | byte-check 19 構成。構成どうしは独立なので CPU の数だけ並べて回す |
| 3 | commit の前・夜 | 全体の試験。並列化(pytest-xdist など)と、変えた所に関係する試験を先に回す道具を試す(効き目を測って採用) |

### 6-5. 検収の書類

- 実装役の報告に「どの数を何で確かめたか(コマンド・入力・指紋・差の表)」を付ける。親は再実行と生の記録の確認で済むようにする。

### 6-6. ユーザーの判断待ちで止めない

- **元に戻せる判断**(切替口や腕で入るもの・既定を変えないもの)は、親案で切替口の裏に入れて先に進め、ユーザーは後でまとめて確認する。
- 止めて聞くのは、戻せない判断と、決定の範囲を超える判断(新しい expedient の値を既定にする・検証専用のデータに触る・許可の一覧の外のドメイン・費用がかかるもの)だけ。

### 6-7. 計画への反映

2. 第329 の報告への答え: (1) 4 つの commit の切り直し(force push)は**しない**。段ごとに commit と記録(byte-check の json など)の対応表を記録に残す。再発防止はリポジトリの仕組みに(改行の形を固定する .gitattributes・commit の前に「入れるはずのファイルが全部ステージされているか」を確かめる手順・第 1 期の前に入れる)。(2) 住人の入れ替わり(4,191/5,000)は止めない。旧の 5,000 体・新の 5,000 体・全体の 3 つで属性の分布(年齢・性別・住民/従業者/来街者の割合・町丁目など)を比べ、偏りが無いことを確かめて記録(偏りがあれば報告)。(3) 10-03 の予想 2 つ(E2 の final・E4 の母集団)が成り立たなかったことは記録のとおりでよい。
3. 時刻表と駅構内図: `data/user_timetables/` にユーザーが各社の公式サイトから手で入手した時刻表と構内図(入手日 2026-10-12・JR・東急・京王を含む)。振り分けは親に任せる。扱いは §2(構内図も同じ)。時刻表からは発車時刻・種別・行き先・平日/土休・方面・版を取り出す(2 回独立に読んで突き合わせ・時ごとの本数とも照らす)。構内図からは事実だけ(SR17: 改札・コンコース・ホーム・階段/エスカレーター/エレベーターのつながりと階・改札の名前と営業時間・エスカレーターの向きと時間帯・号車の位置)。図は使わず公開しない。ファイルも表も git に入れない。ライセンス台帳に記録。NAVITIME のものは除く。最初にファイルの一覧(会社・路線・駅・種類・版や時点)と足りない路線・方面・駅の一覧(§2-3 と照らす)を報告する。
4. 順番: 回答の保存と反映 → 版上げ 1 回目の残り(E3・B0〜B6)→ 時刻表と構内図の一覧と足りないものの報告 → .gitattributes と commit 前の確認 → 第 1 期の 1-0 分解の口の案の報告。リサーチは並行可。報告の先頭に結論の箇条。
