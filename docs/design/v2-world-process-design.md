## 1. 世界過程とは何か(定義の大枠)

**定義(案)**: エージェント個体の意図的行動「以外」から世界状態が変化する過程の総称。

ただしドクトリン「世界の変化はエージェント行動の結果として実装」(CLAUDE.md §3)が常に第一原則。したがって世界過程モジュールは無限定な「エンジンで世界を動かす装置」ではなく、**次の3類に限定**する:

| 類 | 定義 | 例(候補) |
|---|---|---|
| **A 自然過程** | 誰の行動でもない物理・環境の変化 | 天候(気象930日データ)・昼夜/日照・気温・季節 |
| **B 域外システム過程** | **bboxの外**で進行する運行・供給 | 域外区間の鉄道進行・物流/配送の上流・ライフライン |
| **C 集約過程** | 多数の行動の集計が生む「場」 | 混雑場(グリッド密度)・価格指数 |

**D-R2-1決定(仮・2026-09-02)——境界例の帰属**:
1. **営業時間**: 層2が正(店主エージェントが開け閉めする)。センサス由来の営業時間表はC類でなく**計画データ**(下記)として保持し、conf宣言つきフォールバックに使える。Phase 2最小骨格では一時的にフォールバック側で動かす段階案を採用。
2. **交通運行(鉄道・バス・タクシー共通)**: **ダイヤ・路線は「計画データ」(大枠・規範)として存在し、実際の運行はLLMエージェント(乗務員・駅員・運転手=層2)に任せる**(ユーザー方針)。域外区間の進行のみB類。遅延・見合わせ・増発等の逸脱はエージェント判断(+必要なら裁定)から創発する。ODPT実ダイヤ1,810本=計画データの初期値・D10駅利用者数=照合装置。実装上の適合: 「ダイヤどおり運行」は乗務員のT0習慣/役割知識として植えられ、通常時はLLMコスト最小・例外時のみ昇格(認知LODと同型)。運行従事者は40万体中の少数(数千規模)でありコスト影響は限定的——ただしコスト見積は体数でなく**昇格イベント頻度**で行う(障害1件で全線の乗務員が同時昇格・検証答申の指摘)。
   **追補決定(仮・2026-09-02)——指令エージェント**: 障害時の運転整理は乗務員個体の局所判断からではなく、**指令員(単一の改訂権者)が計画そのものを書き換え**、乗務員が改訂版に従う(鉄道再スケジューリング文献の一致所見)。各社に指令エージェント(層2・数体)を置き `revises(指令, PlanSpec)` を発火させる。ユーザー条件2点: (a)**「指令・運行管理」は業種横断の一般パターン**(バス営業所・タクシー配車・航空の運航管理・電力の給電指令・小売本部の価格改定権限など)として理解し、該当役割の設計で同型を適用する。(b)**ハードコードでなく、指令員という役割知識を持つエージェントから自ずと発生する形を第一候補にする**——「障害時は自分が計画を改訂する」が役割知識に入っており、revisesはその出力チャネルにすぎない(ボトムアップ創発ドクトリンと整合)。
3. **治安の体感**: 世界過程には**置かない**。U18(観測+伝承の創発案)を将来扱う時に再考。

**新概念「計画データ(planned data)」**: ダイヤ・営業時間表・路線図のような「世界に存在する規範・予定の記述」。世界過程(状態を変える)ともエージェント(判断する)とも異なる第3の実体で、レジストリが保持し、エージェントは役割知識・習慣を通じてこれに従う(逸脱可)。現実整合アンカー(実ダイヤ)がそのまま初期値になる。**正式形は§2のPlanSpec型**(「参照専用」の旧表現は廃止——エンジンが自律的に進めないだけで、改訂権者のrevisesで実行時に書き換わる)。

**重要な線引き**: bbox内に運転主体がいる過程(店の棚の補充・開店閉店・接客)は世界過程では**なく**、層2(役割の知識を持つエージェント)の仕事。エージェント化できるのにエンジン規則で代替する場合は、従来どおり**conf宣言つきフォールバック**であり、その置き場と台帳(カバー率・返済期限)をこのモジュールが一元管理する。

## 2. 世界側台帳の骨格 — D-R2-2決定(仮・2026-09-02・検証答申反映の修正形)

**原則: 台帳(名前空間・ID体系・概念モデル)は1つ、レコード型は3つ。** ユーザー発案の統合は概念モデルのレベルで採用し、レコード形は業界標準の一致解(Transmodel単一概念モデル+NeTEx計画/SIRI実時間/OpRa実績の3実装・GTFS static/RT・CityGML Versioning/Dynamizer)に合わせて3型に分ける。性質が違いすぎて同じ行に収まらないため(予定=版と有効期間を持つ改訂可能文書/実績=不変の追記記録)。

```
WorldProcess(世界過程):
  { id, 状態の定義, 更新規則, 時計(物理=連続/制度=日次), mechanism|expedientタグ(expedientなら感度試験IDと返済期限),
    門前条件(パターン照合1行・世界側台帳行との対応), 状態成長の宣言(§3), dilatable(時間減速の可否・UGC答申#20) }
PlanSpec(計画仕様・旧「計画データ」の正式形):
  { id, 内容(ダイヤ・営業時間表・価格表・路線図…), 有効期間(valid time), 版(transaction time), 改訂権者,
    規範種別(軸3), 違反可能性(軸4), 公示範囲(誰に届くか=知覚契約との接続), 遵守率の観測欄(死んだ規範の検出=歪み宣言の材料) }
ActualLog(実績ログ):
  { id, 対象, 逸脱語彙(列挙型・GTFS-RT式: SCHEDULED/CANCELED/REPLACEMENT/SKIPPED/NO_DATA等+delay),
    保持窓, 増分索引 }  ※追記専用・不変。O(t)成長する唯一の型なので§3の宣言を型レベルで強制(runB構造の最有力再発地点)

関係(第1級):
  realizes(WorldProcess | AgentAction, PlanSpec) — 属性 executor: {llm_agent | engine_rule | none}
    ※「フォールバック」の正体はPlanSpecが世界過程に変わることではなく、この executor の切り替え。
      conf宣言つきフォールバック台帳(§1末尾)= executor=engine_rule 行の一覧そのもの(カバー率・返済期限を一元管理)
  records(ActualLog, WorldProcess | AgentAction)
  revises(Agent, PlanSpec) — 運転整理(指令)・値上げ(店主)・営業時間変更はここで発火
  counts_as(物理的事実, 制度的事実, 文脈) — 構成的規則(「制服を着た者は駅員として扱う」等・SAI/Searle)
```

**分類軸は4本**(検証答申: 2軸では反例8件が畳めない・Searle/OperA/IG2.0/SAIの4系統が独立に軸3を、Grossi et al.が軸4を要求):

| 軸 | 値 | 出どころ |
|---|---|---|
| 軸1 実行様態 | エンジンが進める / 参照(規範・予定)/ 行動から導出(集約)/ **物理アフォーダンス**(道路網・線路・建物=brute) | 原案+第4値追加 |
| 軸2 可変性・改訂権者 | 誰がどれほど変えられるか(ユーザー原案) | 原案 |
| 軸3 規範種別 | constitutive(構成的)/ regulative(規制的)/ brute-physical / descriptive-only | Searle・OperA・IG2.0・SAI |
| 軸4 違反可能性 | regimented(違反不能=エンジン強制・原則1)/ enforced(違反可能+検知+制裁=行12・14・原則6)/ unenforced | Grossi et al.(既存構造の露出) |

旧3類のうち**B(域外)・C(集約)は導出ラベルへ格下げ。A(自然過程)は第1級を維持**——誰も知らなくても雨は降るが、誰も参照しないダイヤは存在をやめる(brute fact / institutional fact・存在条件が違う)。
「参照専用」という旧表現は誤導的なので廃止: PlanSpecは「エンジンが自律的に進めない」だけで、実行時に revises で書き換わる(運転整理・Trip Modifications)。
分離を保つ最強の理由は**検証可能性**: 計画と実績を分けて持つと「逸脱の分布」が直接の観測量になり、現実の遅延データ(ODPT・D10)と突き合う。
門前条件の二重化(台帳に対応行のない実体は作れない=R1運用規則1)は**3レコード型すべてに適用**。

## 3. 実装原則(runB教訓の反映・大枠)

1. 全世界過程はSoA配列演算またはイベント駆動ハンドラとして書く(3z決定の適用)。
2. **状態成長の宣言を必須化**: 各過程の状態サイズは時間に対してO(1)(集約・リングバッファ)を原則とする。O(t)成長する状態(履歴・蓄積物)を持つ場合は、(a)成長宣言+(b)**読み出しがO(定数)である保証**(増分計算・索引)の両方が必須。——runBを殺した「未有界コーパス×読者ごと全再走査」の構造的禁止。
3. 世界状態への書き込み口は1本(答申原則5=resolve経由)。世界過程も例外にしない。

## 4. エンジン/LLM線引き——設計原則7本+16行表(実体)

### 原則7本(答申の採択・大枠承認の対象)

1. 不可逆な資源移動はエンジン(不足時は無効化+本人通知)
2. LLMの出力は「意図」まで。結果はエンジンが確定(resolve分離)
3. 算術・幾何・時間はLLMに触らせない
4. LLM出力は低次元に絞る——「量はスカラー、質は自由文」の二層出力
5. 一貫性は単一のボトルネックで作る(書き込み口はGM1本)
6. 裁定は必ず判例化してエンジンへ降ろす(2回目は決定論参照)
7. 意味付けと物語はシミュレートしない(言語化=LLM・記録=エンジン・解釈=観測者)
(補助8) 新規行動の追加はVoyager方式(LLMが規則を書きエンジンが実行)に限る

## 5. 憲法5の文言精密化(W③・草案)

現行: 「**知覚されない細部は作らない**」。判定が主観的なのが弱点。精密化の方向(案):

> 全ての細部・世界過程は、(a)少なくとも1つの**知覚契約経由でエージェントに届く**か、(b)少なくとも1つの**パターン照合または観測出力に寄与する**か、いずれかを宣言できなければ実装しない。宣言した届き先が消えた細部は、削除候補として台帳に自動的に載る。

= 「知覚されない」の判定を**宣言可能・機械検査可能**にする(v1教訓: 精緻な屋内SFM座標を知覚が一度も読まなかった、の構造的再発防止)。文言の確定は詳細詰めで。
