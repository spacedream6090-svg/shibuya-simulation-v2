## §1 事実(測って分かったこと)

- **環境の欄は状態のファイルの見出しにしか無い**。ランの manifest・checkpoints・テープの `run_meta.json` には無く、numba の版・git の commit・CPU の命令セット・依存の固定も無い。lock ファイルは無く `pyproject.toml` は下限だけ。golden の 4 つの辞書は環境で分けていない。
- **salt の道具は無い**。近いのは `seed_exchangeability`(seed 以外が同じかの検査)だが、既定 v3 の seed 1 と 2 で未説明の差が 313 欄(全部が観測の値・設定の差は 0)出て FAIL になる。1 本は 5,000 体 mock 1 日で 28〜30 秒。1 腕を基準と比べる直列の時間は 3 salt 2.9 分・5 salt 4.8 分・R-71 の 6 対 5.8 分・Holm で 5 指標の 8 対 7.7 分。CRN の最初の食い違いを毎 tick で探すと 1 本 75 秒。
- **seed を変えると母集団の抽出も変わる**(設計書 §5 の 3 本の根拠=salt 間 JSD は抽出の違いを含んだ値)。
- **AST の検査を外の状態に広げても、10d の漏れ 15 項目は捕まらない**。漏れの主因は軸 2(戻すのに要るか)で、読み手の AST では見えない。持ち主の外で読まれるのは 3 項目だけ。「`__init__` の外で書き換わる」規則なら 14/14 を拾うが候補 351(当たり 4%)。SoA の規則をそのまま当てると no/diag の 56 属性・235 か所が引っかかる(大半は結果の組み立ての読み)。走査は 0.8 秒。
- **K19**: 乱数の呼び手は AST で 31 か所、うち 16 か所は静的に語数が決まらない。実行時の計器(+7%・final 不変)で測った実際のブロックの重なりは、既定 v3 で `w16.sample.stratum` 185・`body.weight` 1・`body.eer` 1、counter ×1000 で `p_notice` 1,729。日の鍵の流れ(`delivery_inbound`)は 1 日のランでは重なりとして出ない。10c の検収の「372 層」は抽出が 2 回走るための流れの数で、実際の層は 186。
- **保存の形式**: 既定 v3 の日の境目の保存 4,302,954 B のうち配列が 92.5%。外の状態 169 道筋のうち、そのまま npz か json になるのは 152、型が落ちるもの 4、印が要るもの 11(集合・タプルの鍵・凍結した dataclass・Generator など)、値のクラス 2。試作の npz+json は非圧縮 +3%・**圧縮 −76%(1.03 MB・205 B/体)**、書き 17 ms・読み 11 ms(pickle は 4 ms・3 ms)。同じオブジェクトを 2 か所から指すものは 2 つ。pickle の先頭の行と sha256 は取り違えを止めるが、外から来たファイルの安全は守らない。
- **気づいたこと(直す候補)**: O75 の `flow_dir8`・`coherence` は軸 1 が behavior だが読み手 0 / `resume.py` の docstring と 10d の README の「sessions と _of_agent が同じ Session を指す」は今のコードでは当たらない(`_of_agent` は整数)/ T0>0 の反実仮想を再開の口で作ると設定の指紋が違って止まる(分岐の口が要る=CP の草案へ)。

## §2 着手の形(段の中の順)

1. **環境の欄**(K26 の答えに左右されない部分): `platform_fields()` を広げ(Python・numpy・numba・llvmlite・blake3・OS と版・machine・CPU の命令セット・numba の実際のスレッド数・git の commit と dirty)、正準の JSON の blake3 の頭 16 桁を `env_id` にして、manifest・状態の見出し・`run_meta.json` に同じ値を書く。既定のランの final・テープの中身は動かさない(欄が増えるだけ。byte-check は manifest を除く列で)。
2. **salt の道具**(K20〜K22 の答えの後): 「腕 × salt で回して差・幅・差 ÷ 幅」を出す道具。R-71 の手順を仕様に: 本数と出力の線(6 対から両側 α=0.05・5 対は片側で事前登録・足りなければ「記述のみ(本数不足)」)・ρ の実測(Var(D) と各腕の分散の比・5 対以上で読む)・D-46 の式の 2 通り(相対の標準誤差と 95% の半幅)・区間(t と並べ替えの反転・百分位ブートストラップは使わない)・効果の大きさ(生の差・比・差の SD・CRN の d_z と d_av)・多重比較(主要 1 つ事前登録・副次 Holm・探索 BH)・CRN の健全性(入力の一致・T0 前の behavior-hash 一致・最初の食い違いの tick=`first_diff.py` の再利用・A/A)。
3. **AST の検査を外の状態に**(K24): 軸 1 の AST(持ち主の外の読み・診断の出口の一覧・名前の衝突 52 は理由つきの許可)と、軸 2 の実行時の検査(「捨てて同じか」=discardable を新しいインスタンスの値に戻して以後の behavior-hash と呼数と診断の行が同じか)。
4. **K19 の検査**(K25): 実行時の計器(合成世界・率 ×1000・2 日)で「実際の重なり 0」と「用途名の許可の一覧」をテストに。静的に安全な 15 か所は AST で固定し、決まらない 16 か所の一覧が増えたら落とす。重なりの修正そのものは版上げ 1 回目(K19 の答え=10-06 §6)。
5. **保存の形式**(K23): npz+json(圧縮)。印は `__t`・`__s`・`__d`(鍵が文字列でない辞書=挿入順を保つ)・`__o`(許可したクラス名+欄)・`__nd`(配列の参照)・`__g`(Generator の state)。`np.load(allow_pickle=False)` と許可したクラスの表だけで組み立てる(読むだけでコードが動く経路を無くす=numpy の文書で一次確認)。読んだ値の形・dtype・鍵の型を台帳の宣言と突き合わせる。旧の pickle は読める口を 10e まで残す。
6. **小さな直し**(答えに左右されない): O75 の 2 属性の軸 1 を見直す(読み手 0 なら diag)/ docstring と README の記述の訂正 / 10c の検収の「372 層」に注。

## §4 試験(既知の答え)

- T1 環境の欄: 同じ環境で 2 回回して `env_id` と final が一致・`env_id` の欄を抜いた manifest は今と同じ(既定の byte-check は 19 構成で不変)。
- T2 salt の道具: 既知の 2 腕(差が分かっている合成の例)で、差・幅・差 ÷ 幅・ρ・p の下限が手計算と一致。3 本のときは「記述のみ」と出る。6 対で p の下限 2/64。
- T3 CRN の健全性: 入力の一致(設定の節だけ)・T0 前の behavior-hash の一致・最初の食い違いの tick が `first_diff.py` と一致・A/A が一致。
- T4 AST(軸 1): わざと外の状態の no の属性を挙動の場所で読むと落ちる。軸 2 の実行時の検査: わざと required を discardable にすると落ちる(10d の 14 項目のうち 1 つで再現)。
- T5 K19: 既定で実際の重なりが許可の一覧の中だけ・わざと 5 語目を引く呼び手を足すと落ちる。
- T6 保存の形式: npz+json で書いて読み、resume == straight(10d の試験)が全点一致・`allow_pickle=False`・許可の外のクラス名は拒否・旧 pickle も読める・大きさが 1.1 MB 以下(5,000 体)。
- 独立の検収(別のサブ): 実装を 1 か所ずつ壊してテストが捕まえるか・記録の数値の突き合わせ。
