## 1. 位置づけと決まっていること

本書は、時間のモデルについて決まっていない事項だけを問いの形に並べたものです。次の事項はユーザーが決めたので、問いません。

### 1-1 指示書 10-03 §7-5 で決まっていること

- モデルの時間は連続値にします。到着・発言・判断・購入は秒(ナノ秒)の時刻を持ちます。決定モデルや LLM はその時刻に呼ばれ、答えは「時刻+考えた時間」に世界へ反映されます。
- 規則はすべて秒で書きます(09-30 §0-2 の規律「時間に関わる確率・長さは秒あたり/時間あたりで書く」)。
- tick は計算の裏方として残ります。出来事を短い時間の窓ごとに集め、窓の中では時刻の順に処理します。まとめて計算する・同時の取り合いを公平に裁く・再現性・LLM をまとめて呼ぶ、のためです。
- 窓の幅が結果を変えてはいけません。窓を細かくしていっても結果が収束することを試験で確かめます。
- 同期は 10 秒以下を目標にします。全員に毎回かけている処理(スケジューラ・反映・知覚・変化の検出)は「出来事のあった人だけ」に作り直します。この作り直しは驚き駆動とカレンダーの作り直しとほぼ重なります。
- 場所や人ごとに別々の時計を持つ作り方(保守的な並列離散事象シミュレーション)を検討します。メッセージや電話は距離に関係なく届くので、先読み幅が小さくなる点は設計の問いとして残っています。
- 先に進めて過去の出来事が来たら巻き戻す方式(楽観的な方式)は、LLM の呼び出しが無駄になるので向かないと考えています(推測)。
- 計算量はランごとに記録します。LLM と決定モデルの呼び出し数、シミュ内の 1 時間ごとの実時間、GPU と CPU の使用量です。
- 呼び出しの上限をランの前に決めることはしません(D-110 のとおり既定は無制限)。
- 計算資源は設計の軸にしません(09-23 のユーザー方針)。必要な量は調達の必要量として扱います。

### 1-2 指示書 10-03 §7-6 で決まっていること(会話)

- 会話は、発言のたびに、その話し手の LLM を 1 回ずつ呼んで作ります。各発言は、その話し手の観測と内面だけから作ります。
- 会話の中は細かい時計で回します。1 つの窓の間に LLM を数回順番に呼び、会話の往復を窓の中で続けて回します。各発言にはシミュ内の秒単位の時刻(発言の長さと間合いから計算)を付けます。
- 会話の間も、世界の他の部分は普通に進みます。

### 1-3 ほかの節で決まっていること

- 10a で済んだもの(第318・IMPLEMENTED #80)。内部の時刻は通しの T(T = 日 × 1 日の tick 数 + tick)です。manifest に `tick_seconds`(既定 60)を記録します。日付・曜日・祝日は `start_sim_datetime` と T から現実の暦で引きます。応答の遅れは「発射+1 tick」で、旧い +2 は切替口 `--response-delay` に残しました([10a の記録](../bench/analysis/wallbounce-1003/10a/README.md) §0・§5)。
- 乱数の鍵は (T, 場所, k) です。k は、同じ時刻・同じ場所の事象を決まった順に並べたときの何番目かです(指示書 §3-2)。
- 決定論は用途で分けます。エンジンは常に決定論にします。受入の試験・腕の比較・反実仮想の比較は厳密モードで回し、長い観測のランは記録だけにします(指示書 §6 ⑨)。
- 物理の計算は CPU で行います。エンジンと LLM のクライアントは別のプロセスに分けます(指示書 §6 ⑩)。
- 予定はカレンダー型にします。1 回きりの予定は通しの時刻 T で保存し、繰り返しの予定は曜日と時刻の規則で保存します(指示書 §7-2)。
- 上の層を呼ぶかは本人(決定モデル)が判断します。エンジンのコードに残る判断は、System 1 の「そもそも決定モデルを動かすか(何か変化があったか)」だけです(指示書 §7-3)。
- 判断の頻度には範囲のグラデーションを持たせます。23 区にいる人は渋谷の外でも粗く判断し、遠いほど頻度が下がります(決定記録 09-25 §5.5 (a))。
- 要件の改訂記録 ③ に、創立時の「認知は事象駆動・一斉の tick は廃止」から 09-06 の「1 分の tick」を経て、連続時間の方向へ戻した経緯を残しました。

以下の問いは、この決まった形の中で、値や作り方が残っているものだけです。

### 2-1 重い問い

#### TM1 同期の形と、即時の通信の先読み幅

- 何を決めるか: 窓で揃える範囲を、全体にするか、区域ごとにするか。メッセージと電話のように距離に関係なく届く通信を、先読み幅の中でどう扱うか。
- 背景: 保守的な方式は、隣の区域から影響が届きうる最短の時間(先読み幅)まで先に進めます。先読み幅が 0 なら、まったく同じ時刻の事象しか並列に進められません(R-73 §2-1)。
- 選択肢(同期の形・R-73 §7-1 の表。どれも推測)
  - (a) 全体の窓で同期する。全事象を時刻印つきで持ち、幅 W の窓ごとに障壁で揃える。窓の中は時刻印順で、同時刻は決定的な鍵で裁く。先例は YAWNS・bounded lag・BEAM の窓・Repast HPC。実装が単純で、今の tick の構造に近い。会話の連鎖が窓を延ばすので、資源が無限でも下限がある(R-73 §6-4)。
  - (b) 区域ごとの別々の時計(保守的)。区域を単位にし、隣への先読み幅(歩く速さ×距離・声の届く距離・知覚の遅れ)まで先に進める。先例は CMB と AI Metropolis。会話の当事者だけが待つ。メッセージと電話で先読み幅が縮み、実装が重い。
  - (c) 混合。全体は窓 W で揃え、窓の中は区域ごとに順序を外す(依存の無い区域は待たない)。メッセージは配信の遅れを先読み幅として、窓の境界で配る。(a) の再現性と (b) の並列性を一部ずつ得る。窓の中の依存の判定が正しいかを試験する必要がある。
- 選択肢(即時の通信)
  - (d) 送る側の最短の遅れ(配信の遅れ・受け手が気づくまでの遅れ・呼び出し音の時間)を先読み幅に使う。最短が 0 に近いと効かない(R-73 §2-4)。
  - (e) メッセージと電話は窓の境界でだけ配る。窓の幅が配信の最短の遅れになる(R-73 §7-1 (c) の一部)。
  - (f) 草案の案(未リサーチ)。受け取りと「読む」を分ける。受け取りは窓の境界で配り、読む時刻は受け手の決定モデルが決める(指示書 §7-7「いつ読むかは受け手が決める」)。読むまでの時間が先読み幅の役をする。電話の着信のように無視しにくいものは (e) に回す。
- 材料
  - Fujimoto は「保守的な方式はどれも、十分大きな先読み幅があって初めて性能が出る」と書き、選び方として「良い先読み幅があり、それを使う手間が重すぎなければ保守的な方式が第一」とします(R-73 §2-1・§2-2)。
  - AI Metropolis は、距離と最高速度から依存を判定して保守的に順序を外し、全体同期より 1.3〜4.15 倍速かった。500 体の混む時間帯で 4.15 倍、1,000 体で 3.94 倍です(R-73 §3-2・◎)。
  - ns-3 は、全プロセスがほぼ全部つながっているときと、事象の無い時間が長いときは、大域の同期の方が有利と書きます。メッセージと電話でほぼ全員がつながる v2 はこちらに近い(R-73 §2-4・○・推測)。
  - 区域の中は細かく、区域の間は粗くする階層化の原典は見つかっていません(R-73 §8 の 3)。
  - 先読み幅の材料: 普通の声が届く距離は背景 45 dB で 3.2〜4.5 m、背景 75 dB で 0.6〜0.8 m(R-78 結論 2・推測)。予期した刺激への単純反応時間は 213〜231 ms(実読)、予期なしは 1.25 秒(二次)([知覚の時間の答申](../research/v2-perception-timing-research.md) 結論 10)。歩く速さは空間の段 1 で実際の値になります(空間の草案 3-10)。
  - 区域ごとの時計の下限は、1 日の中で最も長い「因果でつながった呼び出しの連鎖」で決まります。v2 の実データでの連鎖の長さは測っていません(R-73 §6-4・§8 の 15)。
  - 判断の頻度のグラデーション(決定記録 09-25 §5.5)は、遠い人ほど粗い時計で進む形で、区域ごとの時計と形が近い(本書の読み・未リサーチ)。
  - 物理は窓の中を dt 0.25〜0.5 秒で進める見込みで、40 万体で 1.3〜2.7 時間/シミュ日です(指示書 09-30 §1 P10・推測)。
- 影響する段と文書: 段 T1・T4 / 行動契約・知覚契約 / エンジンと LLM のクライアントのプロセス分離(指示書 §6 ⑩)/ 人と人のコミュニケーションの道具(指示書 §7-7)。
- 親推奨: (c) 混合(全体は窓で揃え、窓の中は区域ごとに依存の無いものから進める)。最初の版は (a) と同じ動き(窓の中の順序外しは無し)で始め、並列性は後から足す。即時の通信は (f)(受け取りは窓の境界・読む時刻は受け手の決定モデル)。(b) の純粋な別々の時計は、依存の構造が無いと下限を出せない(R-73 §6-4)ので実測の後。

#### TM2 LLM と決定モデルの呼び出しの置き方(考えた時間)

- 何を決めるか: 呼び出しを「依頼の事象」と「反映の事象」の 2 つに分けるか。反映の時刻(発射の時刻+考えた時間)の「考えた時間」をどこから取るか。反映の時刻が来ても応答が届いていないとき、誰が待つか。
- 背景: LLM の呼び出しは取り消せない操作に当たります(R-73 §2-3・推測)。Fujimoto は、入出力のような巻き戻せない計算は、その時刻が確定してから行うと書きます(R-73 §2-3)。R-73 §7-4 の案(親の案・未リサーチ)は、依頼の事象(時刻 t・誰が・入力の版)と反映の事象(時刻 t+考えた時間)に分け、その間は体に「考え中」の状態を持たせる形です。反映の時刻はシミュ内で決まり、応答が届いた実時間には依存しません。
- 選択肢(考えた時間の出どころ)
  - (a) LLM の実際の生成時間(計算機の実時間)を使う。計算機の速さで結果が変わる(R-73 §4-1 の読み・推測)。
  - (b) 今の認知設計書 §1 の表を秒のまま使う。L0 0 秒・L1 2.6 秒・L2 82 秒・L3 300 秒・L4(会話の応答)0.2 秒、換算は 0.04 秒/トークン(コードは `llm_bridge.py` の `LANE_SECONDS`)。今は tick へ切り上げているので、L1 も L4 も 1 tick(60 秒)になっています(棚卸し #41)。
  - (c) 認知の周期の錨から決める。ACT-R は約 50 ms、Soar の決定周期は約 100 ms(R-73 §4-1・◎)。周期×段数の形で、段数の錨は無い(本書の読み)。
  - (d) 草案の案(未リサーチ)。発言は TM3 の式(発言の長さ+間)で、判断は (b) の表で決める。どちらも計算機の速さに依存しない。
- 選択肢(届いていないとき)
  - (e) その体だけ待つ(区域ごとの時計なら、その区域だけ)。R-73 §7-4 の形。
  - (f) その窓全体が待つ。全体の窓(TM1 (a))ではこれと同じになる。
- 材料
  - ACT-R と Soar は、内部の処理時間をシミュ内の時刻として足し、外の計算機の時間とは切り離しています(R-73 §4-1・推測)。
  - 知覚の遅れと考えた時間を分ける提案があります。δ_total = δ_perc(きっかけの種類ごと)+δ_think(既存の表)です([知覚の時間の答申](../research/v2-perception-timing-research.md) 結論 10)。
  - 決定モデルの候補 Clef の遅延の中央値は 27B で 209.3 ms、9B で 38.8 ms です。これは計算機の遅延で、シミュ内の考えた時間とは別の量です。GPU の種類と同時実行数は記載が無く、原典は親未読です(R-73 §6-2・◎)。
  - 今の実装は、発射が非ブロッキングで、次の tick の頭で応答が全部そろうまで待ちます(1 段のパイプライン)。c7-day-4 では 1 tick 22.9 秒のうち LLM 待ちが 20.45 秒(89.2%)でした(tick と LLM の重なり §0)。
  - 応答の遅れ +1(10a)は tick の単位の値です。連続時間ではこの問いの「考えた時間」に置き換わります。
- 影響する段と文書: 段 T1 / 認知設計書 §1 の表 / 運用設計書 §2.4(δ_think を分の tick へ切り上げ)/ 10d の「出したが返っていない呼」の保存 / テープの鍵。
- 親推奨: (d)(発言は TM3 の式・判断は認知設計書の表=計算機の速さに依存しない)。(a) は厳密モード(⑨)と両立しない。届いていないときは (e)(その体だけ待つ)。

#### TM3 会話の内側の時計

- 何を決めるか: 発言の時刻を決める式(発言の長さ・間・話者の個人差)。1 つの窓の中で何往復まで続けて回すか。窓をまたぐ会話の扱い。
- 選択肢(発言の長さ)
  - (a) モーラ数×モーラ長。日本語の日常会話のモーラ長は平均 0.151 秒(約 6.6 モーラ/秒)、最速の話者 0.124 秒、最遅 0.198 秒です(R-73 §4-2・◎・石本 2024)。話者の個人差をこの幅から引く。LLM の出力の読みからモーラを数える道具が要る(R-73 §4-2・推測)。
  - (b) 草案の案(未リサーチ)。文字数から換算する。モーラと文字の比は表記で変わり、換算の錨は見つかっていない(R-73 §8 の 8)。
  - (c) 1 発話の長さを固定値にする。英語の電話会話の IPU は平均 1,680 ms・中央値 1,227 ms(R-73 §4-2・◎)。日本語の 1 発話の長さは見つかっていない(R-73 §8 の 7)。
- 選択肢(間)
  - (d) 日本語の値を使う。平均 +7 ms・中央値 0 ms(Stivers ほか 2009・R-73 §4-2・◎)。
  - (e) 10 言語の全体の値を使う。平均 +208 ms・最頻値 0 ms(同)。
- 選択肢(1 つの窓の中の往復)
  - (f) 窓の中に収まるだけ続けて回し、収まらない分は次の窓へ持ち越す(指示書 §7-6 の形)。
  - (g) 草案の案(未リサーチ)。(f) に加えて、1 つの窓の中の往復に上限を置き、上限に当たった回数を記録する。窓の幅を変えたときの差を TM4 の収束試験で見る。
- 材料
  - 同時に進む会話の数は平均 541.8 件です(390,067 体×2 回÷2×120 秒÷86,400 秒・R-73 §6-1 の再計算)。指示書 §7-6 は昼のピーク約 1,100 件、夜は数十件と見込みます(推測)。昼のピークは旧サーバーの効率の良い範囲(同時約 450 件)を超えます(指示書 §7-6)。
  - 全体の窓で同期すると、会話の発話の連鎖が終わるまで窓を閉じられません。1 発話の生成時間を L、発話の長さ+間を約 1.88 秒(英語の値を流用)とすると、実時間はシミュ時間の L÷1.88 倍より短くなりません(R-73 §6-4・推測)。

#### TM7 時刻の型と、乱数の鍵の単位

- 何を決めるか: 連続時間の時刻をどの型で持つか。乱数の鍵 (T, 場所, k) の T を秒の時刻に替えるか。

#### TM8 tick 単位の定数を秒に書き直す順と、既定の値の守り方

- 何を決めるか: 棚卸しの 45 行のうち、tick を変えると挙動が変わる定数(約 30 個)と、「分=tick」を前提にした箇所をどの順で秒に直すか。直す間、既定(1 tick=60 秒)の結果をどう守るか。

  - (c) (a) に加えて、意味の判断が要る 6 件(招待の返事の待ち #9・会話 1 ターン=1 tick #12・停車時間 #21・node 幾何の 1 tick 1 ノード #22・5 分ごとの間引き #38・艦隊の +2 tick #42)は別の短いアジェンダでユーザーに出す。

- 影響する段と文書: 段 T0 / byte-check の 19 構成(10a と同じ)/ 運用設計書 §2.4。
- 親推奨: (c)((a) の一括の秒化+意味の判断が要る 6 件は別の短いアジェンダ)。byte-check で既定の不変を確かめる。

## 4. 決めた後の作業の見取り図

TM6 の (b) の形(5 段)で書きました。各段の実装の前に詳細アジェンダを出し、ユーザーの答えをもらいます(CLAUDE.md §2-2)。

### 段 T0 下ごしらえ(既定は動かない・GPU 不要・10a〜10f と並べてよい)

- 時刻の型と乱数の鍵の単位(TM7)を入れる。SoA の列の型とバイトの増分を宣言する。
- tick 単位の定数を秒の定数+換算に直す(TM8)。「分=tick」の軸を直す。byte-check の 19 構成で既定が動かないことを確かめる。
- 計算量の記録の欄(TM9)を manifest と別のファイルに入れる。10f の環境の欄と一緒に作る。

### 段 T1 窓の導入(tick=60 秒のまま・既定は動かない・GPU 不要)

- 事象の待ち行列と、窓ごとの障壁を入れる。窓の中は時刻印順で、同時刻は (T, 場所, k) の鍵で裁く。
- 呼び出しを依頼の事象と反映の事象に分け、「考え中」の状態を持たせる(TM2)。
- 窓の幅が 60 秒のときに今と同じ結果になることを byte-check で確かめる。
- 収束試験の道具(TM4)を mock で作る。窓なしと W = 60・30・10・3・1 秒を同じ seed で比べる。

### 段 T2 会話の内側の時計と、窓を細かくする(既定が動く・版上げ・GPU 不要)

- 会話の発言に秒の時刻を付け、窓の中で往復を続けて回す(TM3)。会話の定数を秒の意味で決め直す。
- 既定の窓の幅を TM4 の結果で決め、収束試験を受入の試験にする。
- 版上げでは golden と呼数を張り替える。旧値を切替口で再現できるようにする。

### 段 T3 出来事のあった人だけ(既定が動く・驚き駆動とカレンダーの段と束ねる)

- スケジューラ・反映・知覚・変化の検出を、出来事のあった人だけにする(TM5 の順)。
- 体の変化は次に段を跨ぐ時刻を予約する形にするか、驚き駆動の中で行うかを TM5 で決めた形で入れる。
- 予算 P6 を再宣言する。決定モデルが入るまでは、System 1 の変化の検出が起こす数を記録する。

### 段 T4 別々の時計(既定が動く・GPU が要る)

- TM1 で決めた形(区域ごと・混合)で、先読み幅(歩く速さ・声の届く距離・知覚の遅れ・配信の遅れ)を宣言する。
- 全体の窓と結果が同じになることを、mock で全 checkpoint の比較で確かめる。
- 実 LLM で、全体同期に比べた速さと、1 シミュ日の実時間を測る(TM9 の欄)。費用の見込み(TM10)を実測で置き換える。
