# 再開の口(resume)と決定論の方針 — 設計書 v0.1(D-102・2026-09-28・第281・R-55 の事実で §4 を埋めた)

> 憲法との対応: 憲法1(打ち切り禁止)=再開はランの打ち切りを防ぐ道具・方法論「性能予算とバイト予算を先に宣言」=再開の状態台帳はバイト予算に載せる。

## §0 要約

- **決定論の方針(第280・ユーザー・確定)**: 必須=**同じ環境・同じ設定で、salt と LLM 応答(テープ)が同じなら同じ結果**。求めない=異なるマシン・スレッド数・GPU 間のビット一致。checkpoint は**プラットフォーム単位**で管理。受入=主要な腕の比較は**腕ごとに複数の salt**で回してばらつきを示す(本数は §5)。見直し=checkpoint のハッシュを**挙動に関わる状態+乱数の状態**に絞れるか(§4)。決定論にできない外部の道具(LLM・将来の物理)は**出力をテープに記録して再生**。
- **再開の口**: 最初の受入条件は **`resume == straight`**(途中で止めて再開したランと、通しで回したランの checkpoint が一致)+**consistency**(戻ったとき状態が正しい)+**completeness**(視野に入るべきものが入る)(R-41 Q8)。v1 の 5 型(未保存状態・二重発火・キャッシュ消失・未走査区間・締めの二重)を設計で潰す(§2)。
- **粒度**: まず**日境界**で再開(複数日ランの単位)、tick 途中の再開は後(§3)。
- **R-55 が見つけた複数日の障害 2 つ(再開の前に直す)**: ① **呼ごとの乱数・run_salt の鍵・call_id・テープの鍵に日番号が無い**(日内 tick だけ)=複数日を回すと**同じ tick・同じ体で毎日同じ乱数列を引く**。② **状態を持つ乱数が 2 本**(顕著行為・出動=`self.rng` を tick ごとに消費)=再開で作り直すと列の先頭から引き直す(二重発火の v1 型)。→ Q7・Q8。

## §1 決定論の方針(確定)と含意

| 方針 | 含意(設計) |
|---|---|
| 同じ環境・同じ設定・同じ salt・同じテープ → 同じ結果 | 「同じ環境」を manifest に書く: OS・Python・numpy/numba/blake3 の版・スレッド数(`NUMBA_NUM_THREADS`)・CPU の世代(型番は伏せ字可)。既定 checkpoint の版の台帳に**プラットフォーム欄**を足し、値はプラットフォームごとに持つ |
| 機種間ビット一致は求めない | 浮動小数の総和順序・並列化・GPU の非決定は**同じ環境の中でだけ**固定すればよい(スレッド数を固定して回す)。CI(別機)で checkpoint の一致を検査するテストは**同一プラットフォームの値**と比べるか、値の一致でなく「同 salt 2 回の一致」(自己整合)で検査する |
| 腕の比較は複数 salt | 「腕の差 > salt の差」を示す(§5)。1 本の checkpoint の一致は verification(内部整合)であって validation ではない(D-75 (b) の規律) |
| checkpoint を挙動の状態に絞る | §4。挙動に効かない欄(診断・計器)の追加で既定 checkpoint が動かなくなる=記憶の SoA 欄などを「腕でだけ確保」する摩擦を減らす |
| 外部の道具はテープで | LLM は既に (agent_id, tick, wake_class, prompt_hash) で再生。物理(D-122)を入れるなら**物理の出力(位置)も同じ形でテープに**=決定論の物理でも記録を残す(検証の材料)。記録量は R-53 §4 の見積り |

## §2 再開の口: v1 の 5 型に対する v2 の設計

| v1 の型 | v2 の設計(案) | 検査 |
|---|---|---|
| 未保存状態(15 件+5 族) | **状態台帳**: 状態を足すたびに「checkpoint に載るか / 再開で復元するか / 載せない理由」を 1 行宣言する口を `Registry.declare`(SoA)と Python 側オブジェクト(会話・顕著行為・活動文・繰り延べ・経済台帳・過程の状態)に用意する。Python 側は **tick 境界で配列か辞書に外部化できる形**(`to_state()/from_state()`)を契約にする。R-55 の表(§4)が初版の台帳 | `resume == straight`(mock 5,000・日の途中 3 点で止めて再開・checkpoint 一致)。**AST 検査**: `Registry.declare` 以外で `np.zeros(n_agents…)` を持つオブジェクトに `to_state` が無ければ失敗 |
| 二重発火(乱数の取り違え) | 乱数は**カウンタ型**(Philox・`stream(seed, name, tick, agent_id, …)`)=状態を持たない(R-55 で確認)。「その日すでに撃ったか」の印(内省 1 回・日次の締め・満了)は**状態**として台帳に | 再開後の乱数列が通しと一致(同 tick 同 name 同 agent → 同じ値)をテスト |
| キャッシュ消失で結果が変わる | 結果を変えるキャッシュは状態(例: 活動文・会話の拒否記憶)。性能だけのキャッシュ(艦隊の prefix cache・`eatery_mask` の遅延計算)は**再計算で同じ値**になることをテストで固定 | キャッシュを空にして再開 → 一致 |
| 未走査区間の消失(flush と進捗の不一致) | checkpoint の書き出しと**進捗の印(処理済み tick)**を同じファイル・同じ原子的書き込み(tmp → rename)で。日次の締め(センサス・T3・内省 M7・記憶の忘却)は tick 1439 の後・次の日の tick 0 の前に**1 回だけ**走る印を持つ | 締めの回数=日数 |
| 正常終了に重ねる誤用 | manifest に `finished: true` があれば resume を拒否。`parent_run` に親のラン ID と再開 tick を書く | 拒否のテスト |

- **consistency / completeness**(R-41 Q8・第256): 再開直後の観測(B2〜B6)が通しの同 tick と同じであること=`resume == straight` に含まれる。休眠(域外)から戻る体の状態が正しいこと(K9 の「食べたとみなす」も同じ検査に載る)。

## §3 複数日ランと再開の粒度

- **日境界の再開を先に**: 複数日ランは「1 日=1 ラン」を `parent_run` で鎖にする形で始める(いまの `run_day` を保ち、日の終わりに状態を書き、次の日は状態を読んで tick 0 から)。日をまたぐ状態=位置・活動・空腹(energy_balance の持ち越し)・所持金・記憶(エピソード・M17)・関係・在庫・経済台帳・W17 の消化位置。
- **tick 途中の再開は後**(落ちたランの救済用)。日境界が動いてから、同じ状態台帳で tick 境界に広げる。
- 予算: 状態の書き出し=SoA 全列(既定 127 B/体 → 記憶ありで ≤6.1 KB/体)+Python 側の外部化。39 万体で SoA 50 MB・記憶 2.4 GB(M4 の予算内)。書き出しは日 1 回なので壁時計への影響は小さい(実測は実装時)。

## §4 checkpoint の絞り込み(R-55 の事実・親検収)

### 4-1 いまの checkpoint(事実)

- `Checkpoint` = tick+ハッシュ 5 本(agents・world・population・schedule・activity)。**状態そのものは書かない**(`run.py:259-280,2426-2436`)。配列を保存する `save_registry` は tests からしか呼ばれない。
- `agents_hash` は**宣言順の全列**を混ぜ、`mechanism` タグで除外しない(`core/soa.py:382-399`)。**死蔵 3 列**(`plan_cursor`・`invocation_distance`・`wake_pending_class`=宣言以外に参照なし)も入る。
- **読み手未検出の列**(書くだけ): `band`・`age`・`sex`・`talk_partner`・`plan_activity`・`fail_streak`(agents)/ `open_count`・`b4_hash`(world)/ `last_b2_hash`・`last_b4_hash`(知覚)。※ `age`・`sex` は D-118(EER)で読み手が生まれる=分類は版ごとに更新。
- `world_hash` は cells 5 列+pois 9 列だけ。**挙動に効く状態の多くが SoA の外**(R-55 §4): 会話(セッション・拒否記憶・招待 TTL)・アービタの繰り延べ `_pending` と端数 `_pool`・変化検出の前回欄 `_prev_raw`(None なら全セル変化扱い)・保留中の応答 `pending`・鉄道の乗車数 `occupancy`・列の目的 `queue_action`・ホテル `rooms_occupied/bed_cell`・計画実行層の繰り延べ・金と物の台帳・ActualLog。**どれも checkpoint に混ざらず、ファイルに出る経路も無い**。

### 4-2 乱数(事実)

- 基本は**カウンタ型**(`stream(seed, name, tick, agent, …)` が毎回新しい Generator=状態なし)。**例外 2 本**: `SalientProcess.rng`(`world.salient`, day_index)と `PublicServiceDispatchProcess.rng`(`world.public_service_dispatch`, day_index)が tick をまたいで消費される。
- **呼ごとの流れ・run_salt の用途鍵(pk/ak/wk/wd)・call_id `f"{tick}:{a}:{cls}"`・テープの鍵 (agent_id, tick, wake_class, prompt_hash) に日番号が無い**。日単位の過程(salient・civic・goods_flow・logistics)だけ day_index を持つ。天気の種別と再生実日は seed から(`environment.py:194-197`)。
- numpy 2.5.3 の Philox は `bit_generator.state` を dict で取り出し・戻せる(R-55 [実行確認])。

### 4-3 案(親)

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **(a) behavior-hash を既定・full-hash 併記** | behavior=SoA の「挙動」列(R-55 §2 の判定・死蔵と読み手未検出を除く)+world の挙動列+**Python 側状態の外部化(`to_state`)のハッシュ**(会話・アービタ・変化検出・鉄道・列・ホテル・計画実行層・台帳)。full=全列(いまの値) | 診断列・死蔵列の追加/削除で既定が動かない(記憶の SoA 欄を腕に逃がす摩擦が消える)。再開に要る外部化と同じ仕事 | Python 側状態の外部化が要る(段階的に足す。足すたびに behavior-hash の版が上がる=版の台帳) |
| (b) 全列のまま | 現状 | 仕事ゼロ | 欄を 1 本足すたびに既定 checkpoint が動く(いまの摩擦) |

- **段階**(推奨): (i) SoA を挙動列に絞る(死蔵 3 列は削除・読み手未検出は除外)=**既定 checkpoint の値が変わる 1 回**(版の台帳)(ii) Python 側状態に `to_state/from_state` を足すたびに behavior-hash に加える(再開の実装と同じ順)(iii) full-hash は常に併記。

### 4-4 日番号と状態を持つ乱数(Q7・Q8)

- **Q7 日番号**: 複数日ランでは (day, tick) を鍵にしないと毎日同じ乱数列を引く。直す先=呼ごとの `stream(...)` の引数・run_salt の用途鍵の入力・call_id・テープの鍵(版 3)・天気の実日(day で進める)。**1 日ランの既定 checkpoint は day=0 で不変にできる**(鍵に day=0 を足しても値が同じになるよう、day を末尾の任意引数にする=実装で確認)。
- **Q8 状態を持つ乱数 2 本**: (a) カウンタ型に直す(顕著行為の発生は `stream(seed, "world.salient", day, tick)` を tick ごとに作る・出動は事象 ID を鍵に)/ (b) 状態(dict)を状態台帳に載せる。**(a) を推奨**(状態が減る・再開で二重発火しない・既定 checkpoint は動く=同じ回に束ねる)。

## §5 複数 salt の本数(提案)

| 用途 | 本数 | 根拠 |
|---|---|---|
| 主要な腕の比較(5,000 体・行動分布・実現量) | **3 salt/腕** | 行動分布の salt 間 JSD 0.00007〜0.00008 bits vs 腕の効果 0.05(AB7・第202)=効果が差の 700 倍。3 本で家族 95% が出せる(prereg v1.3 の形) |
| 希少な量(会話 25 件/日・未定義語・乗車)を主張するとき | **5 salt/腕** | 希少語の CV(n=2)0.08〜0.56(第202)。5 本で CV/√5 |
| 39 万体 | **3 salt**(D-46 の決定と同じ) | 在圏の salt 間 JSD 0.000162=H1 の線の 1/75(第204)。深夜 2% を言うなら 20 本(D-79)=言わない(記述に格下げ) |
| 同 salt の再現(verification) | 1 本 × 2 回 | `T2-a`(同 seed 同ハッシュ)。validation ではない |

> 〔注(10f・K21 (a)・2026-10-07 ユーザー決定・第326)〕salt は 10f から「動きの seed」を指す。母集団の seed(W16 の抽出・体の属性)と環境の seed(気象の再生実日・大きな催し・道路工事)は別に渡せ(`--population-seed`・`--environment-seed`)、省略すると salt と同じ値になる。上の 3 本の根拠(salt 間 JSD)は 10f より前の値で、母集団の抽出(5,000 体のとき)と、大きな催しの会場・道路工事の抽選のばらつきを含む幅である。気象の再生実日は影のある日への絞りで seed に依らず同じ日だった。39 万体の行は W16 の母集団 390,067 人のほぼ全数なので、抽出の揺れは小さい。10f 以後の salt の比較は既定で母集団と環境を固定し、動きのばらつきだけの幅を出す(`tools/c7/salt_runs.py --environment-mode fixed`)。環境も変える幅が要るときは `--environment-mode salt` で回し、どちらの幅かを報告に書く。入荷の抽選(`world.delivery_inbound`)は動きの側(エンジンの処理によるつなぎ)。本数の規則は K20 (a)=3/5/3 のまま・道具は本数が足りなければ「記述のみ(本数不足)」と出し、外に出す主張の前だけ 6 対(R-71)。記録: [10f の README](../bench/analysis/wallbounce-1006/10f/README.md) 第 2 段。

報告は「腕の差・salt 間の幅(家族 95%)・差÷幅」の 3 列。**salt の幅を超えない差は差と言わない**。
