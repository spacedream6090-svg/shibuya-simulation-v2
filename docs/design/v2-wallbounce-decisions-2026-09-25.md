## 2. 09-24 の 2 調査で増えた項(一覧 §4′)

### D-113 実装の欠陥 4 点 → ユーザー決定: 直す。1 欠陥 = 1 commit
4 点(パーサが未知ラベル「目標:」を対象値として読む/通報の前提「事象を知覚済み」が未検査/満席の列を捌くコードが無い/役割語が観測に無い)はすべてバグなので直す。直し方の条件は次のとおり。
- **1 欠陥ごとに 1 commit** にし、そのたびにモック 5,000 体の既定 checkpoint を記録する。どの修正で結果がどれだけ動いたかを、欠陥ごとに数字で残すため。

### D-111 空腹の設定(行動の 9 割の主因)→ ユーザー決定: (b) を主にし、(a) は独立ランにしない
- 事実(第263 の台帳): 空腹は全員が 30 tick ごとに +1 され、睡眠中も増え、上限 10、購入で −4 されるだけ(expedient)。そのため本人ブロック(B5)が一日中閾値を超え、行動の 9 割、理由の 88.5% が食事になっている。
- 壁打ち側の読み: 原因は LLM の好みではなく**エンジン側の作り**にある。空腹の閾値越えが LLM を起こす数少ないきっかけで、しかも起きたときの観測で個人的な情報が空腹くらいしかない。
- 決定: (b) 行動の駆動源を空腹から世界の過程(勤務・授業・営業時間・約束など)へ置き換える。錨の調査は GPU なしで今すぐ始める。第一候補は総務省の社会生活基本調査(生活時間)。
- (a) 感度の腕は独立したランとしては回さない。置き換えの前後比較が (a) の役割を果たすので、今の空腹駆動を旧版として残しておく。**余力があれば**、(a) を独立ランとして回すのも可(ユーザー)。
- 注意: 本格的な直し方は後半 §4・§5 の再設計そのものになる。(b) の錨調査はその再設計の材料として使う。空腹のパラメータだけを先にいじって辻褄を合わせるのは避ける。
- **追加の依頼(ユーザー決定)**: **起床のきっかけの内訳が何 % ずつか**を、既存ランの診断記録(アービタの起床クラス別の計数)から集計してほしい。新しいランは回さない。これは下のユーザー仮説の検証にもなる。

### ユーザーの仮説(D-111/D-112 の背景として)
ユーザー: 「System 1 のような軽いものから LLM で行う高度なものまで含めた、判断・思考の総量が足りていないから、このような結果になっているのでは」。
壁打ち側は、半分は正しいと返した。総量が足りないのは事実で、実測は 6.94 呼/人/日、目標は 10、D-101 のノートでも人の思考量には桁で届いていない。ただ、起こす理由が空腹に偏ったまま呼数だけ増やすと、空腹の支配はむしろ強まる。**判断が薄いことと、判断のきっかけが狭いことの掛け算**、という整理。上の内訳の集計が直接の検証になる。

### D-112 乗車・移動・降車・退去のずれ 4 点
- **① 観測にホームの手がかりを載せ、意図を落とさない → ユーザーの方針で直し方を変更**
  ユーザー: 「そもそも行動の更新の頻度が高すぎるのでは。**無理やり現実と整合するようにバグを直すのではなく、無理のない範囲でバグをなくすようにして**」。
  直し方: **一度決めた意図は、達成するか失敗するまで保持する。** 駅へ歩いている 28 tick の間に受動的な呼び出しが割り込み、意図が上書きされて消えている(第263 ③)。人は移動中に毎回ゼロから考え直さない。ホームや改札の手がかりは、**実際にそこにいる人に見えるものとしてだけ**観測に入れる。乗車率を現実に合わせにいく目的では入れない。
- **② 移動の行き先を「対象」欄から読む → 推奨どおり**(D-113 ① と同じ種類のバグ)
- **③ 降車を語彙から外す → 推奨どおり**。行き先を決めて乗った人は、着いた駅で自動で降りる。エンジン側(System 1)で済む典型例。

  ※壁打ち側は最初、④を「エンジンの退出と契約の退去のずれ」と説明したが、台帳を読んで訂正した。内容の最終確認は親がしてほしい。

  - 対象の候補: Generative Agents(Park et al. 2023)、AgentSociety(清華大・欲求で動く都市エージェントなので、空腹の問題に同じくぶつかっているはず)、Concordia、OASIS
  - 見る点: (1) 一度決めた行動の意図をどう保持し、いつ上書きするか (2) 空腹などの欲求がどれだけ行動を決めているか、偏りをどう防いでいるか (3) 退出や所属解除をエンジンと LLM のどちらが持つか
  - 読むだけ。実装は変えない。各リポの該当ファイルと行を引用して報告する。

## 3. 今の実装で「誰が何を決めているか」(壁打ち側が main のコードで確認した事実)

ユーザーの問い「エージェントの行動はシミュレーション側が決めている? それとも LLM や判断モデルがエンジンに提示される数値をもとに行動を規定している?」への答え。両方の混成で、役割が分かれている。

- **いつ街にいて、いつ来て帰り、いつ寝て起きるか**: エンジン。計画実行層(`engine/presence.py`・D-66)が W17 の在圏ブロックを読み、ブロック開始に間に合う最後の電車で到着させ(E1)、ブロックが終わると即座に退出させる(E4・受容関数を通さない)。ただし、もとの W17 の予定は LLM が本人として事前に書いたもの。
- **いつ考えるか**: エンジン。`engine/change_detect.py` が起床の候補(セルの描画の変化、内受容の閾値越え)を出し、`engine/arbiter.py` が平均 10 呼/体/日を目標に選ぶ。change_detect の docstring には「知人出現・近接入替・被注視・傍受は C2 では検出しない。内受容だけを第 1 陣として実装」とある。これは C2 時点の記述なので、今どこまで入っているかは親が確認してほしい。
- **考えたとき何をするか**: LLM。観測 B0〜B6 を読み、「理由(40 字以内)/行動(語彙 1 語)/対象/ひと言」で答える。
- **成功するか**: エンジン(権限・前提の検査、効果の書き込み)。
- **判断モデル(System 1.5・Jev のような層)は存在しない。** あるのは LLM(Qwen3-8B)か、その代わりのモックだけ。
- **本人ブロック(B5)の中身は、内受容・所持金・直近の行動・近接・被注視・傍受・広告だけ。** ペルソナも記憶も予定も入っていない。B1 は種別のみで、年代・性別は規約⑧のために外されている。ペルソナが使われているのは W17 生成の段階だけ。記憶(C10)の作業が main に入っていない commit にあるなら、親が補足してほしい。
- 入退場について、ユーザーの問い「範囲内への入場と退出はエージェントの判断で起きているという理解でいい?」への答え: **計画としては Yes、その場の判断としては No**。「もう少し居よう」「早めに帰ろう」と決める人はいない。会話中でも時間が来れば消える。さらに D-69 のとおり、ブロックの 48.4% は乗車の前に移動や支度から始まり、エンジンがそれも在圏と読むので、到着が中央値 40 分早くなっている。つまり入退場の時刻の一部は、エージェントの意図ではなくエンジンの読み方で決まっている。ユーザーの原則「存在はエージェント自身の思考・行動で決まるべき」(08-12)は半分しか実現していない。

## 4. 認知アーキテクチャの再設計(設計ラウンドとして扱う)

### 4.1 ユーザーの問題意識
- 「せっかくペルソナなどを与えているのだから、できることなら**悩むタイミングすらもエージェントが判断する**ようにしたい」
- 「**ペルソナや記憶などを決定モデルや LLM の出力に活かせないと、それを作成した意味がない**。W17 も Jev や LLM で簡単に書き換えられるようになるなら尚更」
- 「内省的な動機から熟考することも自分の経験ではあるから、それも検討したい」

### 4.2 LLM を起こす原理 → 仮決定: 驚き駆動(予測誤差)
- 経緯: 壁打ち側は最初、「LLM が考えるたびに『次に考え直す条件』を自分で書き、エンジンがそれを見張る」案を出した。ユーザーは「**次に考え直す条件を規定することは、想定外の状態に反応できないことと同義じゃない?**」と反論し、「**異常検知 Bot のように、想定外の出来事が起こった場合に Jev もしくは LLM を呼び出す仕組みにするべき**」と提案した。これは 08 月に確定していた「驚き駆動(予測誤差)LLM 発火」の再確認でもある。今の実装(描画ハッシュの変化と内受容の閾値)は、その粗い代用品にすぎない。
- 統合した形: **驚き = その人自身の予想からのずれ**。何を予想しているかは、カレンダー・記憶・ペルソナから作る。待ち合わせのある人にとって「友人が来ない」は驚きだが、予定の無い人には何でもない。心配性の人は小さなずれにも驚く。こうすると、ペルソナと記憶が「いつ悩むか」に効く。壁打ち側の「自分で書く条件」は、予想の一部として吸収する。
- ユーザーの確認「コードで機械的にエージェントの周りの状態に異常がないか検知し、異常を検知すれば Jev に回す、という理解でいい?」への答え: ほぼその通り。ただ、**コードが検知するのは「異常」ではなく「変化」**。コードは周りの何が変わったかだけを安く見る。その変化が**この人にとって**意外か・関係あるかは、本人の文脈が要るので決定モデルが判断する(同じ「雨が降り始めた」でも、傘を持っている人には変化、屋外で待ち合わせ中の人には異常)。
- **判断への入口は 3 つ**:
  1. 外の変化(コードが検出)
  2. 予定の時刻(カレンダーの予定が近い。コードで安く検出できる)
  3. 内側の圧力(内省・§4.5)
- 壁打ち側の提案(ユーザー異論なし・要確認): 話しかけられた、危険が迫った、のように**無視できない最低限のきっかけ**はエンジンが持ち、決定モデルを通さず必ず処理する。

### 4.3 階層 → 仮決定: 変化の検出(コード)→ System 1.5(決定モデル)→ System 2α(小 LLM)→ System 2β(大 LLM)
- ユーザーの構想: 「現状では異常検知 Bot のような判定をコードで行うのは難しそうだから、最初の入力から Jev などの決定モデルを使い、出来事を判別し、その上に小さな LLM と大きな LLM が載る構造になるかも。もし異常検知 Bot を Jev の出力などから NN を使って作ることができたら、System 1, 1.5, 2 の実装に移れる」
- 形:
  - **System 1(コード)**: 何が変化したか、予定の時刻が来たかを検出する。何も変わっていない人は上に通さない。39 万体の毎 tick を決定モデルに通すのは、安いモデルでも重いため。
  - **System 1.5(決定モデル・Jev 枠)**: その変化がこの人にとって意外か、関係あるかをペルソナ・カレンダー・記憶を踏まえて判断する。いつもどおりの場面なら行動もここで決める。**中身は差し替え可能な枠**として作る(09-25 の既定方針「Jev は差し替え可能な外部モデルの一つ」)。Jev が使えない間は、仮の中身(小型 LLM またはルール)で回せるようにする。
  - **System 2α / 2β(LLM)**: 決定モデルの確信度が低い、または初めての状況のときに上げる。どちらを使うかは場面の難しさで選ぶ。
- 注意: 旧設計の「門番(熟慮の判定器)」と「S(e) 引き上げスコア」は、System 1.5 の確信度による引き上げに吸収される見込み。
- **System 1 の中身は今後変わりうる**(ユーザー): 旧 T0 は「本人が熟考で自書した条件付き習慣」だったが、今回の決定ではその習慣が抜けている。習慣をどこに置くか(System 1 に戻すか、System 1.5 の既定行動として持つか)は設計ラウンドで決める。

### 4.4 異常検知 NN の育て方(壁打ち側の提案・ユーザーの構想の具体化)
「上位の層を呼んだ結果、行動が下位の層の答え(習慣や決定モデルの答え)から変わったか」をラベルにする。変わった場面は呼ぶべきだった場面、変わらなかった場面は呼ばなくてよかった場面。ランを回すほど教師データが貯まり、決定モデルの判断を NN に蒸留していける。**D-101 (iv)「学生の教師データの抽出口」はこのデータ源そのもの**なので、実装してよい(§7)。

### 4.5 内省からの熟考 → 仮決定: 入れる
- 外の驚きだけでなく、内側から考え始めることを入れる(ユーザー)。
- 壁打ち側の整理: 内省は**暇な時間**(電車の中・待ち時間・単純作業中)に起きやすく、引き金は**未完了のもの**(やり残した目標・気になる会話・明日の不安)。「暇な時間 × 内側の圧力」で発火させれば、外の驚きとぶつからない。
- 内省の出力は、その場の行動ではなく**カレンダー・目標・習慣の書き換え**にする。旧設計の「夜間に T2 が 1 日を振り返り、習慣を書き換える」は、この内省の一形態として含める。

### 4.6 ペルソナと記憶を判断に入れる → ユーザー決定(方向)
- LLM へ: 本人ブロック(B5)に、ペルソナの要約・関連する記憶・カレンダーを載せる。B0〜B4 に個人の語を置かない規約⑧はプレフィクスキャッシュのためのもので、B5 に入れるのは規約の範囲内。トークン予算(B5 220 tok)の見直しは要る。
- 決定モデルへ: ペルソナを短い特徴量として入力に含める。
- カレンダー(旧 W17)は、決定モデルや LLM が書き換えられる形にする。

### 4.7 モデルの選び方 → 仮決定(ユーザー「あまりわからない」・壁打ち側の推奨を採用)
- ユーザーの発想: 「System 2 の中を小さい LLM と大きい LLM の二階建てにするか、特定の 2 つのモデルと決めずに、複数のモデルの選択肢から選ぶ実装にしても面白いかも」
- 整理: 呼び出しごとにモデルを選び直すと、同じ人の「脳」が毎回入れ替わり、人格が一貫しない。そこで 2 軸に分ける。
  - **誰の脳か(人ごとに固定)**: その人に割り当てるモデルの系統。個人差の源になりうる。
  - **どれだけ考えるか(場面ごとに可変)**: 同じ系統の中で α(小)か β(大)か。
- 当面は **1 系統 × 大小 2 つ**。理由: (1) 今の画一性の主因はモデルの数ではなく、ペルソナ・記憶・性質が判断に届いていないこと。そこを直す前にモデルを増やすと、多様性の出どころが区別できない。(2) 憲法④「解像度は較正とペアでしか足さない」。(3) 検証が単純。
- ただし**作りは最初から複数系統に対応させる**。「この人の脳はどの系統か」を人ごとの欄として持ち、既定は全員同じにする。ペルソナや性質を入れた後に「2〜3 系統を人に割り振った腕」を回し、多様性が現実に近づけば採用する。
- 系統を混ぜるなら、どの人がどのモデルかを必ず記録する(開発元の癖が個人差に混ざるため)。
- D-101 (ii)(iii)・5-5(R16)はこの前提で決め直す。

### 4.8 多様性 → 次回の壁打ち候補(今は壁打ちしない)
- ユーザーの問い「多様性は今どこで発生している? LLM は人に比べ画一的な行動をとりやすいと聞いた」への答え: D-68 の診断のとおり、今の個人差は主に「温度 0.7 の揺らぎ」と「その場の状況」から来ていて、**個性ではなく雑音**。現実は「個人の中は規則的、個人の間は多様」なのに、シミュはその逆になっている。LLM が平均的な人に寄りやすいのも事実。一方、個人についての情報を厚く渡せば個人ごとの再現度が上がる(Park et al. 2024「1,000 人の生成エージェント」)。
- 多様性を生む場所: (1) 性質を数値で持つ(代謝・時間厳守・社交性・価格感度などを母集団の分布から引いて体ごとに固定。決定モデルの入力にもなる)(2) ペルソナと記憶を判断に入れる(§4.6)(3) 経験の積み重ね(馴染みの店・いつもの道)(4) 脳のモデル系統(§4.7)(5) 温度は個性にしない。
- 進め方: 先に**親が物差しで測る**(D-68 (0): 個体間の多様性と個体内の一貫性を、既存のテープと W17 で測り、現実の錨と比べる)。その数字を見てから短く壁打ちする。

## 5. 予定の再設計: W17 からカレンダーへ(設計ラウンドとして扱う)

### 5.1 ユーザーの問題意識(ほぼ原文)
- 「人によって、予定の前に余裕を持って待ち合わせ場所に着いたり、逆に時間ギリギリに来る人もいる。そんな感じでばらつきを持たせたいし、**ほとんどの意思決定をエージェントにさせたい**」

- 「エージェントの予定については**カレンダーのようなイメージ**を持っていた。毎朝スケジュールを考える人はなかなかいない。逆に、ある予定があるから今日はこんなスケジュールになる、ということの方が多い」

- 「**複数日を事前に決めておくのなら、それはシミュレーションを回す前に結果が決まってしまっている**状態にならない?」
- 「W17 は**人によって変更するコストが変化する**ようにしたい。その確率などはコードで規定しておくべき?」

### 5.2 カレンダー型 → 仮決定
- **カレンダー**: 一人ひとりが持つ、日をまたいで残る約束の一覧。例「火曜 14 時 渋谷で友人と待ち合わせ」「平日 9〜18 時 勤務」。各予定は、時刻・場所・相手・変更コスト(§5.3)を持つ。
- **予定が入る経路**: 会話で約束する、勤務の枠が決まる(§5.4)、習慣が固まる。どれもシミュの中の出来事から入る。
- **1 日の流れはその場で決まる**: 「14 時に待ち合わせがある」を見て、何時に家を出るかを本人が決める。早めに着く人とギリギリの人の差は、ペルソナ(時間厳守などの性質)とその場の判断から自然に出る。電車の遅れで遅刻する人も出る。
- **空き時間は空欄のまま**: 何をするかは、空き時間に入ったとき・何か起きたときにその場で決める(§4 の入口「予定の時刻」「外の変化」「内側の圧力」)。
- これで**渋谷に来ること自体が「家を出る」という本人の判断の結果になる**。入退場を計画実行層が機械的に行う今の形(§3)を置き換える。
- W17 の一括生成(親の予定していた「次回は 3 日版で一括再生成」)は**止める**。W17 に紐づく債務(D-63・D-68・D-69・D-101 の活動切り替え 8.9 回/日 vs 人 13.9 回/日)は、新しい設計の要件として引き継ぐ。D-69(域外語彙)は不要になる見込み。
- 壁打ち側の補足: 前の段階で壁打ち側は「毎晩翌日の骨格を書く転がし計画」を提案したが、ユーザーのカレンダー案のほうが現実に近いので置き換えた。

### 5.3 予定を変えるコスト(壁打ち側の提案・ユーザー異論なし・要確認)
- コストは「人」だけでなく 3 つの掛け算にする: **予定の種類**(勤務・授業・予約は変えにくい/昼食・買い物は変えやすい/空き時間はゼロ)× **人の性質**(きっちり守る人・気分で変える人。D-68 の「形質を状態に」)× **状況**(友人との約束は一人の予定より破りにくい)。
- ユーザーの問い「確率はコードで規定すべき?」への答え: **分ける**。
  - コードで持つもの: コストの構造と、予定を考え直すかどうかの閾値。雨・遅延・誘い・空腹などの圧力がその予定のコストを超えたときだけ上の層を起こす(§4 の驚き駆動と同じ仕組みの上に載る)。
  - コードで持たないもの: 「10% の確率で予定を変える」のようなサイコロ。設計者の恣意になるうえ、理由の無い変更になる。起きた後、変えるか・どう変えるかは LLM が決める。
  - 閾値の値は自分で決めずデータの錨から取る。分からない値は実験条件として記録する(ユーザーの 07-31 の方針「初期値そのものも実験条件として記録する」と同じ)。
- 計器: 計画実行層には**計画一致率(E9)**がすでにある。今は予定からずれる仕組みが無いので構造上ほぼ 100% のはず。変更の仕組みを入れた後の一番わかりやすい診断になる。

### 5.4 勤務・授業のような約束の作り方 → ユーザー決定: ③ を土台に、渋谷の中だけ ④
ユーザーは最初「コードとエージェントに考えさせるのとのハイブリッドが理想? よくわからない。いくつか案を出して」と言い、壁打ち側の 4 案を見て「**僕も君の案の通りの考えだった**」。
- ① 世界が与える(時間割・業種別の勤務形態をデータから)
- ② 本人が全部決める(LLM が自分の勤務時間を書く。現実の人はシフトを自由に選べないので不採用)
- **③ 枠は世界、中身は本人**: 固定勤務・フレックス・シフト制などの割合はデータから決める(厚労省の就労条件総合調査などが候補)。その枠の中で、何時に着くか・残業するか・休むか・どのシフトを希望するかを本人が決める。
- **④ 雇い主もエージェント**: 渋谷の中では店長エージェントが従業員のシフトを決める。「渋谷の範囲内は末端まですべてエージェント化」(08-09)の原則に合う。渋谷の外は ③。

### 5.5 判断のグラデーション → ユーザー決定: (a)
- ユーザー: 「Jev のような決定モデルが出てきたことで、これまでより比較的安く判断をさせられるようになったので、できるのなら全員に判断してもらいたい。ただその場合も、東京 23 区内は常時考えるが、その範囲を出たら判断を常時はしなくなるなど、範囲にグラデーションを持たせたシミュレーションにする方がいいかも」。これは憲法①「計算制約は打ち切りでなく LOD で吸収」の認知版。
- **(a) を採用**: 世界の細かさは渋谷 500 m のまま。23 区に住む人・いる人は、渋谷の外にいても頻繁に(粗く)判断する。遠いほど判断の頻度が下がる。世界そのものを 23 区まで広げる (b) ではない。
- 圏外の人が判断する中身は、家で何をしているかの再現ではなく、「いつ家を出るか」「空いた午後に渋谷へ行くか」のような渋谷への関わりに絞る(壁打ち側の提案)。
- **08 月の方針との関係**: 08-09 の「圏外滞在は朝の計画どおりに過ごしたとみなす(特徴的なイベントは発生させない)」「範囲外はルールとして回す」は捨てない。**グラデーションの最外周**として残す(ユーザー「8 月の案でも問題はないと思う」)。
- ユーザーの問い「この場合、範囲から出る際に予定を全て書くことになる?」への答え: カレンダー型なら不要。約束はもともとカレンダーにあり、範囲を出るときに新たに書くものは無い。範囲外にいる間は「カレンダーのとおり過ごし、特筆すべき出来事は無い」とみなし、外側ほど判断の頻度を下げる。

### 5.6 「複数日を事前に決めると結果が先に決まる」問題 → 整理
- 半分はその通り。**先に決まっていて正しいもの**(来週のシフト・授業の時間割。現実の人も事前に知っている世界の構造)と、**先に決めてはいけないもの**(空き時間の中身・どの店に行くか・誰と会うか)を分ける。
- 今の W17 はその区別なしに 1 日の全部を先に書いているので、在圏の曲線がほぼ W17 で決まる。KDDI と比べても、それは W17 の生成品質のテストにしかならない。
- カレンダー型では、事前に決まっているのは約束だけなので、この問題は解消する。複数日を回す前提として、D-102(再開の口)が要る(§7)。
