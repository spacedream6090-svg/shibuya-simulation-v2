# 3 段目 — 呼数の上限を無制限に(D-99 (a′)・D-110・2026-09-28)

> 正典: ユーザー決定 09-25([壁打ちの決定 D-110](../../../design/v2-wallbounce-decisions-2026-09-25.md) §D-110「当面は無制限を既定・上限スイッチは残す・ランごとの総呼数を必ず記録」)・[決定アジェンダ D-99](../../../design/v2-decisions-for-user-2026-09-24.md)((a′) 5,000 体も 39 万体も無制限を既定・L4 は監査線)・PENDING §2 の 3 段目。根拠の調査: [LLM 呼び出しが 7 回で止まる理由](../llm-calls-2026-09-24/README.md)(10 → 7.4 は L4 の均等割り+持ち越し 2 tick の expedient)。
> 実装: `cli.py`(`CLI_DEFAULT_L4_SCALE = 0.0`・`--l4-scale` の既定 0・`cli.run(l4_scale=None)`=既定 0・`fleet_queue_note`)・`engine/run.py`(`RunResult.l4_audit_fields`=manifest `llm_calls_total`/`llm_calls_per_agent_day`/`l4_line`/`l4_exceeded`/`l4_notes`・`RunResult.tick_seconds`)・`engine/arbiter.py`(`L4_LINE_PER_AGENT_DAY = 10`)。**上限スイッチ(`--l4-scale 1`/0.5/2)と従来の配り方(`call_budget_per_tick`・`POOL_CAP_TICKS=2`)は残した**。同じ回の小修正 3 件(§6)。資産・W10 の切替口は触っていない。
> 計測: [l4_measure.py](l4_measure.py) → [l4_arms15.json](l4_arms15.json)(15 腕 × {上限あり `x1`・既定=無制限}+照合腕)。mock 5,000 体・seed 1・1 シミュ日。

## 0. 結論

1. **CLI と `cli.run` の既定を呼数無制限にした**(`--l4-scale` の既定 1 → 0)。mock 5,000 体で呼は腕により **6.1〜8.2 → 9.9〜19.4 呼/体/日**(v3 既定 7.30 → **13.76**・帰無腕 8.23 → **19.41**)。15 腕中 13 腕が監査線 10 を超える(`l4_exceeded`)。
2. **`--l4-scale 1` は段 2c の checkpoint を 15 腕とも 1 バイト違わず再現する**(`x1` の final = 段 2c の検収値・テストで固定)。既定の golden は新値へ(帰無腕 `e0083baf` / 97,028・v3 既定 `a1036ab5` / 68,781)。
3. 無制限にすると**繰り延べ・昇格・縮退は 0**になり、代わりに**不応期の抑止**が 4 倍前後に増える(需要の天井が不応期で決まる=[調査 §(f)](../llm-calls-2026-09-24/sub_a_calls_and_usage.md) と同じ構造)。増えた呼は**場所の変化**(v1 既定 1.22 → 4.28 呼/体/日)と**体の状態**(1.84 → 3.09)が大半で、日課の切れ目はほぼ同じ(3.30 → 3.53=元々上限に当たっていない)。
4. 実 LLM の実測(AB8・語彙 v1・2026-09-20 の版)は上限あり 7.4 → 無制限 15.5 呼/体/日(発射)。mock の同じ形(v1 既定)は 6.7 → 11.4。**mock は実 LLM より場所の入口が少ない**(4.28 vs 7.02)・会話の番が多い(0.49 vs 0.05)=mock は行為を一様に引くので会話が 1/12(§4)。

## 1. 何を変えたか

- **既定**: `cli.CLI_DEFAULT_L4_SCALE = 0.0`(=1 tick の上限を体数に置く=AB8/AB6c の `l4_unlimited` と同じ経路=[IMPLEMENTED #38](../../../../IMPLEMENTED.md))。`cli.run(l4_scale=None)` は既定 0。`budget` を直に渡した呼び出しは従来どおり倍率 1.0 と載せる(予算が優先)。**ライブラリの `run_day(budget=None)` の既定は L4 按分のまま**(`--l4-scale 1` と同じ=切替口・単体テストの前提を動かさない=問い Q26)。
- **監査欄**(D-110「ランごとの総呼数を必ず記録」): manifest に常に `llm_calls_total`(発射数)・`llm_calls_per_agent_day`(÷ 体数 ÷ シミュ日数)・`l4_line`(10.0=`L4_CALLS_PER_DAY / L4_REFERENCE_AGENTS`)・`l4_exceeded`・`l4_notes`。上限ありのランでも同じ欄が出る。
- **艦隊 × 無制限の注記**(D-55): `--llm fleet` かつ `--l4-scale 0` で `--fleet-queue-capacity` が未指定なら、`RuntimeWarning` を出し `l4_notes` に「受理待ち枠は既定 N(max_in_flight×4)・1 tick の上限は体数・超えた呼は繰り延べ」と書く。**挙動は変えない**(偽 vLLM 2 本・300 体のスモークで注記を確認=`tests/c6/test_l4_l6_budget.py`)。
- 残したもの: `--l4-scale 1`(旧挙動)・0.5/2.0(倍率)・`arbiter.call_budget_per_tick`・`POOL_CAP_TICKS=2`・縮退(`DEGRADE_*`)。

## 5. 艦隊(実 LLM)で無制限を回すとき

- 繰り延べ 0 には `--fleet-queue-capacity` を**1 tick の最大の呼**以上にする(D-55)。mock 5,000 体の最大は 2,198(v3)/ 3,201(帰無腕)・既定の枠は `max_in_flight×4`(7 本の艦隊で 7×64×4=1,792)。39 万体は同じ割合なら 1 tick に 17 万呼の瞬間がある(=枠で受けきれない=繰り延べが出る。繰り延べは捨てずに再投入される=D-58)。
- `fleet_peak_in_flight_r*` は「受理=待ち+実行中」の数で、無制限のスモーク(300 体)では 150/レプリカ(L6=64 を超える)。実際の同時実行(偽 vLLM の `peak_concurrency`)は 40/33 で L6 の内。C6 の L6 検査はこの欄で合否を出しているので、無制限では誤って不合格になる(問い Q27)。上限ありの L6 スモークは `l4_scale=1.0` を明示した。

## 7. 問い

- **Q26(ライブラリの既定)**: CLI と `cli.run` の既定は無制限にしたが、`run_day(budget=None)` の既定は L4 按分のまま(テストの多くが `run_day` を直に呼び、`tests/c6/test_l4_l6_budget.py`・`tests/engine/test_mock_day_w2.py` は合成世界で「≤ 10 呼/体/日」を検査している)。`run_day` も無制限に揃えるか。
- **Q27(L6 の検査の欄)**: `fleet_peak_in_flight_r*` は受理(待ち+実行中)の数で、無制限では L6 を超える(実際の同時実行は L6 の内)。C6 の L6 合否を実際の同時実行(レプリカのセマフォの最大)で出すように直すか、欄の名前を「受理の最大」に改めるか。
- **Q28(艦隊の受理待ち枠の既定)**: 無制限では 1 tick に体数の 4〜6 割が呼ばれる瞬間がある。`--fleet-queue-capacity` の既定を「体数」にする(=繰り延べ 0 を既定にする)か、注記のままにするか。
- **Q29(ablation 表の古い腕)**: `tools/c8/ablations_v1.json`(凍結 SHA)の AB1〜AB7・AB6b の腕は `l4_scale` を書いていない=いま回し直すと既定の無制限で回る(AB8/AB6c は明示)。腕の定義を凍結のまま「上限ありで比べた記録」として扱うか、回し直すときは `l4_scale=1.0` を runner 側で重ねるか。
- 空欄: 実 LLM での無制限の呼数と入口(GPU 後)・39 万体の無制限の壁時計(D-99 の見積もり ≈ 21.5 h は AB8 の版の値)。
