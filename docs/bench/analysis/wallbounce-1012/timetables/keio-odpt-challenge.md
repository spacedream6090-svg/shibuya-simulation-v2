## 5. 版の宣言

- **JSON から分かること**: dc:date はどの表も `2026-07-03T14:00:00+09:00`(データの日付)。`dct:issued` は平日の表が 2025-03-17、土休の表が 2025-03-15(駅の時刻表 2 本・列車時刻表とも同じ)。
- **読み(推測)**: 2025-03-15 は土曜、2025-03-17 は月曜。2025-03-15 に始まった版の、最初の土休日と最初の平日の日付と読める。そうなら、2026-07-03 の時点で ODPT が出していた版は 2025-03-15 に始まったもの。
- **世界の時点(2026-07-13)との関係**: 2026-07-03 から 07-13 までに京王がダイヤを改正していなければ、同じ版が 07-13 にも有効(推測)。
- **京王のダイヤ改正日**: JSON には改正日の欄が無い。`dct:issued` が改正日そのものかは確かめていない。**空欄**。

## 6. W12 への取り込みの口(案だけ・コードは変えていない)

今の W12(`src/shibuya/build/field/w12_external_nodes.py`)は、メトロ 3 線の ODPT の駅の時刻表を `parse_metro_timetable` で読み、`w12_timetables.parquet` の列(`line, operator, direction, calendar, departure, departure_min, source`)に入れる。井の頭線は今、等間隔の expedient(上り/下り × 平日/土休)。実装は第 2 期(版上げ 2 回目)。

1. `路線` → `line`(「井の頭線」そのまま。`expedient_lines` から井の頭線を外す)。
2. `会社` → `operator`(CSV は「京王」、W12 は「京王電鉄」。写しの表を 1 行足す)。
3. `平日土休` → `calendar`(平日 → `Weekday`、土休 → `SaturdayHoliday`)。
4. `時`・`分` → `departure`(`HH:MM` に 0 埋め)。`departure_min` は既存の `_minute`(04:00 で切る。0 時台は 24 時台に)。
5. `方面` → `direction`。メトロの行は ODPT の向きの末尾(`Outbound` など)を入れているので、吉祥寺方面 → `Outbound` に写すと形がそろう。等間隔の「上り/下り」は消える。渋谷は終点なので、渋谷発は吉祥寺方面の 1 方向だけになる(今の expedient は 2 方向 × 380/580 本)。
6. `駅` → W12 に駅の列は無い(渋谷だけ)。渋谷の CSV 2 本だけを読み、神泉の 4 本は今は読まない(神泉を駅として持つかは odpt-check.md §5-2 の件と一緒に決める)。
7. `種別`・`行き先` → W12 に列が無い。足すなら列を新しく足す(今のエンジンの `world/assets.py` は `line, direction, calendar, departure_min` だけを読むので、足しても動きは変わらない)。
8. `版`・`md5`・`読み` → `source` を `real` か新しい値(例 `odpt_challenge`)に。md5 は W12 の入力の記録(frozen_sources に相当)へ。
9. 渋谷着の CSV → W12 には到着の表が無い。到着を使うなら新しい表(線・暦・到着の分・種別・直前の停車駅)を足す。直前の停車駅の発車時刻があるので、走る分も出せる。
10. 別の道: 渋谷の駅の時刻表の JSON は ODPT の形のままなので、`parse_metro_timetable` で CSV を経ずに直接読める(railway=`Keio.Inokashira`・direction=`Outbound`)。どちらの口にするか(CSV か JSON か)は親の判断。なお `direction` の値の集まりが変わると、エンジンの向きの番号(`didx`)が全線で振り直されるので、版上げの対象になる。
