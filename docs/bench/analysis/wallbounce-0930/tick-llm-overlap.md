# tick のループと LLM の重なり(指示書 §1-1 P10 の確認)

- 日付: 2026-09-30 / 実行役サブ(Opus 5.5)/ 親の検収前
- 問い(指示書 [v2-wallbounce-decisions-2026-09-30.md](../../../design/v2-wallbounce-decisions-2026-09-30.md) §1-1): 「tick のループが LLM の応答を待たずに進み、物理(CPU)が LLM(GPU)と重なって走るかをコードで確認して報告すること」
- 方法: コードを読んだだけ(ランは回していない・src/tools/tests は無変更)。行番号は HEAD 作業木の時点。
- 記号: 【事実】=コードか記録の逐語で確かめた/【計算】=記録の数値からの算術/【推測】=確かめていない見込み。

## 0. 結論(先に)

1. 【事実】艦隊経路では **発射(④)は非ブロッキング**で、エンジンは同じ tick の Phase A/B/C(移動を含む)と次の tick の前半へ進む。ただし本番の構成(`--fleet-wait-s 120`)では、**次の tick の ④′ で「実行中の呼が 0 になるまで」待つ**(`wait_idle`)。つまり「応答を待たずに進む」のは **1 tick 分だけ**で、tick ごとに同期の障壁がある(1 段のパイプライン)。
2. 【事実】したがって **「④ 発射 → 次 tick の ④′ 待ち」の間に置いた処理は GPU と重なる**。いまの移動(resolve の位置確定)はこの区間(⑦ Phase C)にあり、すでに重なっている。新しい物理を同じ区間に置けば、1 tick の物理時間が「LLM の 1 tick 分の処理時間 − 既に重なっている処理」以下である限り壁時計は延びない。
3. 【計算】c7-day-4(39 万体・実 LLM・1 日)では 1 tick 22.9 s のうち **fleet_wait が 20.45 s(89.2%)**。dt 0.5 s の物理 = 120 歩/tick × 0.028 s = **3.4 s/tick**、dt 0.25 s = **6.7 s/tick** で、どちらも 20.45 s の待ちより小さい。ただし昼夜で呼数が 20 倍違い、**夜の 1 tick の壁時計は記録が無い**(§2)。夜は隠れない可能性がある【推測】。
4. 【事実+推測】妨げは 3 つ: (a) 障壁が tick ごとにある(物理を tick をまたいで先行させる設計にはなっていない)、(b) **艦隊クライアントが同じプロセスのスレッド**(asyncio+httpx)で GIL を取り合う(c7-day-4 の movement 区間は壁 129.6 ms / CPU 31.3 ms=待ち割合 0.76)、(c) 物理の結果(位置・セル)を ② 変化検出と ④ 描画が読むので、物理は次 tick の ② より前に終わっている必要がある。
5. 【事実】副次の発見(直していない): 艦隊経路では応答は「発射 tick + 2」で適用される(mock は + 1)。§1-4。

### 1-1 待ちの設定: 既定と本番が違う

- 【事実】コードの既定は `fleet_wait_s=0.0`=純非ブロッキング(run.py:3959 `--fleet-wait-s ... default=0.0`・docstring run.py:1636-1640「本番(…1 tick ≈ 37 秒の壁時計)では LLM の往復(数秒)が 1 tick の壁時計に収まるので 0 でよい」)。
- 【事実】本番の実 LLM ラン(c7-day-4)は **`--fleet-wait-s 120`**(docs/bench/c7/accept_c7-day-4/layer2_review.md:25 の実行コマンド)。tools/c8/ablation_runner.py:504 も「`fleet_wait_s` は本番既定 120(D-26)」と書き、既定 120 で起動する(:730)。
- 【推測】0 のままだと、エンジンの 1 tick(c7-day-4 で待ち以外 約 2.5 s)が LLM の 1 tick 分(約 20 s)より速いので、応答は何 tick も後に届き、適用の tick が壁時計に依存する(=同じ seed で結果が変わる)。docstring の「0 でよい」は現状の本番の運用と合っていない(文書の食い違い・直していない)。

### 1-2 決定論の現状

- 【事実】適用順は到着順ではなく `apply_key` 昇順(run.py:2674-2675 `order = np.lexsort((ag, ak, ev_class, t_apply))`)。到着の tick は `t_apply = max(res.tick + δ_think, 到着 tick + 1)`(run.py:2914-2917)。
- 【事実(記録)】障壁 120 s でも、タイムアウト・キュー満杯の繰り延べがあると、どの呼が繰り延べになるかが時刻依存になり、同じ seed でも一致しない(D-54・docs/log/pending-archive-2026-09-28.md:108)。5,000 体・`fleet_wait_s 120` では bit 一致が実測されている(docs/bench/c8/ablation/ab8_s1_parent_report.md:8)。c7-day-4 は繰り延べ 14,798 呼(run_cli_summary.txt)。

### 1-3 mock 経路との違い

mock(`fleet_bridge is None`)は ④ で `bridge.call` を 1 呼ずつ**同期**で呼ぶ(run.py:3057-3098「逐次ループ宣言2: 選抜された呼数ぶん」)。応答は `res.t_apply` のまま `pending` へ入る。

### 1-4 副次の発見: 艦隊経路の応答は「発射 + 2 tick」で適用される(直していない)

- 【事実】① の適用(run.py:2666-2668)は ④′ の受け取り(run.py:2900)より**前**にある。④′ で受け取った応答は `max(t_apply, tick + 1)`(run.py:2916)で積まれる。
- 障壁 120 s の本番では、tick T に発射した呼は tick T+1 の ④′ で全部届く → `max(T+1, (T+1)+1) = T+2` → **tick T+2 の ① で適用**。
- mock は `t_apply = tick + δ_think`(llm_bridge.py:652/732)= T+1 で適用。
- よって**同じ構成でも mock と艦隊で応答の遅れが 1 tick 違う**(60 s tick なら 1 分と 2 分)。式そのもの(`max(tick+δ_think, 到着tick+1)`)は docs/design/v2-implementation-plan.md:681 に書かれているが、「本番では常に +2」という帰結を書いた記録は docs/ の grep(「T+2」「到着tick+1」「2 tick 遅」)では見つからなかった。tick を 10〜15 s にすると遅れは 20〜30 s になる。欠陥かどうかは親の判断。

## 3. いまの構造で、LLM 待ちの間に CPU の物理を回せるか

### 3-1 回せる範囲(事実)

- ④ 発射から次 tick の ④′ 待ちまでは、主スレッドは自由に計算でき、GPU はその間も動いている。いまの movement(resolve.py:1441-1483)も ⑦ にあるので**既に重なっている**。
- 【計算】隠せる条件: 1 tick の物理時間 ≤ LLM の 1 tick 分の処理時間 − 既に重なっている処理。c7-day-4 の平均では、待ち 20.45 s に対して dt 0.5 s の物理 3.4 s/tick・dt 0.25 s で 6.7 s/tick(§4)なので**平均では隠れる**。無制限の見積もり 21.5 h/日なら 1 tick 平均 53.75 s でさらに余裕がある。

### 3-2 妨げ

1. **tick ごとの障壁**(run.py:2896-2897)。物理は「次 tick の ④′」を越えて先へ進めない。夜のように 1 tick の呼が少ない tick では LLM 側が早く終わり、物理のほうが長くなれば壁時計が延びる【推測】(時刻別の記録なし)。
2. **GIL**。艦隊クライアントは同じプロセスのスレッド(fleet.py:853)。主スレッドの Python/NumPy の処理は GIL 待ちで遅くなる(movement の待ち割合 0.76 が実測)。numba の `nogil=True` の関数は実行中 GIL を放すので影響を受けにくい【推測: numba の文書の仕様。本件では未測】。リポ内では `engine/change_detect.py:26-28` が既に「numba nogil ループ」を使っている。
3. **状態の読み書きの順序**。物理が書く位置・セル・密度(resolve.py:1462-1480)を、次 tick の ② 変化検出(run.py:2781)と ④ 描画(run.py:3106)が読む。物理はそれより前に終わる必要がある。逆に、④ で描画に使った状態は ⑦ より前の値なので、発射した呼の中身は物理に依存しない(=重ねても LLM の入力は変わらない)。
4. **物理の中の決定論**。numba の `prange` は競合の保証文が無い(R-53 §3・docs/research/v2-r53-spatial-physics-engine-candidates-research.md:107)。engine_spike の核(tools/bench_spikes/crowd_physics_bench.py:55-87)は「全員の新速度を別配列に書く → 別ループで位置を更新」の 2 段で、縮約や原子加算が無いので**実際には**順序に依存しない形になっている【コード読み・未検証】。

### 3-3 選択肢(どれも未実装・親/ユーザーの判断用)

| 案 | 中身 | 壁時計 | 決定論への影響 |
|---|---|---|---|
| (A) ⑦ の中で小刻み | Phase C の移動を「dt ごとの小刻み × 120〜240 回」にし、numba `nogil`(+`parallel`)の核で回す。置き場所はいまの movement と同じ | 物理 ≤ LLM の tick 時間なら延びない。GIL は核の実行中は放す | **変わらない**: 物理は発射済みの状態を読まず、応答は従来どおり apply_key 順で次々 tick に入る。核の中は 2 段書き・格子の構築は逐次にすれば順序非依存【推測】 |
| (B) 艦隊クライアントを別プロセスへ | asyncio+httpx をプロセスごと分け、主プロセスとは待ち行列でやり取りする(docs/design/v2-implementation-plan.md:223 が「実装計画書 §4『httpx イベントループと計算の干渉。出たら LLM クライアントを別プロセスへ』」と既に条件として書いている) | GIL の取り合いが消える。主スレッドの描画(6.6%)と移動の待ちも縮む【推測】。プロンプト(平均 923.5 tok × 約 1,880 呼/tick)をプロセス間で渡す費用が増える | **変わらない**: 到着の順は今も非決定で、決定論は apply_key の並べ替えと障壁が担っている。障壁の位置を変えなければ同じ |
| (C) 物理を別スレッドで並走 | ⑥ の後に物理を nogil のスレッドで起動し、主スレッドは Phase C 後の層・checkpoint・次 tick の世界過程を並行に進め、② の直前で join する | 物理と主スレッドの残り処理(約 0.5〜1 s/tick)も重なる | **条件つき**: join までの主スレッドの処理が位置・セル・密度を読まない/書かないことを表で保証する必要がある。読むものがあれば(例: 世界過程の混雑場は位置を読む【推測】)順序が変わり結果が変わる |
| (参考) tick をまたいで物理を先行 | 物理を次の tick の応答を待たずに先へ進める | 障壁の影響を受けない | **崩れる**: 次 tick の意図は LLM の応答で決まるので、先行した物理は巻き戻しが要る。採らない前提で書いた |

補足【推測】: 障壁の後(④′ → ③ → ④ 発射)の約 1.65 s/tick(llm 1.51+arbiter 0.13)は GPU が空いている区間。描画を早く始めれば GPU の空きが減るが、本件の問いの外。

## 4. engine_spike の数値の出どころと再計算

### 4-1 出どころ(逐語で確認)

- 記録: docs/bench/engine_spike/README.md §2「群衆物理のスパイク(crowd_physics_bench.py・社会力モデル型・2m一様格子・numba並列)」の表「全40万体 | **0.028** | 格子構築0.021(単スレッド計数ソート)・力0.0075 | 0.67h/日 | **1.34h/日** | 6.7h/日」。
- スクリプト: tools/bench_spikes/crowd_physics_bench.py(存在を確認)。
- 条件(README 冒頭の逐語):「環境=ローカル機(Intel Core Ultra 7 265K・20コア・31GB・Windows 11・Python 3.12・NumPy 2.5・numba 0.67)。サーバー(64コア)はSSH不通のため未測(後日追記)。」→ **CPU のみ・GPU は使っていない**。「後日追記」はされていない(README に追記なし)。
- 体数: 400,000(スクリプト :13 `default=400_000`)。dt: 計測は `run(p, v, g, a.steps, 0.5)`(:103)=**0.5 s**。1 歩の時間は dt に依存しない(dt は積分の係数だけ)。平均は暖機 1 回の後の 10 歩(:14 `--steps default=10`)。
- モデルの中身(スクリプトから): 社会力型の簡略版(反発は半径 2 m の指数型・力 50 と速度 3.0 m/s で上限・目標は乱数の一定方向・**周期境界・壁/障害物なし・経路探索なし・階なし**・float32)。配置は 2% を 60 m 四方(2.2 人/m²)・10% を 300 m 四方(0.44 人/m²)・残り一様(README §2)。
- 「GPU 換算 6 分」は FLAME GPU 2 の粒子ベンチからの換算で、歩行者モデルの実測ではない(README §2 の注記・docs/design/v2-crowd-physics.md:17)。

### 4-2 再計算(指示書の「dt 0.25〜0.5 s なら 1.3〜2.7 h/シミュ日」)

式: h/シミュ日 = 秒/歩 × (86,400 / dt) / 3,600

- dt 0.5 s: 0.028 × 172,800 = 4,838 s = **1.34 h**(120 歩/tick・3.36 s/tick)
- dt 0.25 s: 0.028 × 345,600 = 9,677 s = **2.69 h**(240 歩/tick・6.72 s/tick)
- 390,067 体へ線形に縮めると 1.31 h / 2.62 h。

→ 指示書の 1.3〜2.7 h と**合う**。

| ORCA CPU オフィス 5,000 体 15.6 ms(#18) | 1,217 ms | 292 h | 58.4 h |
| engine_spike 40 万体 28 ms | 27.3 ms | 6.55 h | 1.31 h |

違いは 3 つが掛け算になっている【計算】:

1. **刻み**: 0.1 s は 0.5 s の 5 倍の歩数(864,000 歩/日 vs 172,800)。
2. **1 体 1 歩の費用**: ORCA(RVO2・KD 木+体ごとの線形計画・8 コア)は 8 ms/5,000 = 1.6 µs/体・歩(オフィスは壁つきで 3.1 µs)。engine_spike(簡略社会力・格子・20 コア)は 0.028 s/400,000 = 0.07 µs/体・歩。**23〜45 倍**。
3. **外挿の仕方**: ORCA は 5,000 体の値を 78 倍に**線形**に伸ばした[サブ計算]。engine_spike は 40 万体の**実測**。R-53 自身が「近傍探索の密度依存・LOD・スレッド数・世代の違う CPU/GPU を補正していない」と書いている(:123)。

→ 同じ 0.1 s で比べると 150〜292 h / 6.55 h = 23〜45 倍で、これは 2. の費用の差そのもの。食い違いではなく「別のアルゴリズム・別の刻み」の比較。**engine_spike の 0.028 s は壁・経路・階を持たない簡略核の値**なので、D 層(ナビメッシュ上の歩行・壁との衝突・縦の接続)を入れた費用は未測で、ORCA 側の値へどこまで近づくかは分からない【推測】。R-53 は「全組の next-hop 表は作れない前提で、1 回の探索の費用を実測」を未了としている(指示書 §1-4)。
