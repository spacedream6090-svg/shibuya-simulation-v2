## 1. Q57: 口コミの抽出が内心を読んでいないか

### 1-1 (a) 抽出が読む欄

- `src/shibuya/engine/wom.py:69-71`
  ```python
  WOM_TEXT_FIELDS = {"v1": ("comment",), "v2": ("comment",), "v3": ("reason", "target")}
  ```
  v3 の 5 ラベル(理由/行動/対象/活動/まで)のうち、読むのは**理由**と**対象**の 2 つ。行動・活動・まで は読まない。
- `wom.py:303-308` `utterance_text` は、上の表の欄を正規化してから `|` でつなぐ。「なし」の欄は捨てる。
- 呼ぶ所は `src/shibuya/engine/run.py:2529-2537`。**切り詰める前の逐語**(`raw_reason`)を渡している:
  ```python
  reason=str(getattr(parse, "raw_reason", "") or reason or ""),
  target=str(getattr(tgt, "raw", "") or ""),
  ```
- `_utter` は、**起床条件が会話ターン**の応答すべてで呼ばれる。行動の種類は問わない(`run.py:2890-2892`・`2922-2924`・`3095-3098`)。つまり会話ターンの応答で行動を「購入」にし、対象に店名を書いた場合も、その対象は抽出される。
- 設計の記録では、これは宣言済みの選択として扱われていた(`docs/design/v2-store-memory-implementation-agenda.md:27`「v3=理由欄+対象欄(発話本文が無い=Q57 のとおり薄い・宣言)」)。ユーザーの今回の定義(内心が聞き手に漏れる=欠陥)に従うと、これは欠陥になる。

### 1-2 (b) 宛先の店の記憶に伝聞として書かれる経路 → **ある**

- `run.py:2539-2542`:宛先=発話の前の `talk_partner`。それがセッションの参加者でなければ、最初の他の参加者。
  ```python
  if store_wom_on:  # 7c の腕: 口コミ off=抽出は数えるが転写しない
      wom_hear(mem_layer.store, agents, int(t_now), listener, ex)
  ```
- `wom.py:348-358` `hear`:聞き手の店の行に、出どころのビット `wom`(=2)、抽出で得た向き、重み 1.0 で書く。話し手の行には書かない。
- 聞き手の描画:`perception/renderer.py:230-235` と `perception/templates.py:263`。出どころが伝聞で向きが 0 でなければ「{store} は{valence}と聞いた。」、向きが 0 なら「X を知っている。」になる。

**実際に呼んだ結果**(合成の 3 POI:「一蘭 渋谷店」「スターバックス 渋谷店」(food)と事務所。話し手 0・聞き手 1。v3 の理由欄は「一蘭が混んでいたので別の店を探す」、対象は `P-1`):

```
v3 text read: '一蘭が混んでいたので別の店を探す|p-1'
extraction: (0,) ('一蘭',) valence -1 () ('混んでいた',)
v1 text read (comment only): '' -> ()
hear wrote rows: 1
 agent 0: sm_poi=[] ...                                   ← 話し手の行は無い
 agent 1: sm_poi=[0] sm_source=[2] sm_valence=[-0.25] sm_precision=[0.25]
 listener recall: RecallItem(row=128, ..., kind=12, obj=0, valence=-1, source=2)
 listener B5 item text: 一蘭 渋谷店 はよくないと聞いた。
```

話し手が内心で思っただけのこと(「混んでいたのでやめる」)が、聞き手には「よくないと聞いた」として届く。同じ入力でも v1 はひと言が空なので何も起きない。

**実データでの大きさ**(既存の記録・v3 の実テープが無いため v1/v2 のテープに v3 の規則を当てた代理。`docs/bench/analysis/store-memory-2026-09-28/README.md` 164-171 行):
- 会話ターンの呼のうち、理由+対象から店が取れたのは v1 10.7%・v2 16.5%。その**大半は対象欄=自分の行き先**だった。
- 向きつきは v1 97 件=0.09%。−1 の大半は理由欄の「営業時間外」(自分の失敗の理由)。
- Q78 の辞書では 2 件に減ったが、Q83 で「営業時間外」「閉店」を −1 に戻したので、いまの辞書ではまた増えているはず(**未再計測**)。

mock と classical の理由欄は定型文で店名を含まない(同 README 154 行)。したがって**現在の mock/classical の計測値には影響していない**。影響が出るのは実 LLM の v3 だけ。

### 1-3 (c) 会話の要旨として話し手の理由欄が聞き手の記憶に書かれる経路 → **無い**

- `memory.py:594-627` `note_utterance`:ひと言が空か「なし」なら、理由欄の先頭 40 字を要旨にする。書き先は `_put_gist(int(agent_id), int(rows[0]), ...)` で、**話し手自身**の (体, 会話の行) だけ。`record` の対象も `agent_id` 1 体だけ(606-610 行)。
- 想起は体 `i` の要旨だけを引く:`memory.py:408` と `496` の `self.gist.get((i, int(j)), "")`。
- 実際に呼んだ結果:`gist dict: {(0, 0): '一蘭が混んでいたので別の店を探す'}`。話し手の想起では要旨がこの文になり、聞き手の想起では `''`(要旨なし)。
- 付記(漏れではないが Q57 (d) と関係する点):話し手の B5 には「P-1と話した: 一蘭が混んでいたので別の店を探す。」と出る(`renderer.py:188-189`・`templates.py:257`)。**自分の内心が「話した内容」として記憶される**。Q57 (d) で「ひと言」ができたら、要旨の源はひと言だけにするのが筋。

### 1-5 直し方の案(実装はしていない・§8-1 の「切替口の腕の中だけ」に当たる)

## 2. §3-2 G: LLM を呼ぶたびに引いた記憶の行 ID がテープに残るか

### 2-1 いま残っているもの

- テープ版 3(`engine/tape.py:36-40`・`125`):列 `recalled_rows list<int32>`。中身は**その呼の B5「記憶」行に実際に載った**行番号。エピソードは 0..N−1、店の評価は N+行(`memory.py:204`・`504`)。チャネルや個体の予算で落とした項は入らない(`renderer.py:1885-1900`)。
- 書く経路は 3 つあり、どれも同じ値を渡している:同期ブリッジ `engine/llm_bridge.py:790`、艦隊 `run.py:3127` → `llm/fleet.py:1800`(応答行)、`fleet.py:1836`(繰り延べ行)。
- classical も `LLMClient` としてブリッジを通るので、描画 → 想起 → `recalled_rows` が残る(`engine/classical.py` 冒頭「クライアントの 1 つ」)。ただし classical は描画を読まないので、「判断に使った」わけではない。
- 集計:`MemoryLayer.recall_stats`(入口別の件数)と manifest の `memory_summary`。行 ID は持たない。

### 2-3 (c) 追い出しの後の一意性(実際に呼んだ結果)

N=2 の表に 4 件を書き、書くたびに想起した結果:

```
tick 0   buy obj=5 -> slot [0] | obj=[5, 0] first=[0, 0]     evictions=0  recall rows: [(0, 5)]
tick 10  eat obj=6 -> slot [1] | obj=[5, 6] first=[0, 10]    evictions=0  recall rows: [(1, 6), (0, 5)]
tick 500 buy obj=7 -> slot [0] | obj=[7, 6] first=[500, 10]  evictions=1  recall rows: [(0, 7)]
tick 900 eat obj=8 -> slot [1] | obj=[7, 8] first=[500, 900] evictions=2  recall rows: [(1, 8)]
```

テープ上は同じ「行 0」でも、tick 1 の時点では店 5 の購入、tick 501 の時点では店 7 の購入を指す。追い出しは `memory.py:527-533` の `argmin(score)`。統合(同じ鍵の反復)では同じ行の `mem_n` と `mem_last` が増えるが、`mem_tick`(最初の tick)は保たれる。したがって、**(体, 行, 最初の tick)** があれば、ほぼ一意に「どの記憶か」を指せる。例外は、同じ tick の 2 回目の書き込みで、同じ tick に作った行を追い出した場合。これは体あたり 1 tick に 2 件以上の事象があり、しかも表が満杯のときに限られる。種類と対象を足せば、この例外もなくなる。

### 2-4 足すとしたら(案・実装はしていない)

**案 G1(推奨)テープの列を足す=版 4**(LLM の呼ぶたびに引いた記憶を一意にする):
- `recalled_rows` と同じ順・同じ長さの並列リストを足す:
  - `recalled_first list<int32>`:エピソードは `mem_tick`、店は `sm_first`。
  - `recalled_kind list<int8>`:エピソードの種類、店は 12。
  - `recalled_obj list<int32>`:エピソードは `mem_object`、店は POI。
  - `recalled_partner list<int32>`:エピソードは `mem_partner`、店は −1。
  - 4 つ合わせて 1 項 13 B。1 呼の項は最大 3(会話 3・それ以外 2)なので、**圧縮前で最大 39 B/呼**。記憶が off のランは空リスト。
  - (体, 行, first, kind, obj) で一意になる。§2-3 の同じ tick の例外も種類と対象で分かれる。
- `near_acq list<int32>`:B5 近接行で「(知人)」を付けた相手の id。辺は (体, 相手) で一意。辺の世代まで区別したいなら `near_acq_first list<int32>`(`rel_first`)も足す。関係 off のランは空。
- 作り方:`RecallItem` に `first_tick` を足す(既定値つき・描画は読まない)。`Rendered` / `RenderedPrompt` / `LLMCall` / `TapeRow` に並列の欄を通す。`_acquaintances_of` の結果のうち、近接行に載った分を `Rendered` に返す。
- 版上げは**要る**:スキーマの metadata を `shibuya.tape/4` にし、`CALLS_SCHEMA_V4_DEFAULTS` で旧テープを空リストとして読む(版 3 と同じ流儀=`tape.py:136-139`・`402-407`)。リプレイの鍵(agent_id, tick, wake_class, prompt_hash)は変えない。
- 注意:既定のラン(記憶 off)でも**テープのファイルには空の列が増える**。これまでの記録にある「テープ全列が HEAD と一致」の検査は、旧い 14 列で比べる形に直す必要がある。§0-1-4 の「版上げ 1 回に束ねる」の対象にするかは親の判断。

**案 G2 判断の記録(テープの外・エンジン側の判断)**:古典の想起優先・習慣の候補・招待の相手の選択は LLM の呼ではないので、テープ(1 呼=1 行)には乗らない。§3-2 D の「習慣由来か LLM 由来かを必ず記録」と同じ置き場にするのがよい。例えば `decisions.parquet`:
- 列:tick・体・種類(store_choice/habit/invite)・結果(POI/相手)・決め手・使った行の (表, 行, first)。1 行あたり約 30 B。
- 件数(1 日の店選びと招待の回数)は**未計測**。

**挙動が変わらないことの確かめ方**(G1・G2 とも):
1. 描画のバイトが変わらない=`prompt_hash` 列が同じ。
2. mock 5,000 体・v3・`--memory on --store-memory on --relations on` のランで、HEAD(git archive)と作業木の旧 14 列・state_hash・final・manifest(新しい欄を除く)がすべて一致する。既存の記録と同じ手順で行う。
