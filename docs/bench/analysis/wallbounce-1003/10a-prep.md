## 0. 結論

1. **B5・B6 の本文は 1 呼あたり平均 567 B**(既定の腕。B5 344 B・B6 223 B)。記憶・関係・店の記憶を ON にした腕では **671 B**(B5 が 448 B に増える)。プロンプト全体(平均 5.2 KB)の 11〜13%。
2. **5,000 体 1 日の増分**: 生のバイトで 39.7 MB(既定)/ 48.9 MB(記憶 ON)。テープと同じ zstd で calls に 2 列足して書き直すと **+1.59 MB(既定・今のテープ 4.47 MB の +36%)/ +2.85 MB(記憶 ON・+60%)**。1 呼あたり +22.8 B / +39.1 B。
3. **39 万体への外挿(推測)**: 呼数を c7-day-4 の 2,706,593 回/日とすると、zstd で **+62 MB/日(既定)/ +106 MB/日(記憶 ON)**。c7-day-4 の calls.parquet 187.7 MB の +33% / +56%。1 呼あたり 87〜104 B で、宣言の `TAPE_ROW_BYTES` 400 B と上限 5 GB/日の内側。
4. **暦を引いている箇所は 24 か所**(§2-2 の表)。今は全部 `day_index`(0=月曜の約束)か固定の値から引いていて、祝日を見ている箇所は 1 つも無い(W13 の構築の手書きの祝日 2 行と、W7 の構築が `PH` を捨てる箇所だけ)。
5. **食い違いを 2 つ見つけた**(直していない): (i) 既定のランは曜日の計算では「月曜」(`day_index=0`)なのに、プロンプトの日付と天気は 2026-07-28(**火曜**)。(ii) 天気の実日の候補(W13)は 2026-07-28〜08-31 の 35 日だけで、**全部が東京の公立学校の夏休みの中**にある。指示書 A1-3 の「学校の長期休みは開始日に選べない」と、今の天気の実日ブートストラップは両立しない(§2-4)。
6. **内閣府の祝日 CSV の取得は成功**(cp932・1,067 行・1955/1/1〜2027/11/23・md5 `733fabb6b488794a0cd3d94df4b1f24a`)。
7. **応答の遅れ**: 艦隊からの受け取りと待ち(`run.py:3027-3050`)は、反映(`run.py:2784-2800`)より後にある。受け取りを反映の前に移し、同時に下限 `max(t_apply, tick + 1)` を `max(t_apply, tick)` に変えれば +1 になる。位置だけ移しても下限が `tick + 1` のままなら +2 のまま(§3)。

## 1. テープ版 4 に B5・B6 の本文を入れる件の容量

### 1-1 今のテープ(版 3)の形

`src/shibuya/engine/tape.py:91` で `TAPE_SCHEMA_VERSION = "shibuya.tape/3"`。ファイルは 2 本(どちらも zstd・`tape.py:85`)。

**B5・B6 が入っていない理由**: `llm_bridge.py:146-149` の `SHARED_BLOCK_IDS = BLOCK_IDS から B5・B6 を除いたもの`(コメント「B5/B6 は個体依存なので intern しない」)。アダプタは `llm_bridge.py:345` のループでこの 6 本だけを `RenderedPrompt.blocks` に入れ、テープは block_ids にその id を書く。B5・B6 の本文はどこにも書かれない。したがって今のテープからはプロンプト本文を組み直せない(prompt_hash の照合だけができる)。

### 1-2 測り方と限界

- `shibuya.cli.run`(mock・5,000 体・seed 1・1 シミュ日・テープつき)を 2 腕回した。既定 = `vocab_version=v3, activity=True`(w6_regen_measure の `v3_default` と同じ呼び方)。記憶 ON = それに `memory=on, relations=on, store_memory=on`。
- B5・B6 はテープに載らないので、**このプロセスの中でだけ** `PerceptionRendererAdapter.render` を包み、知覚側の `Rendered.blocks["B5"]`・`["B6"]` のバイト列を描画ごとに控えた(src は編集していない。包みは値を読むだけ)。再描画ではなく**全呼の実測**(サンプリングなし)。
- 包みが挙動を変えていないことの確認: 既定の腕の final `993276d5e5bb5cbe`・呼数 69,978 は現行の golden(v3 既定)と一致。記憶 ON の腕は final `1e28c8ce3f80d888`・72,930 呼(比べる golden は無い)。
- 描画の回数と calls の行数は両腕とも一致(69,978 / 72,930)。mock は繰り延べが無いので 1 描画 = 1 行。艦隊では繰り延べ行(応答なし)にも B5・B6 を書くかどうかで数が少し変わる(c7-day-4 で繰り延べ 0.55%)。
- 圧縮後の大きさ: calls.parquet を読み直し、B5・B6 の 2 列を末尾に足した表と足さない表を、同じ pyarrow の既定の水準で zstd と gzip に書いて差をとった。
- 限界: (i) 1 seed・1 日・5,000 体だけ。(ii) mock の応答と本番の応答は違うので、B6「直前の結果」の文面の分布が本番と違う可能性がある。(iii) 39 万体では行グループが大きくなるので、1 呼あたりの圧縮後の増分は同じか少し小さくなると見込む(推測・測っていない)。

## 2. 通しの時刻 T と暦

### 2-1 時計と manifest の今

- `src/shibuya/engine/clock.py` の `SimClock(start_sim_datetime, tick_seconds=60)` は `to_datetime(tick)`・`ticks_per_sim_day` などを持つが、**エンジンからは使われていない**(src で `SimClock` を import しているのは `engine/__init__.py:18` だけ)。
- manifest の型 `manifest/schema.py:173-181` の `Settings` には `tick_seconds`・`n_agents`・`sim_days`・`start_sim_datetime` の欄があるが、**ランが書く manifest の欄(`run.py:920-` `run_manifest_fields`)には入っていない**。入るのは `replay_date`(天気の再生実日)だけ。
- 世界内の日時は `run.py:2319-2326`: `start = DEFAULT_START_DATETIME + day_index 日`、天気の再生実日があればそれに置き換え、`clock_fn(t) = start + t 分`。`DEFAULT_START_DATETIME = 2026-07-28 00:00`(`perception/renderer.py:131`)。`clock_fn` は `tick_seconds` を見ていない(tick = 分の前提)。
- 曜日は CLI の `--day`(`run.py:4141`「曜日(0=月曜)」)= `day_index`。日付とは別に持っている。

受け取りと待ちを tick の頭(① の前)へ移すと(5 行):

1. tick T に発射した呼は、tick T+1 の頭で待って受け取られ、`t_apply = T + δ_think = T+1` がそのまま `pending` に入り、**同じ tick T+1 の ① で反映される**(今は T+1 の ④′ で受け取り、下限 `tick + 1` で T+2 に回る)。
2. ただし**下限 `max(t_apply, tick + 1)` を `max(t_apply, tick)` に直す必要がある**(`run.py:3015,3047`)。位置だけ移して下限を残すと +2 のまま。旧い実 LLM テープ 17 本の再生のために、下限(`tick + 1`)と位置を切替口で残す(テープの `observed_tick` は「受け取った tick」のままで意味は変わらない)。
3. 受け取りの時の会話の発話 `_utter`(`run.py:3021-3023,3053-3055`)と繰り延べの再投入の準備も tick の頭へ移るので、会話の発話が同じ tick の ① より前に記録される順になる(会話ターンの起床候補 `run.py:2984-` より前)。順の変化が会話の記録の tick を動かすかを試験で確かめる。
4. LLM と重ねられる区間は、今の「発射(④)→ 次の tick の ⓪a・⓪・①・②・起床候補」から、待ちの位置より前の分だけになる。待ちを ⓪ の後・① の直前に置けば失うのは ①・②・起床候補だけ、本当の頭(0 の前)に置けば世界過程と知覚の前計算も失う(c7-day-4 の内訳は [重なりの記録 §2](../wallbounce-0930/tick-llm-overlap.md))。指示書の「全体で 1〜2% 遅く」は推測のまま。
