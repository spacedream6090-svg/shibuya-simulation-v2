## 4. 欠陥

### 高

**高 1 判断モデルの短い版に所持金・空腹・記憶が入らない。影響が自己申告より大きく、(G) も同じ短い版で回る**
- 自己申告は「短い版に B5 が入らない」まで。検算すると、44 件の全部で所持金(B5 所持)が短い版に無い。空腹・のどの渇き・疲れ(B5 内受容)は 21 件、記憶(B5 記憶)は 12 件で抜ける。12 件の内訳は what_how_many 5・price_skip 7。price_skip の 11 件中 7 件は、比べの手がかり(前に払った値段か事情)が短い版から消える。
- 値段(B2 値札)は短い版に入る。だから price_skip の短い版で比べられるのは、絶対の値段の高い・安いだけになる。所持金に対する割合(例: price_skip-07 は所持金 2,000 円に対して 1,800 円・-10 は 800 円に対して 600 円)は見えない。revisit の満足の手がかりは B6 結果にあるので短い版にも入る。
- `cli.model_factories` の (G)(`--vllm-*`)と候補(`--hf-*`)は、どちらも `LogprobChoiceScorer` の既定 `length="short"` で作られ、長さを選ぶ引数が無い。8B の logprob の基準も、住人の 8B が実際に読む長い版ではなく短い版で回る。一致の列は「同じ欠けた入力の上での一致」になる。
- 長い版を Choice の形で読むと、文の末尾の指示「先に理由を自由に書き、最後に番号」と、直後の「答え: 」+番号の logprob が食い違う。長い版にすれば済む話でもない。
- engine の `port.compose` の短い版は PS+B6(PS は人物の文)で、状態(所持金・空腹)の欄は無い(src/ を読んで確認)。tools の中だけでは直せない。
- 再現: `S.load_scene_file()` の各場面で `S.render(s, pres, length="short", arm="t1000").text` に「所持金」が無く、「[B5 記憶]」の行は長い版にしか無い。試験 `test_consumption_render_short_and_long` もこの形を固定している。
- 案(親の判断): (a) 場面の側で所持金と比べの値段を B6(契機の文)か B2 に置く(engine のブロックの約束から外れる) (b) DM4 の短い版に状態の短い欄を足す(src の変更=実装の停止の外) (c) 消費の場面だけ、(G) と候補を短い版と長い版の両方で回す腕を足す。

### 中

**中 1 古典の当て口の分布が提示の並びで変わる(同じ kind の候補が 2 つ以上ある場面)**
- `judge.ClassicalScorer._score` の `by_kind = {c.kind: c.id for c in candidates}` は、同じ kind の候補が複数あると、提示の並びで最後の候補に kind の質量を全部置く。evalset(13 語が全部別の kind)では起きないが、消費の場面では what_how_many(購入 4 つ)と price_skip(購入 2 つ)の 22 件が当たる。
- 再現: 各場面の `S.orders(...)` の 4 通りで `ClassicalScorer().score(s, p)` を比べると、**44 件中 20 件で分布が変わる**(例: what_how_many-01 では、購入の質量 0.002 の行き先が並びによって b1・a3・a1 に移る)。
- 今の記録で「1 位が変わる率」が 0 なのは、購入の質量が小さい(0.001〜0.056)からにすぎない。古典の「対 古典の JSD」の列は、並び 0 での恣意的な割り当てに乗っている。
- 直し方(tools の中): 同じ kind の候補には kind の質量を等分する(id の順に)。evalset には同じ kind が無いので golden は変わらない。

**中 2 `match_free_text` は丁寧語を「破綻」に数え、量の数を番号と取り違える**
- 再現(場面の並び 0 で): 「クロワッサンを2つ買います。」・「高いのでやめます」・「安いほうを買います」・「別の店で探します」・「また来ます」は、すべて None(=破綻)になる。見せ方の文の完全一致と kind の語にしか当たらないため。
- 「クロワッサン 2 個にします」(数と単位の間に空白)は番号 2 と読まれ、見送る(skip)に**黙って**当たる。「1位は食パン」も番号 1(よく考える)に当たる。
- 列「日本語での破綻率」は、日本語が壊れた率ではなく「候補の文と字面が違う率」になる。外れた答えは「その他」に確率 1 を置くので、その他の率にも混ざる(低 5)。いまは Noul の候補が無いので数値は出ていないが、Noul の候補が入る前に、当て方(語幹・丁寧語の正規化・数と単位の間の空白)と列の定義を決め直す必要がある。

**中 3 vLLM の echo の形(既定)は、日本語の文の後ろの位置に依存する。記録の「番号は ASCII なので影響しない」は echo には当てはまらない**
- echo は答えの `text_offset`(文の頭から数えた位置)で候補の頭を探す。番号そのものは ASCII でも、その位置は日本語の文の全トークンの decoded の長さの和で決まる。バイト単位のトークン(漢字の途中で切れる物)の decoded が置換文字か空になると和がずれ、毎件 `TokenBoundaryError` で止まる。偶然ほかのトークンの頭に重なると、違うトークンの値を黙って切り出す。
- `prompt_logprobs` の形は後ろから引くので、末尾の ASCII の番号には強い。実機は未確認(自己申告どおり)。
- 案: 番号の形の既定を prompt_logprobs にするか、echo で `choice.text[begin:end] == 候補` と「`text_offset` の最後+最後のトークンの長さ == len(text)」を確かめてから切り出す。README §8 の 1 文も直す。

**中 4 語彙の版と語の形が routing §5 と合っていない**
- 場面と古典は語彙 v1 で書かれている(params の `vocab_version: v1`・待機 33 候補)。routing §5 は今の語彙を v3 とし、待機は v3 で欠番。
- routing §5 では「値段を見て見送る」は「候補+知覚」、「満足して戻るか」は「候補」で、語ではない。#36・#38 はどちらも語彙「見送る」を使う。実装はこれを 4 つの kind の語(値段を見て見送る・また行く・また行かない を含む)にした。「見送る」という同じ字面は、routing の「見送る(電車)」ともぶつかる。
- 器の欠陥ではなく、語彙への写し方の判断(設計者の指紋になり得る)。問い 2 へ。

### 新たな欠陥
**中**
- **新 中 1 「来る」「する」の否定の形が、肯定の候補の当たりに入っている**。`verb_forms` は来る・くる・するにだけ否定の形(来ない・こない・しない)を足す(五段と一段には足さない)。そのため否定の答えが、反対の意味の候補に**黙って**当たる。
  - 再現(revisit-01 の並び 0): 「もう来ない」→ again(また行く(この店にまた来る))。「この店には来ないと思う」→ again。する も同じで、「次は別の店にする」の候補は「しない」で当たる。revisit は判断点の 1 つそのものなので、Noul の候補を回すと破綻率と 1 位の両方が歪む。
  - README §3-1 の 2 は「否定」を当たりの形に含めると書いており、設計としても直す必要がある。
  - 直し方: 否定の形は肯定の候補の形から外す(候補の文が「〜ない」のときだけ否定の形を当てる)。
  - いまは Noul の候補が無いので数値はまだ出ない。Noul を回す前に直すこと。

**低**
- **新 低 1** 失敗の記録(`compare.scorers[名].failures[腕].items` と厳密モードの「失敗」の欄)に、例外の文の頭 160 字(`message`)が入る。vLLM の `BackendError` の文は艦隊の答えの本文の頭 160 バイトを含むので、艦隊がエラーの文に入力を引き写す場合、評価セットの本文が result.json に写り得る。README §2 の「数・id・並び・型の名」という説明とも食い違う。案: `message` を記録に出さない(型の名と HTTP の状態だけにする)。
- **新 低 2** 漢数字の数(「クロワッサンを二つ買います」)は当たらず、破綻に数える。何をいくつで言い方がぶれると破綻率が上がる。
