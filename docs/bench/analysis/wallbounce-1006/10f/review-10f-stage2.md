## 2. seed の分離の正しさ(検査 1)

- **網羅**: src(`build/` を除く)の乱数の呼び出しは `stream`・`philox`・`derive_key` の 3 つの入口から入り、numpy の `default_rng` の直呼びは src に無い(道具の `salt_compare.py` の検定の無作為の組だけ)。`build/` は固定の seed で世界データを作る処理で、ランの中から import されない。用途名の 26 個は表の 10+16 に全部載っている。実行時の試験は `derive_key` を包むので、`stream`・`philox` を経由する呼び手も全部数えられる(`core.rng` の中の呼び出しはモジュールの名前で引くため、包んだ関数が使われる)。
- **用途名を持たない塩**(`run_salt`・出勤の抽選・艦隊の呼ごとの種)は 3 つとも動きの seed から作られていた(run.py で `run_salt_for(seed)`・`Presence(seed=seed)`)。
- **静的な試験の穴(S3-1)**: (1) `from shibuya.core.rng import stream as _s` のように別名で読むと拾わない (2) `stream(seed, domain="…")` のように用途名を名前つきの引数で渡すと、引数の数の条件で飛ばす (3) blake3・xxh64 を seed で直接作る乱数は静的にも実行時にも数えない (4) `self.domain` の対応は試験の中に手で書いた表(`_DYNAMIC`)で、既定の値が変わっても追わない。どれも今の src には該当がなく、実行時の試験が通る経路なら (1)(2) は表に無い用途名として落ちる。穴は「試験で回さない経路に新しい流れを足したとき」だけに残る。

## 4. CRN の健全性と最初の食い違い(検査 8)

- 2 段の探し方は、最初の区間(0 から毎 tick)・中の区間(止めて状態を書き、再開して毎 tick)・最後の区間(止めずに最後まで)・食い違いなしの 4 通りで、毎 tick の通しと一致した。区間の端の tick(59 の倍数でない最後の checkpoint=169)でも崩れない。
- **腕から導かれる差の宣言(`arm_keys_derived`)**: 宣言の効き目は「対の間の設定の差を許す」だけで、同じ腕の salt の間の交換可能性(`seed_exchangeability`)には効かない。このため、宣言した欄が salt ごとに揺れれば落ちる。残る抜け道は「腕の固定の差として、人が理由を書けばどの設定の差でも通る」ことと、報告に欄の**値**が残らないこと(S3-3)。
- **腕の欄の決め方**: 2 つの腕の引数の名前の和集合を、接頭辞の一致で許す。両方の腕で同じ値の引数や、引数の名前の下の木全体(`activity` なら `activity.*`)も許してしまう(S3-4)。今の 5,000 体の例では害は無い。
- **全体の `ok`**: A/A のランが無いと `all([])` で真になり、`ok: true` のまま `aa_note` だけが出る。T0 > 0 で T0 より前の checkpoint が 1 本も無いときも `pre_t0` は真になる(S2)。
- R-71 §8-1 の 1 は「世界の hash も対で同じ」を求めるが、道具が見るのは最初の checkpoint の母集団と日課のハッシュだけ。世界の入力は設定の節(`registry_hash`・`frozen_sources` など)の比較で見ているので、欠陥とはしない。

## 6. 欠陥(重さ順)

### S1 気象の再生実日と合成世界を「母集団」の側に入れた判断は、K21 の範囲を超える(判断待ち)

- どこで: `engine/run.py` の `POPULATION_RNG_DOMAINS` の `engine.processes.environment`・`world.synthetic`、`engine/processes/runner.py`(`EnvironmentProcess` に母集団の seed を渡す)。
- 内容: K21 (a) で決めたのは「母集団の抽出を固定して、動きだけを変える」こと。気象は母集団(誰が居るか・体の属性)ではなく環境で、外から与える入力にあたる。実装役は「manifest の設定の節に載る値は salt で動かさない」という帳簿の規則で母集団の側に入れた。結果として salt の幅から気象のばらつきが抜ける。
- 是非の意見: 固定する向き自体は筋が通る。DT の定義(現実のある時点のスナップショットが舞台)に照らすと、気象の実日は舞台の一部で、腕の効果を測るときに混ざらない方がよい。ただし次の 3 点で、このまま既定にはできない。
  1. 名前と分類が中身と合わない。`population_seed` が「母集団+環境の一部」を決める。表は母集団・環境(舞台)・動きの 3 つに分けるか、少なくとも表の中で気象を「環境」と明記したい。
  2. 規則がそろっていない。同じく外から来る環境の出来事である `world.large_event`(大きな催しの日の抽選)・`world.road_works`・`world.delivery_inbound` は動きの側に残っている。salt を変えると催しや工事の有無は変わるのに、気象だけ固定される。気象を固定する理由が「manifest に載るから」だけなら、帳簿の都合で科学的な意味が決まっていることになる。
  3. 設計書 §5 の「salt 間の幅」の意味が変わる(抽出に加えて気象のばらつきも含まない)。K21 で約束した設計書 §5 への注記(「抽出を含む幅」)も、まだ書かれていない。
- 直し方の案: 親とユーザーに 3 択で聞く。(i) 今のまま(気象は固定・名前と表の分類だけ直す)(ii) 気象を動きの側へ戻す(1 行)。この場合、salt の比較の入力の一致では `replay_date` を許容に入れる (iii) 環境の seed を別に立てる(気象・催し・工事を同じ側にそろえる)。どれを選んでも既定の結果は変わらない。CLAUDE.md §2-6 の「設計者の指紋になる挙動」に当たるので、commit の前に聞く。合成世界は資産が無いときの代用なので、母集団の側で問題ない。

### S2 A/A を回していないランでも CRN の健全性が `ok: true` になる

- どこで: `tools/c7/salt_compare.py` の `crn_health`(`all(x["ok"] for x in out["aa"])` が空の列で真)と `pre_t0_match`(T0 > 0 で T0 より前の checkpoint が 0 本でも真)。
- 再現: `--aa` 無しで回した索引を `crn_health` に渡すと、`ok: true` と `aa_note` が出る。
- 直し方の案: A/A が 0 本なら `ok` を偽にするか `"incomplete"` にする。T0 > 0 で T0 より前の checkpoint が 0 本なら `pre_t0` を偽にする。試験を 2 件足す。R-71 §8-1 は A/A を自動の確認の 1 つに挙げている。

### S3(既定の結果に影響しない・まとめて直せる)

1. **静的な網羅の試験の穴**(§2): 別名の import・名前つきの `domain=`・seed から直接作るハッシュの乱数・`_DYNAMIC` の手書き。案: 呼び手の名前を `core.rng` から import した別名まで追う。名前つきの引数も読む。blake3・xxh64 に `seed` を入れる呼び出しを grep で数え、`MOTION_SALTS` の 3 つと突き合わせる試験を足す。
2. **差 ÷ 幅の読み**: 幅に対の差の SD を使うと、差 ÷ 幅 > 1 は α/m の対の t 検定と同じになる。報告の `status_note` に「差 ÷ 幅は記述。1 を超えても K20 (a) の検定ではない」と 1 行足す。
3. **導かれる差の宣言の値**: `arm_keys_derived` を `{道筋: {"base": 値, "arm": 値, "reason": …}}` にして、実際の値と照らす。少なくとも報告の `pairs` に差の値(基準と腕)を出す。
4. **腕の欄の和集合と接頭辞**: 2 つの腕で値が違う引数だけを腕の欄にする。接頭辞での一致は、宣言したときだけに絞る。
5. **ρ の警告の扱い**: `warn_ratio_over_1` が `rho_readable: false`(5 対未満)でも立つ。README §6 も 3 対の比 1.23 を警告として書いている。警告は 5 対以上に限るか、「読まない」を同じ行に添える。
6. **スクラッチの使い回し**: `salt_runs.py` の細かい探し方は `fine_*/state_head` の古い状態のファイルを glob で拾いうる(同じ scratch で回し直したとき)。案: 置き場が空でなければ止めるか、ランごとに消す。
7. **試験の注記の誤り**: `test_known_two_arms_three_pairs_hand_values` の注記「比 15/12」は、正しくは 14/12(試験の式は 14/12 で正しい)。
8. **母集団の seed の型**: `input_match` は `_norm`(文字列化)で母集団の seed をそろえるので、`1` と `"1"` を同じとみなす。`core.rng` では別の鍵(`i:1` と `s:1`)になる。CLI からは整数しか来ないので害は小さい。

## 7. 実装役の §8 への意見(1 行ずつ)

1. 母集団の側の範囲: 体の属性と mock 日課は賛成。気象は S1 のとおり、判断を取ってから既定にする。
2. 幅の定義: 差の比較には対の差の SD が R-71 §5-4 と合うので賛成。各腕の SD の幅も並べるのは良い。「どちらを幅の列にするか」は親の判断に残し、S3-2 の注記を足す。
3. 最初の食い違いの探し方: 最初・中・最後の区間と食い違いなしの 4 通りで、毎 tick の通しと一致することを確かめた。賛成。
4. manifest に載っていない腕の欄: 今は報告だけでよい。腕の効き目そのものを入力の一致で確かめられないので、後の版で `salient_rate_per_10k`・`report_precondition` を設定の節に足す(列の追加だけ)ことを勧める。
5. 導かれる差の宣言: 人が宣言する形に賛成。自動で許すより安全。ただし S3-3 のとおり期待する値まで書かせる。
6. 指紋に載せるのは seed と違うときだけ: HEAD で書いた状態のファイルが作業木で再開でき、違う値の状態を値無しで再開すると止まることを確かめた。賛成。
7. 回す役が `shibuya.cli.run` を別のプロセスで呼ぶ形: byte-check の道具と同じで、腕の引数の型が崩れない。賛成。
