## 欠陥(重さ順)

### U1(中〜高・コミットの前に直すことを勧める): 旧の pickle の口が中身で自動的に選ばれ、外から来たファイルでもコードが動く

- どこで: `engine/resume.py` の `read_state`。`data.startswith(MAGIC + b" ")` なら `_read_state_pickle` へ進み、検査の後に `pickle.loads(payload)` を呼ぶ。
- 先頭の行の sha256 と写しの `.json` のラン ID は、同じ人が両方を書けば必ず合う。だから「自分が書いたもの」の証明にはならず、壊れたファイルや取り違えを止めるだけになる。
- 再現: 作業用の場所に、`__reduce__` で印のファイルを作る中身の pickle を作った。10d の形の先頭の行(sha256 は中身から計算)と、ラン ID の合う写しの `.json` を添え、名前は `state-T00000750.npz` にした。`RS.read_state` に渡すと、印のファイルができた(=コードが動いた)。その後に「形式の版が違う」で止まった。警告は出るが、開く前に止める手段にはならない。
- 影響: `resume.py` の docstring にある「読むだけでコードが動く経路が無い(外から来たファイルでも)」と README §4-2 の主張は、npz の枝にしか当たらない。`--resume-from` に渡すファイルの全体では成り立たない。実際の危険は、手元で自分のファイルを使う間は小さい。ただし K23 (a) の目的(約束を外す)とぶつかる。
- 直し方の案: `read_state(path, *, allow_legacy_pickle=False)` にする。旧の形式は、明示の切替口(CLI の `--resume-legacy-pickle` など)と拡張子 `.pkl` の両方がそろったときだけ開き、それ以外は「旧の形式。切替口を付けて読むか、変換してから読む」で止める。試験の `test_legacy_pickle_still_reads_with_a_warning` と第 3 段の §4-3 の確かめは切替口を付けて回す。docstring は「npz+json は外から来たファイルでもコードを動かさない。旧の pickle は切替口を付けたときだけ開き、そのときは自分のファイルに限る」と書き分ける。

### U2(中・第 3 段の欠陥ではない・10e の範囲に効く): 日の鍵の流れは、次の日に 1 ブロックずれた同じ列になる

- 実装役の §7 の 2 の「日をまたいだ相関」は、実際には**ほぼ写し**だった。`stream(1, "world.delivery_inbound", 1)` の最初の 8 個は、`stream(1, "world.delivery_inbound", 0)` の 5 個目から 12 個目とビット単位で同じ(手元で確かめた)。1 日目の配送の計画は、0 日目の乱数の列を 4 語ずらして使っている。工事・stateful の顕著行為・出動も同じ形。
- 影響: 2 日以上のランでは、これらの過程の日ごとのばらつきが作り物になる。日の差を測る主張には使えない(1 日のランと既定の byte-check には効かない)。
- 案: 10e の版上げの 1 回目で P1・P2・R3 と同じ優先度で直す。それまでは「2 日以上のランでは、配送・工事・顕著行為・出動の日ごとの差は乱数の写し」と K19 の許可の表の理由と README に書く。

### U3(低): 許可したクラスの組み立てで、宣言の外の属性と型の違う値が通る

- どこで: `engine/state_codec.py` の `Decoder.dec` の `__o`(`object` の形)。dataclass は「欄が足りない」だけを見て(`need <= set(fields)`)、余分な欄を拒まない。dataclass でない値のクラス(`DeferralQueue`・`EventBudget`)は欄の検査が無い。
- 再現(どれも受け入れられた): `PendingInvite` に余分な欄 `evil` を足す / `__dict__` という欄で、欄の検査の後に属性を丸ごと `{"x": 1}` に置き換える(全部の欄が消えた値ができる) / `__eq__`・`__repr__` を属性に置く / `tick` に文字列を置く / `DeferralQueue` に `zzz`。
- どれもデータを置くだけでコードは動かない(dunder は型の側から引かれるので、インスタンスの属性では効かない)。ただ「台帳の宣言と突き合わせる」の網から外れる。
- 案: dataclass は欄の集合が**一致**すること(`==`)を見る。`__` で始まる名前は拒む。dataclass でないクラスは、許可の表に欄の一覧を持たせる。欄の値の型は、試験で 1 つ見ておくとよい(`Target.kind` が `TargetKind` か など)。

### U4(低): 拒否の例外が `StateFormatError` にそろわない

- 再現: `__ns` の桁あふれ(`|i1` に 1000)は `OverflowError`、MT19937 の鍵の配列の長さの違いは `IndexError`、深さ 10 万の JSON は `RecursionError`、zip の中の `meta` が npy でないと `AttributeError`、`__class__` に Enum の値を置くと `TypeError`。
- どれも読みは止まり、コードは動かない。ただし `read_state` は `StateFormatError` だけを `ValueError` に包むので、CLI では生の例外とトレースバックが出る。
- 案: `SC.loads` の組み立ての部分(`np.load(allow_pickle=False)` の後)は `except Exception` で `StateFormatError` に包む。この時点で実行されるのは許可したクラスと numpy の中だけなので、広く包んでも安全。圧縮の爆弾(展開して巨大になる配列)の上限は無い(コードは動かず、メモリが尽きるだけ)。上限のバイト数を宣言するかは 10e で決める。

### U5(低): 場所ごとの許可が「行の文字列を含む」で当たり、何か所でも許す

- どこで: `engine/state_ledger_ast.py` の `check_external`(`a.contains in s.text`)。今は許可 17 項が 18 か所に当たっている(1 項が 2 か所を許している)。
- 影響: 許可した行と同じ文字列の行を、挙動の場所に写しても通る。
- 案: 許可の項に「当たる数」を持たせ、数が増えたら落とす。

### U6(低・限界の明記): 軸 1 の名前の衝突の規則と getattr の変数

### U7(低): 軸 2 の検査が拾える範囲

- **10d の漏れの別の項目を再現**(T4 の `conv.n_opened`・`_snap` 以外):

## 確かめたが欠陥でなかったもの

- **静的に安全な 15 か所**: 定数の語数 8 か所を全部読んだ。どれもループの中ではなく、引くのは 1〜2 語(`integers` の上限が 2^31 なら半分の語)。定数の 1 語目 7 か所も、隣の流れは無い。`integers` の棄却で語数が増える確率は無視できる大きさ(理屈の上だけ)。決まらない 16 か所は走査の結果と一致した(全部で 31 か所)。
- **5 語目の呼び手**: 静的(`random(5)` で落ちる・`random((2, 2))` は通る)・実行時(最大 2 ブロック・重なりで落ちる)とも、試験を自分で回して通った。
- **npz の読み**: `np.load` は `allow_pickle=False` の 1 回だけ。object の配列と、object を含む構造化の dtype は numpy が拒む。許可の表の外のクラス名は import もしない。`__g` は許可した 5 つのビット生成器を種 0 で作り、状態を置くだけ。`__r` の循環は「定義の前」で拒む。構造化の dtype(object 無し)と文字列の配列は受け入れるが、SoA は台帳の dtype、外の状態は戻す前の型の突き合わせで止まる。
- **同一性**: 試験(凍結した `Target` 3 か所・配列・list・実物の日の境目の `_last_close`)を読み、通ることを確かめた。
- **既定の結果**: 上の表のとおり不変。`_canon` の Enum の順の入れ替えで指紋は変わらない(HEAD の `.pkl` から再開できたことが傍証)。
- **記録の数値**: `byte_check_stage3.json`(19 構成・`all_ok` true・HEAD `129da80`)・`two_day_check_stage3.json`(`47e0a85b02797e23`・142,043 呼・HEAD と作業木が同じ)・`k19_runtime_stage3.json`(5,000 体・1 日の 185・1・1・最大 2,602 ブロック)・`resume_19x2_stage3.json`(19 行・全部一致・89,962〜160,561 B)は README の数と合う。表 4-1 の比(768,757 ÷ 4,306,062 = 0.179・1 体あたり 154 B・記憶+関係 0.066)の計算も合う。許可の数(出口 12・衝突 20・場所ごとの許可 17 項・11 属性)は表と合う。README と 4 つの JSON に、絶対パス・ユーザー名・機械名は無かった。

## 実装役の §7 への意見(8 件。依頼は「6 件」だったが §7 は 8 件ある)

1. 看板の露出: 今は理由つきの許可でよい。根は、軸 1 の `no` が「導ける・配線・tick の中だけ」を含み、挙動の読みが正当な値を含むこと。10e で `no` を分けるか、AST の規則を `diag` に絞るかを決める項にする。
2. 日をまたぐ重なり: 10e に入れる。重さは U2(相関ではなく 1 ブロックずれた写し)。
3. 軸 2 の近似: 測った。違うのは金の台帳の生の行の 5 配列だけ(U7)。近似のままでよく、その 5 つは再開の試験に任せると README に書く。
4. 印 4 つ: 妥当。`__ns` の桁あふれだけ例外の型がずれる(U4)。
5. `InboundStarts`: 妥当。書く時点で場所つきで止まるので、足りない型は見落とさない。
6. 鍵の型の検査の弱さ: 同意。低い。値の中身は full-hash の検算で守られている。U3 の欄の検査を厳しくする方が先。
7. 旧の pickle を 10e で消す: 同意。それまでの間は U1 の切替口が要る。
8. 写しの `.json` の共有: 試した形では、取り違えは sha256 かラン ID で止まり、黙って読み違えることは無い。10e で写しの名前を `state-T….npz.json` のように拡張子つきにすれば消える。
