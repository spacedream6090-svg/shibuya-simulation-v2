# 艦隊の口の試験の揺れと、接続の置き場が詰まる件(第347・2026-11-20)

CI で 2 回落ちた試験の原因を、手元で調べた記録。src は変えていない。変えたのは、試験の「失敗したときの表示」だけ。

## 1. 何が起きたか

- 落ちた試験: `tests/engine/test_fleet_wiring.py::test_timeout_defers_then_reinjects_and_is_finally_answered`。偽の vLLM を 3 秒後に直し、0.2 秒の時間切れで 90 刻みを回して、「時間切れ → 繰り延べ → 送り直し → 答えが返る」を見る試験(本物の時計に頼る)。
- CI で 2 回、`fleet_ok == 0` で落ちた(`ff0b2af`・`54d8c68`)。どちらも、同じコードの隣の commit は緑(`4af887b`・`b93f95f`)。手元(Windows)では落ちない。
- 2 回目の失敗の表示で読めた数は `fleet_calls` 17,376・`fleet_answered` 0 だけ。前に足した表示は dict のまま渡していたので、pytest が途中で切った。偽サーバーの側の「遅れた応答の誤り」(BrokenPipe)は約 200 件だった(ログの行を数えた目安。1 刻みの呼の数=約 193 に近い)。

## 2. 手元の再現(Windows・Python 3.12・httpx 0.28.1・httpcore 1.0.9)

- 版: CI も httpx 0.28.1・httpcore 1.0.9(`54d8c68` の CI のインストールの記録で確かめた)。anyio は手元 4.15.1・CI 4.16.0。`pyproject.toml` は `httpx>=0.27` で、版は固定していない。

時間切れを試験の 0.2 秒から縮めて、遅い実行機のまねにした(`tools/fleet_counters_probe.py`・90 刻み・直すまで 3.0 秒。出力 [probe_out/counters.txt](probe_out/counters.txt) の 1・4・5 行目)。

| 時間切れ | 呼 | 答えが返った(`fleet_ok`) | ランの壁時計 | 直した後に偽サーバーへ届いた要求 |
|---:|---:|---:|---:|---:|
| 0.2 秒(試験と同じ) | 845 | 291 | 5.1 秒 | 335 |
| 0.1 秒 | 13,762 | 55 | 61.7 秒 | 93 |
| 0.05 秒 | 18,000 | 0 | 44.5 秒 | 0 |

- 0.05 秒の回は、CI の失敗と同じ形になった(答え 0・呼は約 200 件 × 90 刻み)。
- この回をもう一度回し、ランの間に 4 秒ごとに見張った(`tools/fleet_pool_probe.py 3.0 0.05 30`・出力 [probe_out/as_is_e2e005.txt](probe_out/as_is_e2e005.txt))。
  - 偽サーバーへ標準ライブラリで直に送ると、0.00〜0.02 秒で返る。**偽サーバーは生きている。**
  - 艦隊の口の接続の置き場(httpcore のプール)は、3 つのレプリカとも `Requests: 0 active, 2〜16 queued | Connections: 16 active, 0 idle` のまま変わらない。**上限の 16 本が、どの要求にも使われていない接続で埋まっている。** 新しい要求は置き場で待ったまま時間切れになり、サーバーへ出ていかない。
  - 検収役も同じ台本を 1 回回し、同じ形になった(直した時の要求の数がランの終わりまで増えない・置き場は 3 つとも 16 本が埋まったまま・`fleet_ok` 0)。
- 0.2 秒でも余裕は小さい。偽サーバーを直した後に最初の要求が出る形にすると(`fleet_counters_probe.py 3.0 2.2` と `3.0 2.9`。counters.txt の 2・3 行目)、健全な偽サーバーに対して、時間切れが 95〜121 件出た(刻みごとの内わけは出していない)。
- counters.txt の 1〜3 行目は、台本に時間切れの引数を足す前に回したので、行に `e2e_s` が出ていない(時間切れは 0.2 秒)。4・5 行目は `3.0 0 0.1` と `3.0 0 0.05`。

## 3. 分かったこと

- **手元の再現で確かめたこと**: 落ちる形は「偽サーバーが遅い」ではない。艦隊の口の側で接続の置き場が詰まり、偽サーバーを直しても、ランの終わりまで回復しない。
- **推測(まだ確かめていない)**: CI の 2 回の失敗も同じ仕組み。合う点は 3 つある。呼の数が 193 件 × 90 刻みに近い(17,376)。答えが 0。偽サーバーの遅れた応答の誤りが約 200 件だけ(その後は、遅れた応答が出ていない)。
- **次に落ちたときに確かめる手だて**(試験に足した表示):
  - 偽サーバーへ届いた要求の数(直した時までと、ランの終わりまで)。サーバーの側か、艦隊の口の側かが分かる。
  - ランが 8 秒・30 秒を超えて続いた回だけ、その時の接続の置き場の表示・接続の状態ごとの数・口の実行中の数を控える(手元の健全な回は約 5 秒で終わるので、何も読まない)。置き場で詰まったのか、口の Semaphore が戻らないのか、接続を張る所で詰まったのか(偽サーバーの待ち行列は既定の 5)が分かる。
  - 失敗の形にしたときの表示の見本: [probe_out/forced_failure_display.txt](probe_out/forced_failure_display.txt)(`tools/force_fail_show_diag.py`。時間切れだけを 0.05 秒に差し替えて、試験の関数をそのまま呼ぶ)。8 秒と 30 秒のどちらも `Requests: 0 active, 9〜16 queued | Connections: 16 active, 0 idle` だった。16 本の内わけは、3 つのレプリカで、張っていない接続(CONNECTING)が 11・9・10 本、張り終えたがまだ送っていない接続(NEW)が 5・7・6 本で、8 秒と 30 秒で同じだった。
- **`fleet_conn_retry_*` が多い理由**: 置き場の時間切れ(`PoolTimeout`)は、艦隊の口では「接続の誤り」に分類され、同じレプリカと別のレプリカへ 1 回ずつ送り直す(`_classify`)。失敗の形の見本では、同じレプリカへ 5,479・別のレプリカへ 1,672 だった。
- **上流の既知の不具合と同じ形**: httpcore の `AsyncConnectionPool` は、置き場で待っていた要求に新しい接続を割り当てた後、その要求が送り始める前に取り消されると、要求だけを外して、接続を一覧に残す。残った接続は、閉じられも使い回されも期限切れにもならない。上限まで溜まると、健全なサーバーに対しても全部の要求が置き場の時間切れになる。`asyncio.wait_for` と `Task.cancel()` の取り消しで起きる(艦隊の口は、1 回の試行を `asyncio.wait_for` で包んでいる)。手元の httpcore 1.0.9 の `connection_pool.py`・`connection.py` を、親と検収役が読んだ。
  - 残る形は 2 つある。張る前に取り消された接続(CONNECTING)と、張り終えた直後、送り始める前に取り消された接続(NEW)。接続を張っている最中の取り消しは片づく。
  - NEW の接続は、ソケットを開いたまま残る(コードの読み。開いたソケットの数は数えていない)。
  - [encode/httpcore PR #1099](https://github.com/encode/httpcore/pull/1099)「Reclaim connections orphaned by a cancelled request」(2026-07 に開かれた。読んだ時点で未マージ。コメントに httpx 0.28.1・httpcore 1.0.9 での再現の報告がある)。
  - [encode/httpcore discussion #783](https://github.com/encode/httpcore/discussions/783)「Race Condition with Asyncio Cancelled Tasks」(2023-08。issue #785 へ)。
  - どちらも WebFetch の要約で読んだ(全文は読んでいない)。

## 4. 対策の候補(どれも決めていない=報告の判断待ち)

src を変えずに、接続の上限だけを替えて試した(`fleet_pool_probe.py 3.0 0.05 40 x4 0.8` と `… unbounded 0.8`)。

| 形 | 答えが返った | ランの間の置き場 | 出力 |
|---|---:|---|---|
| 上限 16(今) | 0 | 16 本が埋まったまま | [as_is_e2e005.txt](probe_out/as_is_e2e005.txt) |
| 上限 64 | 237 | 答えは返ったが、ランの後半の見張りでは `Connections: 63〜64 active` まで埋まっていた(そのとき使っている要求は 1〜8) | [x4_e2e005.txt](probe_out/x4_e2e005.txt) |
| 上限なし | 240 | 詰まらないが、ランの後半の見張りでは、使っている要求(3〜9)より多い接続(14〜23)が残っていた | [unbounded_e2e005.txt](probe_out/unbounded_e2e005.txt) |

上限 64 は、詰まるのが遅くなるだけで、漏れは残る。上限なしは詰まらないが、使われない接続の一覧が伸び続ける。候補は次の 6 つ。

- (a) そのまま。本番の時間切れは 60 秒と 300 秒(expedient)で、「時間切れが、接続を割り当てられた直後に当たる」ことは、試験の 0.2 秒より起きにくいと見ている(推測。測っていない)。ただし、次の 2 点がある。
  - 起きれば溜まって戻らない。長いランでは、レプリカの上限(本番 64)が少しずつ減り、最後は答えが返らなくなり得る。
  - 本番も試験と同じ組み立てになっている(口の Semaphore と置き場の上限が同じ数・置き場の時間切れは e2e と同じ 300 秒)。時間切れが続く局面は、接続を閉じて作り直す局面なので、漏れの窓が開きやすい局面と重なる。
- (b) 試験の時間の余裕を広げる(0.2 秒 → 1 秒など)。CI の揺れは減るが、この不具合は CI から見えなくなる。
- (c) 艦隊の口の側で回復する(例: 時間切れが続いたレプリカの httpx のクライアントを作り直す)。src の変更で、実 LLM のランの挙動に関わる。
- (d) 上流の直しを待つか、直しの入った配布へ替える(依存の入れ替え)。
- (e) 置き場の上限を、口の Semaphore より大きくするか、上限なしにする(src の小さな直し)。要求が置き場で待つ場面が減る。漏れは残る(上の表)。NEW の接続はソケットを開いたまま残るので、上限なしでは、手元とサーバーの側に開いた接続が溜まり得る(推測。数えていない)。
- (f) 時計に頼らない再現の試験を足す(割り当ての直後に取り消して、置き場に残る接続を数える)。(b) を採っても、不具合が CI から見えなくならない。

## 6. 道具

- `tools/fleet_counters_probe.py <直すまでの秒> [<run_day の前に待つ秒> [<e2e の秒>]]`: 試験と同じ呼び方で 90 刻みを回し、艦隊の数と、偽サーバーへ届いた要求の数を 1 行で出す。
- `tools/fleet_pool_probe.py <直すまでの秒> <e2e の秒> [<刻みの数> [<形> [<見張りの間隔の秒>]]]`: ランの間、偽サーバーへ届いた要求の数・偽サーバーへ直に送ったときの所要・接続の置き場の表示を出す。置き場の表示は httpx の private な属性を読む(調べるための道具で、src からは使わない)。
- `tools/force_fail_show_diag.py`: 時間切れだけを 0.05 秒に差し替えて試験の関数を呼び、失敗したときの表示を出す(試験のファイルは書き換えない)。
- どれもリポの根で、`PYTHONPATH=src` を付けて回す。偽サーバーの遅れた応答の誤りが標準エラーに大量に出るので、標準エラーは捨てる。出力には、回したときの引数が出ない(上の各節に書いた)。
