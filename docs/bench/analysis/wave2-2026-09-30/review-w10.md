## 2. 見つけた欠陥(重い順)

### 2-1 【中・潜在】町名に漢数字を含むと `chome_name_from_address` が例外を投げ、ラン全体が止まる

- 原因: `C.normalize_jp` が漢数字の一〜九を**文字列の全体で**算用数字に変える。そのため `三田1丁目` は `3田1丁目` になり、`^(\D+?)(\d+)丁目` にも `^(\D+)` にも当たらない。
- 再現: `R.chome_name_from_address("目黒区三田1丁目2")`、`"目黒区五本木2丁目"`、`"港区六本木6丁目"`、`"新宿区四谷1丁目"` はどれも `ValueError: 町名が読めない`。
- 影響: いまの 7 点(青葉台・用賀・神宮前・鉢山町・広尾・本町・東)には当たらない。ただし `ruler_rows` は区を判定する**前に**この関数を呼ぶので、区外の 1 点でも当たると全体が止まる。Q-W10a(都内の R5 の点を探し直す)で確実に当たる。付随して、`渋谷区神宮前5-53-1` のような丁目の無い書き方は黙って `神宮前` になり、`NO_BOUNDARY` に紛れる(名前が突合できなかったのか、境界が無いのかの区別がつかない)。
- 直し方の案: 丁目の番号だけを正規化する(NFKC で全角の数字を半角にし、`([一二三四五六七八九十]+|\d+)丁目` を切り出してから数字にする)。町名の部分は正規化しない。町名が突合できない点は `NAME_NOT_FOUND` として `NO_BOUNDARY` と分け、例外ではなく行として返す。試験に「三田」「六本木」「千駄ヶ谷」「丁目の無い書き方」を足す。

### 2-2 【中・記録の読み違いを招く】`road` 代表値に距離の上限が無い

- 事実: `estat` の点では、半径の中で「測った階級の辺に最も近い格子点」がその辺から大きく離れている。No.78 は 265/234/192 m(r=25/50/100)、No.79 は 114/45 m(r=50/100)。README W10-3 の表は、これらを路側の実測と同じ「道路の値」として並べている(例: No.79 `estat`/road/r50 = −10/−13 は、幹線から 114 m 離れた住宅地の格子の値)。`road_dist_m` は JSON にはあるが、表には出ていない。
- 直し方の案: `road` に上限を付ける(例: 格子の帯の幅 8 m 以内。上限を超えたら None)。または README の表に `road_dist_m` を併記し、上限を超えるセルに印を付ける。どちらにするかは expedient の選択なので親が決める。

### 2-3 【小】昼と夜の `road` が別の格子点から来ることがある

- `measure_near` は昼と夜で別々に呼ばれ、距離が同じ点が複数あると、それぞれ「値の大きい方」を選ぶ。そのため同じ距離の候補が複数あるとき、昼と夜で違う点を選びうる。2.5 m の格子と軸に沿った道路では、同じ距離の点はありうる(いまの 3 点で実際に起きたかは確かめていない)。
- 直し方の案: 距離が同じなら昼の値で 1 点に決め、夜も同じ点の値を読む。または添字の順で決める。

### 2-4 【小】NaN への弱さ(いまの資産では起きない)

- 値に NaN があると `max` は NaN を返す(JSON に NaN が書かれる)。距離に NaN があると `rd == nan` が空になり、`ValueError: zero-size array` で止まる(再現: `measure_near(0,0,[0,1],[0,0],[50,60],[nan,2],5)`)。
- 騒音場は uint8、距離は線分からの計算なので、いまの資産では起きない。直すなら `np.isfinite` で前もって除く。

### 2-5 【小】投影の式を写している

- `_to_local` は `geo.common.latlon_to_local` の式を写したもの(shapefile.py の docstring では、W0 の CRS が唯一の正典)。いまは同値で、正典の関数で独立に計算し直した値は一致した。それでも写しがあると将来ずれうるので、`G.latlon_to_local` を呼ぶ形がよい。
