# エンジン側の実時間スパイク(2026-09-07・設計判断用=言語/アーキテクチャ選択)

> 目的: 「エンジン側の時間はLLM側よりどれほど短いか」をユーザーの判断材料として実測する。**シム本体ではない**(tools/bench_spikes/ のスクリプト2本)。環境=ローカル機(Intel Core Ultra 7 265K・20コア・31GB・Windows 11・Python 3.12・NumPy 2.5・numba 0.67)。サーバー(64コア)はSSH不通のため未測(後日追記)。

## 1. 1tick処理のスパイク(engine_tick_bench.py・40万体・453セル・約3,200起床/tick・200イベント/tick・60tick計測)

設計どおりの段階を模す: 需要更新→移動→密度集計(bincount)→セル動的ハッシュ(xxhash×453)→起床判定→アービタ(4クラス+ハッシュ優先度でlexsort)→観測レンダリング(個体部B1/B4/B5/B6・Python文字列)+prefixキー→出力パース(2行形・ラベル分割)→resolve(購入=transfer・移動・休憩)→保存則検査(純資産合計=不変)→p_notice(200イベント×近傍≈9セル・TTPF)。

| 実装 | 秒/tick | 1シミュ日(1,440tick)外挿 | 内訳(秒/tick) |
|---|---|---|---|
| NumPy+numba・セル索引つきp_notice | **0.068** | **約1.6分** | p_notice 0.041・render 0.007・parse 0.005・needs 0.007・move 0.003・wake 0.002・density 0.001・conserve 0.001・cell_hash 0.0001・arbiter 0.0001 |
| NumPyのみ・同上 | 0.060 | 約1.4分 | ほぼ同じ(この規模ではNumPyの配列演算で足りる) |
| 素朴なp_notice(毎回全個体走査) | 0.34 | 約8分 | p_notice 0.315(92%)=設計(セル索引)を守らない場合の例 |

- Python文字列処理(render+parse)=約12ms/tick=3,200呼分 → 1呼あたり約4μs。C++なら10-30倍速いが差は秒〜数十秒/シミュ日。
- 未計上: 経路探索(前計算表でO(1)想定)・会話状態機械・経済センサス・checkpoint・可視性参照。配列指向なら合計で数分〜十数分/シミュ日の範囲【推測】。

## 2. 群衆物理のスパイク(crowd_physics_bench.py・社会力モデル型・2m一様格子・numba並列)

配置: 40万体を6.93km²相当に置き、2%(8,000体)を60m四方(2.2人/m²=スクランブル級)、10%(40,000体)を300m四方(0.44人/m²=駅周辺)に集中、残りは一様。反発力は半径2m・指数型・力と速度に上限。周期境界。

| 対象 | 秒/step | 内訳 | dt=1.0s | dt=0.5s | dt=0.1s |
|---|---|---|---|---|---|
| 全40万体 | **0.028** | 格子構築0.021(単スレッド計数ソート)・力0.0075 | 0.67h/日 | **1.34h/日** | 6.7h/日 |
| LOD=混雑地区のみ(12%・48,000体) | 0.013 | 格子0.012・力0.0014 | 0.31h | 0.62h | 3.1h |

- 格子構築が単スレッドで支配的=並列化で0.005秒級に落ちる余地(→全40万体・dt0.5で約0.6h/日【推測】)。
- GPUの先行実測: FLAME GPU 2(SPE 2023・原文実読)=100万体を約0.003秒/step(V100)。40万体なら約1-2ms/step→dt0.5で約6分/日・dt0.1で約30分/日【文献値からの換算】。予算P1(≤50ms/フレーム@40万体)は保守側。
- 含意: **群衆物理はエンジン側で唯一LLM側(現行14.8h/日)に近づき得る項目**だが、GPUカーネル(Warp/CUDA)に載せれば0.1-0.5h/日、CPUでもLOD+dt0.5で0.6-1.3h/日。言語(Python/C++)ではなく「GPUに載せるか・刻み幅・LOD」が決める。
