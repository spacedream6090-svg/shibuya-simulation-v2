## 2. 艦隊の口の直しと、実 LLM の道の欠陥の直し(§5-2)

### 2-1 艦隊の口の接続の置き場(§1 の 24)

- **先に足した試験は、直す前のコードで赤でした。** 置き場に取り残した接続を作ってから呼を送ると、6 回とも時間切れで、答えは 0 でした(`fleet_answered=0`・`fleet_deferred_timeout=6`)。直した後は緑です。
- 足した試験は 4 本です(`tests/llm/test_fleet_pool_orphans.py`)。どれも、待つのはイベントだけで、時計の長さに頼りません。
  - 段 A: httpcore の置き場が、割り当て直後に取り消された要求の接続を残すこと。上流が直った版では期待を直す、と注に書きました。
  - 段 B: `FleetClient` が、その状態から回復して答えること。
  - 作り直しで進行中の呼を落とさず、全部のクライアントを閉じること。
  - 成功で続いた数が 0 に戻り、古いクライアントの遅い時間切れで作り直しが連鎖しないこと。
- **(c) 回復**: 置き場の時間切れが、同じレプリカで間に成功を挟まずに 3 回続いたら、そのレプリカのクライアントを作り直します。古いクライアントは、進行中の試行が無くなってから閉じます。作り直した回数は、ランの診断の欄 `fleet_client_rebuilt` に出ます(艦隊のランにだけ出ます)。
- **(e) 上限**: 置き場の上限と keepalive を、同時実行の上限(Semaphore)の 2 倍にしました。上限なしにはしていません。
- 1 回の試行を包む `asyncio.wait_for` は残しました(1 呼の全体の締め切りを保つため)。(d) 上流の PR は見張るだけです。
- **発注と違う所(§10 の 5)**: 詰まった置き場で待つ試行は、ほぼ `PoolTimeout` になりません。1 試行の締め切りの方が先に切れるためです。そこで、「httpcore の印を 1 つも受けないまま切れた時間切れ」も置き場の時間切れに数えました。この見分けは、再試行と繰り延べの決まりには使っていません。
