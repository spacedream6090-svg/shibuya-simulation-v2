## 評価 A: エンジン中核(engine・core・manifest・cli.py)

根拠: `engine/systems/*`・`run.py`・`arbiter.py`・`scheduler.py`・`resume.py`・`core/{soa,rng,hashing,write_permit}.py`・`llm/fleet.py`・`cli.py`・IMPLEMENTED #75・#87〜#89・c7-day-4 の実測(`docs/bench/c7/accept_c7-day-4/run_cli_summary.txt`)。手元で 2 点だけ小さく測った。

### 1. 実装と質
- **run_day の分解(#89)**: `run_day`(run.py:1776)は引数 113 個と `conduct()` だけになった。本体は `systems/conductor.py:88-122` で、系の表 `table.py` の 31 系が読み書きする欄を宣言する。`writes.soa` は resolve の口から機械で作る。宣言の外への書き込みは `write_permit` と `guard.system_scope` が実行時に止め、AST と前後の差の試験でも捕まえる。19 構成で結果が 1 バイトも変わらないことも確かめてある。ECS の形に入った大きな前進。
- ただし分解は機械的。各系は旧区間を「文は変えない」で写し、局所変数を箱から結び直しただけ(decide.py:28-60)。補助は今も `engine.run` から引く。道筋の宣言は 180 本中 174 本が `*`。同じ列を 2 系以上が書く例は宣言で 56 列(`activity` は 7〜9 系)。run.py は 2,484 行残り、うち `RunResult` が約 900 行。
- **SoA**: 欄ごとにバイト予算と mechanism/expedient の印を持つ。39 万体でも RSS は 1.6 GB と余裕がある。ただし会話・記憶・意図は Python の dict で持つ(conversation.py:280-290・memory.py:244・intent.py:135)。
- **時刻**: `clock.py` はナノ秒の整数で時刻を持てる。だが主ループは 1 分ごとの全員一斉のままで、事象の待ち行列 `scheduler.py`(596 行)は主ループから使われていない。`1440` の直書きが 45 か所、`// 60` が 28 か所ある。
- **乱数と決定論**: Philox のカウンタ型で、鍵は (seed, 用途)、カウンタは時刻と体から作る。`k19_counters` で隣の流れとの重なりも避けている。順序はハッシュの鍵で決め(commit.py:408・arbiter.py:438)、atomic 演算は使わない。FLAME GPU と同じ形で、理屈の上では GPU でも決定論を保てる。
- **checkpoint**: npz+json・fsync の後に置き換え・sha256・`allow_pickle=False`・設定の指紋の照合までそろい、質は高い。ただし再開できるのは日の境目だけ。
- **艦隊とアービタ**: 非同期の httpx・レプリカごとに 64 本・満杯なら繰り延べ。アービタは 4 クラスの固定優先・昇格・合流を NumPy で行い、入力の並び順に依存しない。よく練られている。

### 2. 性能と 39 万体
- c7-day-4(実 8B を 7 台・39 万体・1 日)の壁時計は 9 時間 10 分、1 tick あたり 22.9 秒。そのうち **`fleet_wait` が 20.45 秒(89%)**で、`llm` が 1.51 秒、エンジン本体は約 0.7 秒。mock なら 1 日 34〜39 分(1 コア)。律速はエンジンではなく、tick ごとにそろうまで待つ作り。
- 処理量は約 82 呼/秒(1 台 12 呼/秒)。e2e の p50 は 4.4 秒なのに、平均 20 秒待っている。**推測**: 毎 tick `wait_idle`(llm_io.py:99・`--fleet-wait-s 120`)で全部そろうまで待つので、GPU が遊ぶ。非同期のクライアントを同期で使っている。
- 手元の実測: `_hash_rows_u64`(hashing.py:147)は行ごとに Python で blake3 を呼び、**39 万行で 332 ms**。体の数に比例して使うと 1 tick の予算を超える。
- GPU 化の妨げ: ①行ごとのハッシュ ②dict の層と呼ごとの Python ループ(decide.py:85・128)③同じ列を多くの系が書く。numba は構築側にしか無い(エンジンでは change_detect の 1 か所だけ)。

### 3. 決定論が縛っていないか
- 縛っている。19 構成の byte-check が強いため、ハッシュ関数・鍵の配置・系の順を変えるたびに版上げが要る。その結果、遅いハッシュや node 幾何で体が重なる癖(#75: 組の 99.7% が距離 0)まで、HEAD と同じ値を守る対象になる。
- 旧版の実 LLM テープ 53 本は今の版で再生できない(#88)。唯一の実データの再現性が、版上げのたびに失われる。
- ライブラリと CLI の既定がずれている: `run_day` は v1・L4 按分・空腹 v1、`cli.run` は v3・無制限・energy(cli.py:102-112・434)。試験の多くは前者を通るので、試験する構成と本番の構成が別物になりうる。

### 4. 同分野との位置
- OASIS(100 万体・確率で起こす人を間引く)に近いのは、アービタで起こす人を選ぶ点。物理・経済・鉄道を 1 本の決定論的なエンジンで扱う点はこちらが厚い。
- AgentTorch/LPM はテンソルと GPU で、LLM は人の型ごとに呼ぶ。こちらは体ごとに呼び CPU で回すので、1 体あたりの費用は桁で重い。
- MATSim は事象駆動で並列に回る。こちらは 1 分の一斉ループのまま(TM の決定は正しい方向だが未実装)。
- resolve を唯一の書き手にした点と二相コミットの厳密さは、Generative Agents や Concordia より上。

### 5. 優先して直すべきこと 上位 3 つ
1. **艦隊の同期の待ちをやめる**: 応答を待たずに進め(TM2「考えている間も体は動く」)、GPU の利用率を記録する。事象駆動の時計(T1・T3)を、計画の第 3 期・第 6 期から繰り上げる。
2. **決定論の契約を「順序に依存しない鍵」にし、関数は凍結しない**: ハッシュを配列演算で作れる形に替えて版上げに束ねる。byte-check は純粋なリファクタにだけ使い、意味のある変更は salt のばらつきの中に収まるかで受け入れる。旧テープは変換器で再生できるようにする。
3. **分解を仕上げる**: `*` の道筋と、複数の系が書く列を絞る。`engine.run` からの引き込みを解く。引数 113 個は `RunConfig` で受け取り、ライブラリと CLI の既定を 1 か所にそろえる。系の並列化と GPU 化の前提になる。

注: 壁時計の予算は redesign.md:491 では「≤8h/日@40万体」、c7_accept.md の W1 では上限 24h で、食い違っている(どちらが今の正典かは未確認)。

### 2. 「住人が決める」はどこまで本当か(数え)

既定のラン(mock・語彙 v3・energy・計画実行層あり)で、1人の1日の判断を並べると次のようになる。

| 決める主体 | 判断の項目 |
|---|---|
| **LLM(実行時)** | 行動語(12語から1つ)/移動の対象欄(解釈できたときだけ)/活動の文と「まで」/招待への承諾/見えている店の名指し |
| **LLM(構築時に1回)** | 週の予定 W17(8B・regex 制約つき。その後コードで修正し、W12 の曲線に寄せる。実行は月曜の行だけ) |
| **コード** | いつ考えるか(起床・不応期・L4 予算)/来る・帰る・寝る・起きる(予定をエンジンが実行。洗い出しの D5・D6・C23〜C25)/カテゴリで頼んだ店の選択(既定は `NearestChooser` の one-hot)/名指しの無い会話の相手/会話の終わり/席30分・列15分・乗車待ち30分・意図60 tick の打ち切り(C18〜C22)/域外の食事/役割の仕事(開閉店の 99.6% は代打。C3)/記憶の重要度と関係の符号 |

- 洗い出しの55行のうち、行動を経ずに結果が出るものは **48行(C29+D19)**、既定で動いているのは45行。群①(本人の選択をエンジンが決めている)は14項。

- まとめ: LLM が実質的に決めているのは「次の1語」と、ときどき「行き先」だけ。**いつ・どこへ・誰と・いつまでの大部分はコードが決めている**。作者の狙いとはまだ距離がある。

合成世界で `Renderer(vocab_version="v3", role_words=True)` を描画した。約1,000 tok(文字数÷2 の見積り)。

### 4. バグの疑い・リスク

- **語彙 v3(CLI の既定)には「ひと言」欄が無い**(`llm/contract.py:879` の `TWO_LINE_RE_V3`)。会話の発話本文が存在せず、口コミの抽出は 0(`engine/wom.py:78` に自認あり)。相手の発話はプロンプトに載らない(`renderer.py` に受け渡しが無い)。会話は「中身の無い3往復」になっている。
- 社会的な起床のうち、近接入替・被注視・傍受の3つは生成元が無い(`change_detect.py:40` に「C2 では検出しない」とあり、参照は `commit.py:151-153` の表だけ)。知人出現は関係 on のときだけ動く。
- `ClassicalPolicy` はプロンプトの日本語を正規表現で読み直している(`classical.py:676-708`)。System 1.5 が描画の文面に依存しているので、テンプレの改版で黙って壊れる。
- 9/22 以降は mock で開発しているので、記憶・関係・意図・選び手は**配管の検証だけで、行動としての検証が無い**。mock は既定で対象欄をほぼ「なし」にする(`move_target_p=0`)ため、エンジンの既定の経路ばかりが試されている。
- 保守性: renderer 2,675 行、contract 1,241 行。v1/v2/v3 の分岐が parser に21か所あり、CLI の旗は85本ある。「既定は1バイトも変えない」腕を積み重ねた結果、既定 off の機能が増え続けている。
- トークンの見積りは文字数÷2(`perception/channels.py:73`)。日本語では実際のトークン数とずれる可能性がある(推測)。共有部の予算 745/750 tok は余裕が薄い。

### 5. 同分野と比べた位置

- **Generative Agents**: 記憶の流れ・内省・計画のうち、ここにあるのは記憶の数式だけ(重要度は固定表で、LLM は採点しない)。内省は数を数えるだけ(`resolve.py:2628`)。規模は4桁大きい。
- **AgentSociety / OASIS**: 行動の語彙を閉じ、露出や移動はコードが決めるという形は OASIS に近い。AgentSociety にある欲求と感情のモデルは無い。
- **Concordia**: GM の LLM が行動を裁く代わりに、物理エンジンが裁く。厳密さは上だが、開かれた行為は「なし」に落ちる。
- **AgentTorch/LPM**: 原型(archetype)を一括して LLM に聞く方式は採らず、1体ずつ描画している。39万体の費用面では不利(推測)。
- **MATSim**: 計画のスコアで再計画する仕組みが無い。選び手には距離減衰を意図的に入れていないので、人流の形(KDDI)に合わせる較正の手段が限られる。
- 再現性(テープ・決定論・凍結 SHA)と、expedient を明記する規律は、これらの先行例より強い。

### 6. 優先して直すこと(上位3つ)

1. **会話と社会の配線を直す**: v3 に会話の行だけ発話欄を足し、会話ターンの B6 に相手の直前の発話を載せる。生成元の無い起床3種と `watched_by` は、作るか、テンプレから消すか、どちらかに決める。いまは「LLM に決めさせている」と言える会話が中身を持っていない。
2. **個体ブロック(B5)に「誰か」と「今日の予定」を入れる**: 共有ブロックを壊さずに、W17 の事実と次の予定の1行を足す。条例の行は条件つきにして B0 を削る。あわせて、GPU が戻ったときのために固定の評価セット(CLAUDE.md §4 の計画)を今のうちに作る。
3. **判断の口を1つにする**: 群①の固定の打ち切り(席・列・乗車待ち・意図・会話の終わり)を `Chooser.probs` 型の「候補 → 選び手」に揃え、呼び出しごとに 1/1.5/2 を振り分ける器を作る(今はランごとの切替)。同時に v1/v2 の経路を引退させ、分岐を減らす。

## 評価 C: 世界データ・人口・経済・較正と検証

対象: src/shibuya/{world,census,build,economy}、tools/realworld_fetch、tools/c7、docs/bench(c7・anchors・analysis・c8/sensitivity_v1.md)、docs/data-license-ledger.md。コードと記録を読んだだけで、ランも data/ の実体確認もしていない(data/ はリポに無い)。

### 1. 何が実装されているか(質)

- **世界の構築(W0〜W20)**: OSM の歩行グラフ 3,499 ノード/4,944 辺(w1_walk_graph.py)、100 m 格子 × 3 層で 520 セル(w2_cells.py。街区面は回転系の走査を自前実装)、全点対 next-hop(w3_distances.py、numba Dijkstra)を作り、ハッシュで凍結する。holdout の封印は w19_freeze.py:40-43 の 3 層で、sha256 を取るうえに build 配下のコードが封印層の名前を参照していないかを静的検査する。仕組みとしてはよくできている。
- **合成人口(W16)**: 国勢調査 2020 の小地域表を使い、16 階級 × 性別の**結合表で IPF**(w16_population.py:465-476)。年齢不詳の按分や町丁目の被覆率(10 m の標本格子)も手当てしている。住居は建物の床面積で按分(:1143-)。従業者は経済センサスの組織の席から作る。PopulationSim 系の作法に沿っており、住民側の質は高い。
- **来街者の数と時刻**: 数は PT の「自宅−私事/自宅−勤務」の比 × 従業者の席数(:413-419)。時刻は W17 で 8B の LLM が週の日課を書き、修復したあと 2015 年の大都市交通センサスの時刻分布へ raking する(w17_schedule.py:1294-)。
- **経済**: 単一の transfer API、書き込み不可の配列、AST 検査、四重記入の検算(ledger.py・checks.py)。会計の器は堅い。

### 2. 良い点

- 事前登録 v1.3 の作り方は分野の水準を超えている。腕・指標・線・予想を開封前に固定し、家族 95% で同値検定、undecided を合格に数えず、停止則を置き、外れた予想も記録した(prereg_arms_v1.md §6-8)。LLM の社会シミュ(AgentSociety・OASIS・Generative Agents)で、封印した現実データに 0/4 と書いて公開した例は見当たらない。

### 3. 問題点・リスク

**(A) 較正が効いていない。holdout の 0/4 はかなりの部分が予想できた**
- W17 の時刻の較正は「修正率 20% 未満」という予算に縛られ、raking に使えたのは 9.4% だけ(ADAPTIVE_MODIFIED_TARGET=0.19・:103)。raking 後の JSD も「自宅−勤務 0.42/私事 0.23」と大きく残っている(world-data-build-spec.md:451)。さらに較正カーブは**乗車時刻の分布**(2015 年)で、目的地への到着時刻ではない。ActivitySim は目的別の出発時刻分布を調査に合わせ込むのが標準なので、作者が一番言いたい「時刻の形」が実質的に較正されていない。PT の時間帯別表 c-2 は 09-30 に取得済みだが、コードからはまだ使われていない(grep で 0 件)。
- 来街者を作るとき、PT の「私事(自宅以外から)106,681」を入れていない(:416 は自宅−私事だけ)。R-109 は指摘しているが、sub_e の原因の表には無い。夕方 18 時のピークの有力な担い手は「勤務→私事」の連鎖で、これが無い。通勤者は計画の終わりに即時に退出する(walk_to_platform は既定外)。〔推測: ピーク時刻の外れの主因の一つ〕
- 来街者の骸格の日課も 10:00 着に固定されている(w17_schedule.py:929)。

**(B) holdout の比較の定義のずれ(未対処のもの)**
- KDDI は「国内居住者・au の同意ユーザー・20 歳未満を除く」(d1_reacquisition.md:203-208・R-56)。一方 c7lib.py:97-107 は訪日来街者(kind 7)を「来街者」に入れていて、attr_arms.py にも訪日を外す腕が無い。central の 03 時の在圏の 87% は訪日なので(sub_e §2-5)、H3 と H5 に直接効く。
- KDDI は年間合算で週末を含む。sim は月曜 1 日。この差は記録済みだが、補正の腕は無い。
- 移動は既定の node 幾何で、1 tick に 1 ノード(graph.py:75-87)。実資産では約 2.3 km/h になる(c9-geometry-brief.md §1.3)。c7 の本番 3 本はこれで回っている(推測: C9 の前のランなので)。

**(C) 次の test 層は独立でない疑いが強い**
- shibuya_jinryu は、開封済みの kddi_la と同じ KDDI の 2018〜2024 月次である(shibuya_jinryu.py:7-11、44-49)。パターン台帳 §10-2 も「人流 2018〜2024 は開封済み」と書いている。R-56 §3-4 の「日次 CSV なので平日で比べられる」は、取得日でフォルダを分けた day_dir(common.py:371)を日次データと読み違えた可能性が高い。
- 時間帯の軸の有無も文書どうしで食い違っている。d1_reacquisition.md §3-3 は「5〜28 時あり」、shibuya_jinryu.py:48 は「無し」。
- 封印前に、設計者が KDDI のピーク 18 時と属性シェアをすでに見ていた(pattern-ledger D1′、kddi-attribute-shares-2024.md・09-03)。D1′ には「起草時に目視済み」の宣言が無い。

**(D) 経済は会計の器で、経済の動きはまだ無い**
- ラン中に使われる科目は CONSUMPTION・CARRY_IN・CARRY_OUT(運賃)・IMPORT_PURCHASE・ENTRY_CAPITAL だけ。monthly_wages(anchors.py:217)と pricing(Calvo など)は試験からしか呼ばれず、給料日も既定でなし(calendar.py:24)。税・家賃・利子・配当は列挙があるだけ。

- 居住者の初期現金を「来街者持込」科目で入れている(ledger.py:516-)。

**(E) ライセンス**
- OSM: 「出力に OSM の生値を載せないので share-alike を回避」(台帳 :9)は ODbL の整理として不正確。POI の位置などを持つ世界資産は派生 DB で、公開利用すれば 4.6 条の提供義務がかかる。ODPT チャレンジの「成果物を無償公開」と組み合わさるので、法務の確認が要る。
- KDDI の Power BI ダッシュボード由来の生 JSON を「同系列として CC BY 4.0」と推定している(台帳 :19)。ダッシュボードの規約は未確認。
- JR の時刻表の「電磁媒体への加工を禁ず」とチャレンジ限定枠(目的は応募に限る)を本体の構築に使っている。研究段階の判断として記録はあるが、作者の狙いである「最初の顧客=小売・行政」への商用化の前に、置き換えか許諾が必須になる。
- 一方で、e-Stat・PLATEAU・PT の出典表記と再配布しない運用は丁寧にできている。

### 4. 同分野との位置

- MATSim は交通量カウントへの継続的な較正(Cadyts)、ActivitySim は調査から推定した選択モデル+定数の反復較正、Replica は携帯位置データで学習し地域ごとにカウントで検証する。本リポは**検証の規律ではこれらと同等以上**だが、**較正の仕組み(目標に合わせて繰り返す手続き)が無く**、構築時に 1 回合わせて終わる。
- AgentSociety は経済(企業・銀行・政府・賃金・税)をごく簡素ながら閉じている。本リポの会計の厳密さはそれを上回るが、経済の動きは下回る。

### 5. 優先して直すこと 上位 3

1. **時刻の形を正面から較正する**: PT c-2 の目的 × 着時間帯を較正の目標にし、予算に縛られない IPF/raking か生成時の条件づけで合わせる。来街者に「勤務→私事」「自宅以外からの私事」の連鎖を足す。PT は地域や人で較正用と検証用に分ける(§10-2 の要決定)。
2. **比較の定義を揃えてから次の事前登録を書く**: 訪日を除く・20 歳未満を除く・area 写像・滞在 30 分・週末を含む重みの腕。あわせて test 層の独立性を実データで確かめる(shibuya_jinryu の期間と時間帯の軸)。独立でなければ K5(2025 年以降)か、別ベンダ(D1b)を test にする。
3. **経済の主張を実態に合わせる**: README を「会計の器と保存則」に直す。賃金・価格・在庫補充をつなぐまで、売上や消費を現実の指標と並べない。あわせて ODbL の派生 DB の扱いを、公開(ODPT チャレンジ)の前に整理する。

### 7. 優先して直すべきこと(上位 3 つ)

1. **CI を緑に戻し、第三者が再現できる形にする。**

2. **「現実との差」を測る mock の回帰テストを 1 本常設する。** 5,000 体・mock/classical で、在圏のピーク時刻・来街者比・エリア JSD を毎回出して記録する。holdout は開けず、較正側のアンカー(PT・センサス)を使う。来街者の時刻形状(W17)の修正を、第 4 期を待たず前倒しできるか判断する材料にする。
3. **記録を一元化して写しを減らす。**
   - 決定は決定台帳 1 か所を正にし、他は ID リンクだけにする。
   - IMPLEMENTED は 1 項 2〜3 行に縮める。
   - README・概要図は計画の版上げごとに必ず更新する。
   - 「判断待ち」と「作者の手作業」を週 1 回まとめて出し、判断の割り込みを減らす。
