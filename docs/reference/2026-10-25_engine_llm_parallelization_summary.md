# 渋谷LLM社会シミュレーター：判断頻度・並列処理・高速化の議論まとめ

## 1. この文書の目的

本書は、渋谷シミュレーターについて議論した次のテーマを、実装判断や別のLLMへの引き継ぎに使えるよう整理したもの。

- 人間の「意識的な判断」が1日に何回あるか、その研究上の限界
- 人間の判断頻度をシミュレーターのLLM呼び出し頻度へ反映する際の考え方
- エンジン側とLLM側を同時に処理できるか
- 現行リポジトリで確認できる性能値と、実際のボトルネック
- 今後の並列化・推論高速化・LLM呼び出し頻度最適化の方針

**重要：** 以下では、リポジトリに記録された実測値、外部研究から読み取れる範囲、設計上の提案・仮説を区別する。推定値を実測値として扱わない。

対象リポジトリ：<https://github.com/spacedream6090-svg/shibuya-simulation-v2>

---

## 2. 要点

1. **エンジンとLLMは同時に処理できる。** 現行設計でも、LLMへのリクエストはバックグラウンドのイベントループから非ブロッキングで発行され、エンジンは応答待ちの間に別の処理を進める。
2. **並列化の仕組み自体はすでに存在するが、全体の実行時間はLLM艦隊の処理能力に強く制約されている。** 現行の本番実行は約9〜9.5時間/シミュレーション日。エンジン単独の換算値は約1.4時間/日。
3. **非同期化は推論時間そのものを短くしない。** GPU側の処理能力を超えてリクエストを発行すると、待ち行列や繰り延べが増える。したがって「エンジンが待たずに進むこと」と「シミュレーション全体が早く完了すること」は分けて考える。
4. 高速化は、①エンジン・LLMのパイプライン並列化、②LLM推論のスループット改善、③LLM呼び出し総数の最適化、の3方向を併用する必要がある。
5. **人間の判断頻度には信頼できる単一の標準値がない。** 1日3万5千回の判断という有名な数値は、厳密な実測根拠が確認できない。思考の切り替わりの推定値を、意思決定の回数として扱うのも不適切。
6. 現時点で約7回/人/日のLLM呼び出しがある一方、これは人間の判断頻度の実測値ではない。起床候補の選定、呼び出し予算、キュー容量などの実装仕様にも左右される。

## 3. 人間の判断頻度について分かっていること

### 3.1 数字をそのまま使えない理由

「判断」と呼ぶ範囲が研究によって違う。意識して比較検討する重要な判断だけを数えるのか、何を食べるか・どちらへ歩くかといった小さな選択も含めるのかで、数字は大きく変わる。また、自己報告型の研究は、本人が思い出せない判断や自動的な選択を取りこぼす可能性がある。

| 数字・主張 | 根拠と解釈 | シミュレーションへの使い方 |
|---|---|---|
| 約5回/人/晩という計算値 | 134人が6晩にわたり自己報告した判断が計3,850件。3,850 ÷ (134×6) ≈ 4.8件/人/晩。ただし、研究は日々の全判断を網羅的に数える設計ではなく、回想による報告である | 意識的判断の厳密な平均値とはみなさない。明示的に思い出せる判断の下限寄りの参考値として扱う |
| 約70 choices/日 | Sheena Iyengarの2011年TED講演で、米国人2,000人超の調査を紹介した自己申告値。広い意味の「選択」を含み、厳密な全数カウントとは異なる | 日常の小さな選択も含む広義の選択数の参考値。熟慮的判断だけの数字ではない |
| 約4,000〜6,240/日 | 思考の切り替わり・メタ状態遷移などから導かれた推定。これらは意思決定そのものを計測した数ではない | LLM判断呼び出し数へ直接転用しない。思考イベントと行動選択を分離する必要がある |
| 35,000判断/日 | この数字を厳密に数えた研究上の根拠が確認できず、広く流通する主張として扱うべき | 基準値として採用しない |

### 3.2 設計上の暫定値

会話で検討した **5〜20回/人/日** は、科学的に確立した人間の平均ではない。意識的な判断をどう定義するかが確定していない段階での、実験用の暫定的な設計レンジである。

シミュレーターでは、次の3つを区別して計測する。

- **行動・状態更新：** 移動、計画された活動の継続、身体状態や環境状態の更新。すべてをLLM呼び出しにしない。
- **速い判断：** 習慣から外れた場合や、状況に応じた選択が必要なときの低コスト判断。
- **熟慮・言語生成：** 葛藤、重要な判断、会話、説明や自由記述など、LLMにより高い推論能力が必要な場面。

この分類では、LLM呼び出し回数を人間の判断回数と一対一対応させない。1回の呼び出しが複数の内部的な判断をまとめて表現する場合もあれば、一つの社会的な意思決定に複数回の呼び出しを使う場合もあるためである。

## 4. 現行リポジトリの設計と確認できる性能値

### 4.1 アーキテクチャの基本方針

READMEと詳細設計では、役割を次のように分離している。

- **エンジン：** 世界状態、物理・移動、世界過程、資源制約、経済台帳、状態の整合性、行動の実行可能性を扱う。
- **LLM：** エージェントの意思決定や発話を出力する。LLM自身が世界状態を直接書き換えるのではなく、出力をエンジンが検証・適用する。
- **コミット処理：** 意図を集め、資源制約を裁定し、単一の書き込み経路で状態に反映する。
- **再現性：** 応答テープや決定論的な適用順序などにより、ランの再生・検証を行う。

現行設計では、前tickのLLM応答を適用し、世界過程と計画実行層を進め、変化検出と起床候補選定を行い、選抜したエージェントの観測を描画してLLMへリクエストを送る。LLM応答は非同期に戻り、エンジン側の適用処理へ渡される。

### 4.2 規模と性能（記録されたランごとに分けて読む）

| 指標 | リポジトリ記録にある値 | 注記 |
|---|---:|---|
| エージェント数 | 390,067体 | 渋谷駅周辺のシミュレーション母集団 |
| 1日のtick数 | 1,440 | 1分刻みのシミュレーション日 |
| 現行のLLM構成 | 7×NVIDIA A5000、Qwen3-8B INT8、vLLM | 実行環境の記録 |
| 本番ラン例A | 2,706,593呼、約9時間10分、約6.94呼/体/日 | README記載のC7本番結果 |
| 本番ラン例B | 2,805,670呼、約9時間29分、約7.19呼/体/日 | C7-day-3の記録。上のランと混同しない |
| エンジン単独の換算 | 約3.49秒/tick、約1.4時間/日 | 390,067体のmock LLM計測からの換算 |
| 艦隊待ちが大きかった例 | 22.9秒/tickのうち、fleet wait 19.37秒（約84%） | C7-day-2での実測。ラン構成が異なる |
| 別の本番ランの待ち割合 | fleet waitが壁時計時間の約89% | C7-day-3の記録 |

これらは異なるラン・設定の値を含む。性能差を議論する際は、母集団、呼び出し数、キュー容量、計画・世界資産の版、モデル設定、GPU構成を合わせて比較する。

### 4.3 性能以外の重要な制約

READMEには、KDDIの滞在人口holdoutとの照合が4つのコア指標で合格していないことも記録されている。具体的には、在圏人口のピーク時刻がシミュレーションでは10〜13時、実データでは15〜18時となる問題や、来街者比のずれがある。エンジンやLLMを速くしても、現実との整合性が自動的に改善するわけではない。

また、会話・記憶・関係性など、READMEで未実装と宣言されている機能が残る。高速化の成果は、呼数や壁時計時間だけでなく、実際の行動分布・相互作用・現実データとの整合性とセットで検証する必要がある。

## 5. エンジンとLLMは同時に処理できるか

**答え：できる。現行設計でも非同期・非ブロッキングなLLMリクエストを利用している。** ただし、任意の処理を因果関係を無視して同時に確定できるわけではない。

### 5.1 同時処理のイメージ

```text
                    ┌────────────────────────────┐
                    │      エンジン（CPU）        │
                    │ 世界過程・移動・状態更新    │
                    │ 変化検出・候補選定・裁定    │
                    └────────────┬───────────────┘
                                 │ 観測・リクエスト
                                 ▼
                    ┌────────────────────────────┐
                    │       LLM艦隊（GPU）        │
                    │ 複数エージェントを並列推論  │
                    └────────────┬───────────────┘
                                 │ 応答（非同期）
                                 ▼
                    ┌────────────────────────────┐
                    │    応答キュー／適用管理     │
                    │ 前提・時刻・順序・資源を検査│
                    └────────────┬───────────────┘
                                 ▼
                    ┌────────────────────────────┐
                    │ エンジンが状態を確定・更新  │
                    └────────────────────────────┘
```

エンジンが独立した世界過程を計算している間に、GPUはすでに発行されたLLMリクエストの推論を進められる。応答を待つ間、エンジン全体を毎回停止させる必要はない。

### 5.2 なぜ非同期化だけでは9時間が消えないのか

非同期化はCPUの待ち時間を隠したり、独立した仕事を重ねたりする技術であり、GPUの推論処理そのものを無料にしたり、短くしたりするものではない。

現在の実測では、エンジン単独なら1日分を約1.4時間で進められる一方、実LLMを使った本番ランは約9〜9.5時間かかる。いくつかの本番計測では壁時計時間の約84〜89%がLLM艦隊の待ちに関連している。これらからは、現状の主要な制約がエンジンの演算だけでなく、LLM応答の処理量・キュー待ちにあると考えられる。

リクエスト発行を増やしすぎた場合、GPUの処理能力を超えた分がキューに蓄積するか、アービタによって繰り延べられる。したがって、**エンジンが待たずに進めること、LLMが単位時間あたりに応答を返す量、シミュレーション日全体の完了時間**を別々に計測する。

### 5.3 並列化で守るべき因果関係

- LLM応答が来る前でも、応答結果に依存しない世界過程や別エージェントの処理は進められる。
- 未確定の購入判断などを前提に、その購入が成功したことを要求する後続行動を確定してはならない。
- 応答が古い観測に基づいている場合、適用時に位置・在庫・権限・対象の状態などを再検証する必要がある。
- 応答の到着順だけで結果を変えないよう、適用時刻・優先順位・競合解決規則を明確にする。
- 再現性を保つため、リクエストと応答、繰り延べ、再投入、応答の適用タイミングを記録し、テープ再生で検証する。

## 6. 高速化の3方向

### 6.1 ① エンジンとLLMのパイプライン並列化

**狙い：** LLM応答待ちの間に、依存しないエンジン処理や別エージェントの準備を進める。

実施候補：

- リクエスト生成・送信・応答受信を、エンジンのtick処理から適切に分離する。
- 既発行のリクエストが推論されている間に、独立した世界過程、観測の前計算、別の候補の準備を進める。
- 「応答が来るまで待つ必要がある行動」と「エンジン側で継続可能な活動」を明示的に分類する。
- どの状態スナップショットをLLMに見せたか、どのtickで返答を適用するかを記録する。

**注意点：** パイプライン化で隠せる待ち時間には上限がある。次の状態がLLMの返答に依存する場合、そこを無条件に先行確定するとシミュレーションの因果整合性を壊す。

### 6.2 ② LLM推論のスループットを上げる

**狙い：** GPU群が単位時間あたりに処理できるリクエスト数を増やす。

実施候補：

- GPUあたりの実効スループット、キュー滞留時間、TTFT、end-to-end latency、バッチサイズを計測する。
- vLLMの同時実行数、バッチング、GPU間の負荷分散、キュー容量を検証する。
- 入出力トークン数、max tokens、モデルサイズ・量子化方式などを比較する。
- 大量の軽い判断をより小さいモデルに任せ、より重いモデルへの競合を減らす。
- GPU追加の効果は、モデルの並列効率・通信・キュー制御を含むベンチマークで確認する。

**注意点：** GPU数を増やした場合の速度向上は、単純にGPU数に比例するとは限らない。実測値を基に計画する。

### 6.3 ③ LLM呼び出し総数を最適化する

**狙い：** 同じ実行時間で、より豊かな認知や社会的相互作用を扱えるようにする。

設計候補：

- 習慣的な行動や既定の活動継続は、エンジン側の状態遷移として処理する。
- 状況が変わった、予測が外れた、身体的な違和感がある、社会的に重要な出来事が起こったといった場面で判断候補を立てる。
- 軽量判断モデル（Jev型decision modelなどを含む候補）で日常的な選択を処理し、会話・言語生成・大きな葛藤・高い重要度の判断だけLLMに振り分ける。
- 速い判断と熟慮を分け、トークン上限、処理頻度、昇格条件を独立に調整する。
- 個体の内部状態・記憶・経験が変化検出や判断にどう影響するかを評価する。

現行設計の起床候補は、計画境界、個体の変化、セルの変化、会話、顕著な出来事、繰り延べられた呼など複数の要因に基づく。一方、**予測誤差を中核にして「どれほど意外だったら熟慮を起動するか」を決める仕組みは、設計候補と実装済み機能を分けて確認する必要がある。** リポジトリのPENDINGには、予測誤差の設計判断が保留とされた記録がある。

## 7. LLM呼び出し数の概算と解釈

現行の記録で約6.9〜7.2呼/体/日を使う場合、390,067体では概算で約270万〜281万呼/日になる。仮に15呼/体/日に増やすと、約585万呼/日となる。

現行の処理速度が同等で、呼あたりのトークン数やモデル負荷も同程度だと**仮定**すれば、呼数が約2倍になることで総実行時間も概ね増える可能性がある。ただし、この比例換算は予測のための目安であり、実測保証ではない。出力長、キュー飽和、繰り延べ、バッチ効率、起床分布、呼び出しの時間帯などによって変わる。

また、現在の呼数は人間の「意識的判断」の回数を直接測った数字ではない。エンジンが生成した起床候補、アービタの優先順位、予算上限、繰り延べ、LLM出力の適用規則で決まる実装上の値である。呼数を増やせばリアリティが増すとも限らない。出力が現実の行動分布や社会的相互作用を改善したかどうかを同時に検証する必要がある。

## 8. 推奨する実験計画

### 8.1 まず計測を分離する

各ランで最低限、以下を別々に記録する。

- エンジン処理時間（tickごと・フェーズごと）
- LLMリクエスト数、実際に応答が返った数、繰り延べ数、再投入数、失敗数
- キュー待ち時間、TTFT、end-to-end latency、GPUごとのスループット
- リクエスト当たりの入力・出力トークン数
- 起床理由別の候補数・採択数・繰り延べ数
- エージェント当たりの呼数、行動分布、会話回数、重要イベントの発生数
- tickごとの状態ハッシュ、テープ再生一致、資源保存則
- 現実アンカーとの一致度（在圏分布、時間帯別ピーク、来街者比など）

### 8.2 最小の比較実験

1. **ベースライン：** 現行構成を同一seed・同じ世界資産で実行する。
2. **パイプライン実験：** 独立したエンジン処理をLLM応答待ちに重ね、壁時計時間と因果整合性・テープ再生を確認する。
3. **推論性能実験：** キュー容量、同時実行数、バッチ設定などを一つずつ変更し、実効応答数/sと待ち時間を計測する。
4. **呼出頻度実験：** 呼数予算や速い判断の比率を変える。既存のablationで呼数予算が購入行動などの結果に影響したことが示されているため、速度だけでなく行動結果も比較する。
5. **ハイブリッド判断実験：** 軽量判断モデルとLLMの振り分けを導入し、総呼数・行動分布・現実整合性を比較する。

すべての実験で、処理時間の改善だけでなく、同seed再生、保存則、応答適用の決定性、ホールドアウト指標を回帰検査する。

## 9. 実装・設計上の判断指針

- **世界状態はエンジンが管理し、LLMは意図・発話を返す**という責務分離を維持する。
- 非同期化を進める際は、CPUとGPUの処理を重ねられる範囲と、LLM応答に依存する因果境界を明示する。
- 同tick内で独立に計算できる個体の知覚・候補生成は並列化し、世界状態への書き込みは決定論的な裁定・コミット経路に集約する。
- 1,440 tickの時間依存関係を単純に消すことはできない。ただし、全tickを全エージェントに同じ詳細度で計算させる必要はなく、イベント駆動・活動の継続・動的LODを用いて不要な再計算を減らせる。
- LLMの応答遅延や繰り延べを「細かい実装問題」として隠さず、モデルの時間的な振る舞いに与える影響を測定対象にする。
- 予測誤差を採用する場合は、驚き・重要度・新規性・直近の失敗・社会的露出のような候補を整理し、重みや閾値を固定の真理として扱わず、感度実験と現実データによって較正する。
- 最終的な目標は単純な呼数削減ではなく、**計算資源あたりの社会的・行動的な情報量と現実整合性を高めること**である。
